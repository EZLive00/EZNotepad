# 开发经验与心得

这是一个写了好几个月的纯前端 + Tauri 桌面记事本，功能密度不低：所见即所得编辑、
CodeMirror 源码模式、大纲、查找、多标签、独立对比窗口、真机验证工具链。这里把
一路上真金白银换来的经验按主题沉淀下来，供后续开发（以及别的项目）翻阅。

> 配套文档：结构设计见《架构设计.md》，跨平台清单见《跨平台移植.md》，构建步骤见
> 《构建说明.md》；真机测试方法论见 `test/real/TEST-PLAN.md` 与 `RESULTS.md`，
> 长线项目约定见 `.workbuddy/memory/MEMORY.md`。

## 一、架构判断：哪些决定被证明是对的

**1. 纯 ESM、无打包器，`src/` 编译期内嵌进二进制。**
前端没有 vite/webpack，浏览器直接吃原生 ES Module。代价是必须 `cargo build`
才能看到前端改动；换来的是：零构建配置、改哪看哪、vendor 的第三方库
（CodeMirror、KaTeX、lucide）提交进仓库后**永远可复现**，不怕 unpkg 改版。

**2. 模块边界按「谁独占某个 API」划，不按功能划。**
CodeMirror 6 的状态是一坨全局单例，任何地方散用 `EditorState` 都会出诡异 bug。
所以规定：**CM6 API 只有 `plain-editor.js` 能碰**，其他模块只调它暴露的
`value / selection / revealOffset`。同理序列化只认 `markdown.js`。这条边界
整个项目没破过一次，后来排查问题也从不用怀疑「是不是两处各改了一份状态」。

**3. 性能约定先立后写。**
「输入路径禁止全量重算」是项目早期就写死的规矩：normalize 只扫光标块 ±1、
大纲 250ms 防抖 + 结构签名、标签栏签名比对。后期加对比窗口、加 callout 时
新代码照抄这套模式，没有出现过「加了功能打字变卡」的回退。

**4. 每功能一提交，约定式前缀 + 一句话说清「改了什么」。**
回溯某个 bug 是哪次改动引入时，`git log --oneline` 一眼可读，比「fix bug」式提交
省一个数量级的翻找时间。（2026-11-02 起提交信息统一用英文，见《构建说明.md》§九。）

## 二、Tauri / Windows 原生窗口：这一轮最深的水

**1. tao 的 maximize 在无边框窗口上是坏的（最大的一个坑）。**
`decorations:false` 的窗口，tao 的 `WindowState` 在窗口还没 VISIBLE 时就把
MAXIMIZED 标志位写成 true，却跳过 `ShowWindow(SW_MAXIMIZE)`；此后任何
`maximize()` 都因「标志位没变化」被直接忽略。实测四种时序
（builder `maximized(true)` / 建完立刻 / `on_page_load` / 前端调用）全部无效。
**结论：别跟窗口状态较劲，直接算矩形。** 用 `SPI_GETWORKAREA` 拿工作区 +
`SetWindowPos` 摆位，注意还要按 DWM 隐形边框外扩 8~9px，可见区才正好贴边。

**2. 建窗口的命令必须是 `async fn`（血泪第二课）。**
症状极具迷惑性：窗口壳子、标题、尺寸全对，**页面永远不加载，整扇窗子纯白**。
根因：Tauri 的同步命令在主线程上执行，而 `WebviewWindowBuilder::build()` 要等
WebView2 回调 —— 主线程被自己占着，`build()` 卡到超时。命令行参数路径走
`setup()`、本来就在主线程外，所以同一份代码一条路好一条路坏。
**教训：凡是「建窗口 / 弹对话框」的命令，一律 async。**

**3. 没有日志时排查窗口问题，别猜，往流程里埋点。**
把关键节点（spawn start / building / page started / fill ok）追加到
`%TEMP%` 下的日志文件，一次真机运行就能看出卡在哪一步。注意**不能用窗口标题
输出诊断** —— 测试工具按标题找 HWND，改标题会让工具失明。

**4. 多窗口的权限要单独登记。**
第二个窗口必须在 `capabilities/default.json` 的 `windows` 数组里出现，否则
所有 `core:window:*` 调用静默失败（不报错，只是不生效）。前端窗口操作大面积
失效时先查这里。

**5. 跨窗口传参别走 URL query。**
中文文件名经过双重编码后跟磁盘路径对不上。改成 Rust 侧放一个
`Mutex<Option<T>>` 状态 + 前端 `take_xxx` 命令取一次，简单可靠。
窗口已开时复用：`unminimize + show + set_focus` 再 `emit` 推新数据。

**6. WebView2 的参数黑名单。**
`--disable-gpu` / `--in-process-gpu` / `--enable-low-end-device-mode` 它一概
不吃，参数层压不动内存。真正需要的是 `--disable-gpu-sandbox`（否则 GPU 沙箱
崩溃）。内存口径用 `WorkingSetPrivate`，`PrivateMemorySize64` 虚高 60MB。

## 三、前端工程：编辑器类应用的特殊纪律

**1. contentEditable 的光标是易碎品。**
任何「重建 DOM」的操作都会丢光标，所以规矩是：打字路径只动光标所在块 ±1；
需要整块替换时（如标题降级）先记光标偏移再 `restoreCaret`；`contentEditable=false`
的子元素（如 `###` 哈希把手）绝不混进 `.w-text`，且所有白名单 sweep 都要带上它。

**2. 「编辑态」的脏标记必须覆盖所有写路径。**
本轮真机抓到的丢数据 bug：打字走 `flush()` 会标脏，但 Enter / Backspace 并行 /
Tab 这类结构性编辑走 `applyEdit()`，忘了标脏 → `Ctrl+S` 判定「无改动」直接丢。
**教训：每加一条写路径，先问「脏标记在哪」，写测试时每条路径都要有落盘断言。**

**3. 虚拟滚动三个关键件缺一不可。**
固定行高（CSS 变量，字号缩放同步重算）、可视区 ±6 行的窗口渲染、
`top = i * ROW_H` 的绝对定位。另一个容易踩的：行容器和「当前块」覆盖层必须
分开两个 div —— 高亮写在行上会被逐行画成表格格子。

**4. 行尾与快照校验的「假失败」。**
`core.autocrlf=true` 时磁盘文件是 CRLF，脚本生成的字符串是 LF，内容一致也判
不一致。所有「自己生成的字符串 vs 磁盘文件」的比较，读取时统一
`.replace(/\r\n/g,'\n')`。**症状识别：校验失败但 `git diff` 该文件为空。**

**5. diff / 比较类功能的边界永远比主体难写。**
空行算不算块、忽略空白后行号怎么对齐、「仅左」「仅右」「修改」三态与行内
mark 的组合、块区间从起点扫到第一个 `same` 为止（不能用「下一块起点 -1」）——
这些边界都要在夹具里有一行对应的用例。

**6. 「看起来像」的启发式，最后一定会被用户当成 bug。**
大纲面板最初对纯文本用「像标题的行」规则（`1.` `2.` `3.` 开头、`====`、`【】`），
结果一份带序号的清单或日志就是「每行都是大纲」，而且统统压成同一级；`====`
自己还成了空标题。用户第一句话就是「txt 每行都当做大纲了吧」。
正确做法是先问「这个格式里**什么是结构**」，再只认那些标记：`#`、Setext 下划线、
`【章节】`、`第X章/节/条`、多级编号（点号段数就是层级）。单级编号更微妙 ——
`1.` 既可能是章节也可能是一张清单，用「空行断组后只剩它一条」区分。
把「猜」换成「认」，规则反而更短、更好解释，空态也能说清「缺什么」而不是
含混的「没有可提取的结构」。

## 四、真机验证：比单测贵十倍，也只有它能抓到单测抓不到的

**1. 分层：单测抓逻辑，真机抓「系统集成」。**
本项目 155 项单测全绿，但「菜单开窗口页面白屏」「tao maximize 失效」这类
问题只有真机能暴露。真机工具链自己搭（UIA 按键名找菜单、SendInput 合成鼠标、
CDP 读状态、BitBlt 截图 + 局部放大），比引入 Playwright/Electron 系工具轻得多。

**2. 合成点击的坐标系要「相对量」。**
无边框窗口铺满/还原切换后绝对坐标全废。约定从窗口右下角（或矩形）量坐标，
放大截图人工量按钮位置一次、写进用例生成器，之后窗口尺寸再变也不怕。
特别注意 DWM 隐形边框：窗口 rect 原点不在可见区左上角（实测 `-7, 0`）。

**2.5 输入前必须验证「前台真的是被测窗口」。**
SendInput 的点击/键盘落点是全局的：另一个应用（比如最大化还弹着对话框的
Chrome）盖在屏幕上时，全部输入静默落进它那里，而 `PrintWindow` 截图不依赖
z-order，画面永远「看起来正常」——这个组合能浪费一整个下午。正解是发输入前
`ForceFocus` 并**核实** `GetForegroundWindow()`，失败就大声报错，绝不静默继续。

**2.7 原生文件对话框走 Win32，不走 UIA。**
Vista+ 的 IFileDialog 保留老模板控件 ID（路径框 1148/1152、IDOK=1），UIA 对
路径框暴露不稳定且新建顶层窗口可能几秒都进不了托管 UIA 的桌面查询。
路径用 `WM_SETTEXT`（文件夹选择器**不收正斜杠**），找对话框用
`EnumWindows`（可见 `#32770` + pid），确认用 `PostMessage(BM_CLICK)`——
**SendMessage 等回复期间对话框自我销毁会直接崩掉调用进程**；报 ok 前等对话
窗口真正消失，否则「文件夹名无效」的横幅会把假成功递给你。

**3. 每条真机用例自带断言与夹具重建。**
用例开头先重写夹具文件（不依赖上次运行残留），结尾用字节比对校验收盘内容，
中间的关键状态（窗口矩形、页面标题、统计行文字）靠 `wins` / 截图三重交叉。
**「看起来对」不算过，能机器判读的判读，不能的截图放大人工看。**

**4. 测试环境的噪音要提前识别。**
vitest 在沙箱里报 `EPERM ...\Temp\...` 是环境噪音不是项目缺陷（`TMP` 指到
`node_modules/.tmp` + `--no-file-parallelism` 可绕）；`cargo test` 报
「拒绝访问 os error 5」多半是残留进程占着产物，重跑即可。**先分类「假失败」，
别急着改代码。**

## 五、过程方法论

**1. 一次只怀疑一个变量。**
「菜单路径白屏」排查走过：先怀疑时序 → 加前端兜底 → 怀疑权限 → 怀疑
`on_page_load` 没触发 → 最后靠全链路日志锁定 `build()` 阻塞。回头看，第一步
就该埋日志；**盲改三处不如日志一处**。

**2. 修完立刻删诊断代码，但把结论写进文档。**
本轮日志、看门狗、标题诊断全部清干净后才提交，根因与修法沉淀到
`RESULTS.md` 的「这轮修掉的 4 个坑」表格。代码要干净，**知识要留下来**。

**3. 根因修法要能一句话讲清。**
「tao 标志位先写后跳过」「同步命令占主线程」——如果一个 bug 的根因不能
一句话说清，说明还没真正定位，修了大概率会复发。

**4. UI 的美观靠纪律不靠灵感。**
三层底色分界靠面不靠线、圆角只有三档、accent 只给当前态、浮层不写 border
走 shadow —— 这些约定写进长期记忆，每次新界面照抄，风格自然统一，评审
成本趋近于零。

## 六、如果重来一次

- **窗口管理第一周就该建真机工具链。** 多窗口、无边框、DWM 这些问题躲不掉，
  晚建工具链 = 晚发现 = 晚修。
- **Tauri 的命令签名表（sync vs async）该在项目开头立规矩**，而不是踩一次坑改一处。
- 单测对「编辑器」这类强 DOM 组件覆盖有限，**jsdom 测不到光标、滚动、合成层**；
  对这类模块，几个精心设计的真机用例价值超过几十个组件测试。
- `--compare 左 右` 这类命令行入口成本极低（几十行 Rust），却是自动化测试的
  最佳抓手 —— **给每个复杂功能留一条绕过 UI 的直开通道**，测试会感谢你。

## 七、多语言（i18n）：一次做九种语言的七个坑

**1. 键用「简体中文原文」，不用 `menu.save`。**
gettext 那套做法的好处是永远不会出现「键叫 save、值写着删除」的漂移，翻词条时
直接在代码里看得懂上下文；代价是原文改动要同步词条表。所以必须有自动化兜底：
`test/run-i18n.mjs` 会把「源码用了但表里没有」的键全部列出来，改文案忘同步会红。

**2. 顶层常量会把文案定死。**
`const MODE_META = { ... label: tt('预览') }` 在模块加载那一刻就求值了，切语言后
工具栏还是旧语言。凡是带 `tt()` 的顶层常量都要改成函数（`const modeMeta = () => ({...})`），
调用点补 `()`。这一轮改了 6 个：modeMeta / newTypes / menuTree / fileFilters / list /
blockKinds / blockInserts。

**3. 取词函数不能叫 `t`。**
`app.js` 里 `t` 是「当前标签」，几百处 `t.path`、`closeTab(t.id)`。叫 `t` 会被局部变量
遮住，而且 `t('关闭')` 读起来像「把标签对象当函数调用」。用 `tt`。

**4. `data-i18n` 只能挂在「文字由静态 HTML 决定」的节点上。**
对话框标题（`#dlgTitle`）、草稿状态（`#stDraft`）、文件夹路径、合并向导里的文件名、
预览标题 —— 这些是 JS 运行时写的，挂上 `data-i18n` 后 `applyDom()` 会在切语言那一刻
把它们改回静态词（现象：设置面板里的标题从「Einstellungen」变回「Hinweis」）。
判断标准很简单：**JS 里有没有对它赋值 textContent**，有就不挂。

**5. 换语言时菜单要 `update()`，不要重建。**
`createAppMenu()` 会往 `document` 上挂「点外面就关」的监听，重建等于叠一层，
多点几次菜单开始自己闪。appmenu.js 因此加了 `update(next)`，只换顶级标签文字。

**6. 繁体不手写，走 OpenCC `s2twp`。**
`文件→檔案`、`设置→設定`、`保存→儲存`、`字符→字元` 这些是短语级转换，手写五百条
必然前后不一致。源表只维护 7 列（en/ja/ko/fr/de/es/pt），繁体由
`tools/build-i18n-dict.py` 生成 —— 产物 `src/js/i18n-dict.js` 是只读的，
改词条请改 `i18n-dict-src.js` 再跑脚本。

**7. 后端的错误文案不带语言。**
Rust 侧 65 条错误信息是中文，后端不认识界面语言。真正干净的做法是返回错误码，
但那要改遍所有命令和调用点。折中做法是在 `backend.js` 的统一出口过一道
`ttBackend()`：整条命中词条就整条翻；「前缀：系统细节」只翻前缀 —— 细节那半是
Windows 自己给的（本来就跟随系统语言），翻了反而错。

**顺带一条工程纪律**：这一轮的 368 处自动包装是脚本做的（`tools/i18n-wrap.py`，
状态机跳过注释/模板字面量/对象键），但**模板字面量里的 HTML 必须手工拆**——
脚本按行匹配会把 `<button title="关闭">` 的属性也包进 `tt()`，直接炸 DOM。
自动化的边界要认得清：机械替换交给脚本，判断结构交给人。

## 八、后端错误码：把「翻译句子」改成「翻译语义」

i18n 第一版让 Rust 回中文句子、前端用 `ttBackend()` 拿字符串匹配翻译。这条路有
两个绕不过去的毛病，所以重构掉了：

1. **字符串匹配天然脆弱**。后端补个标点、改个措辞，前端整条失配，静默退回中文，
   用户什么都不说你就发现不了。
2. **带变量的句子永远匹配不上**。`「a.md」已经存在` 里的 `a.md` 是运行时才知道的，
   想匹配就得连变量一起匹配，等于没匹配。

正确分工是：**后端说发生了什么（语义），前端说怎么说（语言）**。

- Rust 侧（`error.rs`）：命令一律回 `Result<T, AppError>`，`AppError = { code, vars, detail }`。
  `code` 是稳定错误码（`io.read` / `entry.exists` / `name.path_sep`），`vars` 是模板参数，
  `detail` 是 `std::io` / Win32 的原始报错文本 —— 那段本来就是系统按自己的语言给的，
  不归我们翻，原样透传。
- 前端侧（`errors.js`）：`ERR_TEXT` 表把错误码映到词条键（键里带 `{detail}` `{name}`
  占位符），`localizeError()` 拼出完整句子；`backend.js` 的 `invoke` 出口统一过一道，
  调用方 catch 到的一定是带人话 `message` 的 `Error`。

三个坑：

- **冒号别拼接**。`前缀 + '：' + 细节` 这种拼法每种语言都是错的：中文全角、
  日文全角、法语的冒号**前面**还要空格。把整个句子（含冒号）做成词条键，
  译文里各语言自己带自己的冒号样式。
- **防二次翻译**。`localizeError` 出来的 `Error` 带 `message`，判据
  `isBackend = 有 code 且没有 message` 让它天然不会被再翻一遍（再翻会把 detail 弄丢）。
- **没收录的码要露出来**。宁可让用户看到 `[io.foo] boom`，也不要静默吞掉 ——
  至少能顺着码找到是哪条命令。`test/run-i18n.mjs` 里有一条双向对账：
  ① `ERR_TEXT` 的每个模板必须都在词条表里；② **Rust 源码里出现的每个
  `AppError::xxx("code")` 前端都必须有模板** —— 后端加错误码忘了配文案会直接红。

端到端验证方法（真机）：CDP 里 `import('/js/backend.js')` 然后故意触发四类失败
（读不存在的文件 / 读二进制 / 名字带路径分隔符 / 同名条目），检查 message
的 `code`、参数填充和 detail 透传；再 `setLang('en')` 跑一遍确认句子换语言、
detail 不变。

---

**7. 退化分支最危险的不是慢，而是"看起来正常"。**
`diff.js` 里有一条规模保护：`n*m > 4M` 时不再跑 LCS，改成"这行在对方文件里
存不存在"。它还给不匹配的行编了个 `b = -1` 冒充"相同"。后果是：两个 2000 行
的文件一比较，右栏**整页空白**，所有新增堆在文末 —— 界面上不报错、不转圈，
就是安静地给出错误答案。这类问题极难被用户描述清楚（"对比好像没生效"），
也极难被测试发现（没有断言过 `same` 行的行号有效性）。

三条规则：
- 退化路径的输出必须**和正常路径同一语义**。算不动就说"这段整段替换"，
  不要伪造"相同"。
- 退化路径要有**自己的断言**。现在 `run-units` 里有十条守它：行号在范围内、
  没有 `undefined` 文本、修改成对、无关文件不出现 `same`。
- 阈值附近的规模要**主动测**。4M 单元格对应约 2000×2000 行 —— 这不是极端
  用例，是"两份会议纪要"就会踩到的日常规模。

改进后的做法：段小就精确 LCS；段大到放不下 DP 表，就先找"两侧都只出现一次
的行"当锚点，用最长递增子序列保证顺序一致，再逐段递归。2000 行级文件 11ms，
3000×3000 全无关文件 12ms，都不会退回假结果。

**8. "部分成功"比"整体失败"危险得多。**
对比窗口打开一对文件时，如果左侧文件因为超限没读进来，而右侧读成功了，
旧实现会**保留左侧上一轮的内容**。界面上一切正常：有行号、有差异、有统计，
只是左栏是新文件的"前世"。用户没有任何线索知道这个结论是拿两个不相干的
文件比出来的。

规则：**一次操作要么完整生效，要么把受影响的输入清空**。不能只更新成功的
那一半。失败的一侧要显式回到「未选择」，并用一条常驻提示说明原因——toast
会消失，消失之后用户只会记得"它比较过了"。

同理，状态跨操作残留也要防：对比窗口是复用的，差异清单的排序/筛选会留在
上一次的状态里。产品上这是合理的（用户偏好），但任何断言都得先归零，否则
"点了位置列顺序没变"可能只是因为它本来就在按位置降序。

**9. 定位控件要和被定位的内容共用一套坐标。**
预览条原先按自身高度映射行位置，可它和正文区顶上都还有一条 26px 的栏头——
底部 26px 的行永远画不到，点击也差一截。短文档更糟：内容只有 100px 高，
映射却按 800px 的容器算，视口框比容器本身还高。

改法是把几何收进一个 `rulerGeom()`：轨道起点取滚动区的 `getBoundingClientRect().top`，
高度取 `min(可视高度, 内容高度)`，绘制、点击、悬停提示全用它。预览条 DOM 的高度
也跟着设成内容高度，短文档时它就是一小截——**控件本身的尺寸也要服从内容**，
不是把容器拉满再往里画。

性能上还有一个反例值得记：`drawRuler()` 原本每帧扫一遍所有行去拼差异段，
5 万行时光这一项就吃掉十几毫秒。改成用 `recompute()` 已经折好的差异块列表后，
每帧降到 3.6ms。**滚动路径里不要出现 O(总行数) 的循环**，哪怕它看起来只是
"扫一遍数组"。

**10. 测试需要的能力，先找平台开关，别改产品配置。**

真机探针要 CDP 端口，一直是「临时改 `tauri.conf.json` 的 `additionalBrowserArgs`
和 `lib.rs::spawn_compare_window` 两处 → 全量重编 → 跑 → 撤掉再重编」。
前端是编译期内嵌的，所以一轮探针两次 `cargo build`，50~100s 一次，还外带
「忘了撤销就把调试端口提交了」的风险。

其实 WebView2 认 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS`，而且是**进程级**的：
主窗口和随后打开的对比窗口都会带上。于是改成启动时注入，零改配置、零重编。
一般化的教训是——**为了测试去改产品代码，通常说明还没找对平台的运行时可调项**。
退而求其次的"临时改 + 事后撤销"，除了慢，还会留下"忘了撤"这一类必踩的坑。

同一处还踩了两个细节，都写进了 `test/lib/appctl.mjs`：

- **端口通 ≠ 应用可用**。`/json/version` 一通就去断言，只会拿到
  `window.__snp` 未定义的报错（WebView2 起来了，前端脚本还没跑）。就绪判据得是
  `document.readyState === 'complete' && !!window.__snp`。
- **收尾要用 `taskkill /T`**。`Stop-Process` 只杀主进程，`msedgewebview2`
  渲染进程会变成孤儿挂着吃内存（实测残留 6 个、约 400MB），而且它们的父 PID 会被
  系统回收给别的进程，事后看像"别人的进程"，很难判断该不该清。
