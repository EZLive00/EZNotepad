# 跨平台移植（macOS / Linux）

> 用途：把现在这个 Windows 版本移植到 macOS 和 Linux 时，**照着这份清单逐条改**。
> 每条都写了「现在怎么做的、在哪一行、换平台会怎样、怎么改」，可以直接当工单用。
>
> 配套：《架构设计.md》说明结构，《构建说明.md》说明环境与打包，《开发经验.md》收集踩坑结论。
> **本文所有结论都以当前代码为准（v1.0.1，2026-11-02）**；标记【待实测】的条目是
> 从 API 文档/源码推断、尚未在目标机器上跑过，移植时必须先验一遍再决定改法。

---

## 0. 结论先说

**移植面比想象的小。** 业务逻辑（`src/js/` 约 1.4 万行）与平台无关，一行都不用改；
真正要动的东西集中在四处：

1. **打包配置**（`tauri.conf.json` 里写死了 Windows 目标）；
2. **Rust 的 5 处系统调用**（圆角、工作区矩形、回收站、窗口铺满、浏览器参数）；
3. **macOS 独有的两个入口**（Finder 双击打开文件、系统菜单）；
4. **测试工具链的另一半**（真机套件是 Windows 专用 PowerShell）。

按影响分级：

| 级别 | 含义 | 条目数 |
|---|---|---|
| **A 阻断** | 不改就连构建/启动都过不去 | 4 |
| **B 数据安全** | 能跑，但会丢用户数据或写坏文件 | 2 |
| **C 功能残缺** | 能跑，但某个功能不可用或明显不对 | 6 |
| **D 体验打磨** | 能用，但不像这个平台上的原生软件 | 6 |

工作量粗估（一个人、有目标机器、不含签名证书申请）：

| 平台 | 代码与配置 | 首次真机联调 | 主要不确定项 |
|---|---|---|---|
| macOS | 2～3 天 | 1～2 天 | 打印（WKWebView 不支持 `window.print`）、无边框 + 交通灯的观感 |
| Linux | 1.5～2 天 | 1～2 天 | 发行版 WebKitGTK 版本、无边框窗口拖边缩放、输入法 |

真正的风险不在「改多少代码」，而在**三个平台的 WebView 内核不同**（WebView2 / WKWebView /
WebKitGTK）：同一段 DOM 代码在三者上的光标、滚动、字体、选中行为会有差异。
所以下面的里程碑**每一档都要求先在目标机器上跑通再往下走**，不要一次改完再统一联调。

## 2. A 级：不改就跑不起来

### A1 打包目标写死 `nsis`

`src-tauri/tauri.conf.json:38` 是 `"targets": ["nsis"]`。NSIS 是 Windows 专属打包器，
在 macOS / Linux 上执行 `tauri build` 会直接报「target not supported」。

**改法**（二选一，推荐后者）：

```jsonc
// 方案一：按平台列全，Tauri 会挑当前平台能用的那些
"targets": ["nsis", "dmg", "app", "deb", "appimage"]
```

```jsonc
// 方案二：交给各平台的 CI 显式指定（推荐，能按需只出某一种）
"targets": "all"
// CI 里：pnpm tauri build --bundles dmg
//        pnpm tauri build --bundles deb,appimage
```

同时把 `bundle.windows.nsis` 这些 Windows 专属配置保留（其它平台会忽略），
再补两块：

```jsonc
"macOS": {
  "minimumSystemVersion": "10.15",
  "entitlements": null,          // 不用 JIT/摄像头时保持 null
  "signingIdentity": null        // CI 里用环境变量注入，别提交到仓库
},
"linux": {
  "deb": {
    "depends": ["libwebkit2gtk-4.1-0", "libgtk-3-0"]   // 现在这个数组是空的
  }
}
```

> `depends` 现在是空数组。空着也能装上，但装完可能起不来（缺 webkit2gtk），
> 用户侧报的 bug 会长这样：「双击没反应」。

### A2 系统依赖

| 平台 | 需要 | 备注 |
|---|---|---|
| macOS | Xcode Command Line Tools（`xcode-select --install`） | 编译 Rust 与 bundler 都要 |
| Linux | `libwebkit2gtk-4.1-dev`、`libgtk-3-dev`、`libayatana-appindicator3-dev`、`librsvg2-dev`、`build-essential`、`pkg-config` | Ubuntu 22.04 / Debian 12 及以上（webkit2gtk-4.1 起） |
| Linux（运行时） | 中文字体：`fonts-noto-cjk` | 否则中文全是豆腐块；`--font-ui` 的最后一级是 `sans-serif` |

WebKitGTK 4.0 与 4.1 是两个 ABI，Tauri 2 只认 **4.1**。Ubuntu 20.04 那种只有 4.0 的系统
跑不起来，需要在文档里写明最低发行版。

### A3 macOS 双击打开文件不通（最容易漏的一条）

现在打开文件的入口是命令行的 `argv`：

```rust
// lib.rs:277
fn initial_files() -> Vec<String> { file_args(&std::env::args().collect::<Vec<_>>()) }
```

Windows 和 Linux 都靠「把路径塞进命令行」打开文件，macOS **不是**：

- 从 Finder 双击 → 系统发 **Apple Event**，进程 `argv` 里**没有**文件路径；
- 应用已经在跑时 → 事件发给**已有进程**，根本不会启动第二个进程，
  所以 `tauri-plugin-single-instance` 的回调也不会被调用。

Tauri 把这件事包装成了 `RunEvent::Opened { urls }`，而且**只有 macOS/iOS/Android 才编译
这个变体**（`tauri-2.12.4/src/app.rs:257`）。现在的 `run()` 是空回调，等于把这个事件丢了。

**改法**：

```rust
// lib.rs::run() 末尾
app.run(|app_handle, event| {
    #[cfg(target_os = "macos")]
    if let tauri::RunEvent::Opened { urls } = event {
        let files: Vec<String> = urls.iter()
            .filter_map(|u| u.to_file_path().ok())
            .map(|p| p.to_string_lossy().to_string())
            .collect();
        if files.is_empty() { return; }
        // 与 Windows 的「第二次启动」走同一条路：先亮窗口，再把文件推进去
        if let Some(w) = app_handle.get_webview_window("main") {
            let _ = w.unminimize();
            let _ = w.show();
            let _ = w.set_focus();
        }
        let _ = app_handle.emit("open-files", files);
    }
});
```

注意三点：

1. 事件可能带**目录**（不是文件），过滤掉或在 `emit` 前用 `Path::is_file()` 判一下。
2. 首次启动（冷启动）时 `RunEvent::Opened` 可能**早于**前端监听器就绪 —— 现在的
   `open-files` 事件只在窗口已经创建后发。稳妥做法是把它也存进 Rust 状态
   （照 `CompareRequest` 的做法：`Mutex<Option<Vec<String>>>` + `take_opened_files` 命令），
   前端初始化时先 take 一次，再开始监听。**Windows 的 `initial_files()` 已经是这个模式，
   mac 上不复用就会丢第一批文件。**
3. `--compare 左 右` 在 mac 上要写成 `open -a EZNotepad --args --compare a.md b.md`，
   `argv` 里能拿到，不受影响。

### A4 通用二进制

`package.json` 里已经有 `build:mac: tauri build --target universal-apple-darwin`，
但通用包要求**两个 target 都装好**：

```bash
rustup target add aarch64-apple-darwin x86_64-apple-darwin
```

只想出一个架构时（绝大多数用户是 Apple Silicon）可以只跑
`--target aarch64-apple-darwin`，体积减半、构建快一倍。

## 3. B 级：会丢数据

### B1 删除文件：非 Windows 是永久删除

```rust
// lib.rs:204  Windows：进回收站
#[cfg(target_os = "windows")]
fn delete_file_impl(p: &Path) -> Result<(), AppError> {
    /* SHFileOperationW + FOF_ALLOWUNDO */
}

// lib.rs:229  其它平台：直接抹掉
#[cfg(not(target_os = "windows"))]
fn delete_file_impl(p: &Path) -> Result<(), AppError> {
    fs::remove_file(p).map_err(|e| AppError::detail("io.delete", e))
}
```

界面上这个动作叫「删除（进回收站）」，用户以为能捞回来。**这一条不改，移植版第一天
就会被投诉。**

**改法**：换成跨平台的 `trash` crate（Windows 走 `SHFileOperation`/回收站 API，
macOS 走 `NSFileManager.trashItemAtURL`，Linux 走 freedesktop 的 trash 规范，
涉及 `~/.local/share/Trash`）。

```toml
# Cargo.toml
trash = "5"
```

```rust
#[tauri::command]
fn delete_entry(path: String) -> Result<(), AppError> {
    let p = PathBuf::from(&path);
    if !p.exists() { return Err(AppError::new("entry.missing")); }
    // 目录只删空的：递归删除风险太大
    if p.is_dir() {
        return fs::remove_dir(&p).map_err(|e| AppError::detail("dir.not_empty", e));
    }
    trash::delete(&p).map_err(|_| AppError::new("recycle.failed"))
}
```

删掉整段 `#[cfg(windows)]` 的 `delete_file_impl` 与 `windows-sys` 的
`Win32_UI_Shell` feature。错误码 `recycle.failed` 现在带 `rc` 变量，改完后是固定文案，
要同步改 `errors.js` 的模板（`run-i18n.mjs` 会替你把漏改的地方报出来）。

> Linux 的 trash 规范要求文件在同一个挂载点才能「进回收站」，跨盘的移动会变成 copy+delete。
> 这一点不用特别处理，但要知道大文件删除会慢。

### B2 编码回退一律当 GB18030

```rust
// lib.rs:35  UTF-8 严格校验失败 → 当 GBK 解
let (s, _, _) = encoding_rs::GB18030.decode(bytes);
```

Windows 中文环境下这个假设是对的（系统 ANSI 就是 GBK 系）。到 macOS / Linux 上，
一个非法 UTF-8 的文件更可能是 Latin-1、Shift-JIS、或者二进制误判，用 GB18030 硬解
会得到「看起来像中文的乱码」，用户会误存成 UTF-8 —— **原文件就毁了**。

**改法**：用 `encoding_rs` 自带的 `chardetng`（同作者，同一仓库）做候选打分，
并给候选集按平台排序：

```toml
encoding_rs = "0.8"
chardetng = "0.1"
```

```rust
// 候选集：Windows 偏好 GB18030，其它平台偏好 windows-1252 / Shift_JIS
let mut det = chardetng::EncodingDetector::new();
det.feed(bytes, true);
let guess = det.guess(None, true);
```

另一条路更省事：**只把 GB18030 当成「可选项」**，非 Windows 上回退到 `windows-1252`
（Latin-1 超集，永不失败、不会解出假中文），并在状态栏明确显示当前编码，
让用户自己用「以…编码重新打开」纠正。项目已经有编码显示与重载能力，成本更低。

## 4. C 级：功能残缺

### C1 打印 / 导出 PDF（最不确定的一项）

```js
// src/js/pdf.js:20
const win = window.open('', '_blank', 'width=900,height=1000');
win.document.write(html);
win.print();
```

- **Windows（WebView2）**：可用，走系统打印对话框，「另存为 PDF」是系统提供的。
- **macOS（WKWebView）**：`window.print()` **没有实现**【待实测】。WKWebView 的打印是
  `NSPrintOperation` + `WKWebView.printOperation`，属于原生 API，JS 调不到。
  另外 `window.open` 在 WKWebView 里默认返回 `null`（Tauri 需要显式允许新窗口）。
- **Linux（WebKitGTK）**：`window.print()` 有实现（弹 GTK 打印对话框），但样式与分页
  表现与 Chromium 不同【待实测】。

**改法（按代价从低到高）**：

| 方案 | 做法 | 代价 |
|---|---|---|
| ① 保底 | 「导出 PDF」在 mac 上改成「导出 HTML」+ `opener.openPath()` 用默认浏览器打开，让用户自己 ⌘P | 最小，体验可接受 |
| ② 原生打印 | Rust 侧 `#[cfg(target_os = "macos")]` 用 objc2 调 `NSPrintOperation`，把当前页打出来 | 中，要写 ObjC 桥 |
| ③ 自带渲染 | 引入 PDF 生成库（如 `printpdf` / headless Chromium） | 大，违背「5MB」原则 |

建议：**先做 ①**，把 `pdf.js` 抽成 `printTo(kind)` 接口，三个平台各自实现；
等真的有人抱怨再考虑 ②。

### C2 拖文件进窗口（已按原生通道实现）

`tauri.conf.json` 的 `"dragDropEnabled"` 决定走哪条通道，两个开关是连在一起的：

- **`true`（当前值，Tauri 默认）**：`tauri-runtime` 置 `drag_drop_handler_enabled = true` →
  `tauri-runtime-wry` 注册处理器（`tauri-runtime-wry-2.12.2/src/lib.rs:4783`），同时 wry 把
  WebView2 的 `SetAllowExternalDrop(false)`（`wry-0.57.0/src/webview2/mod.rs:155`）关掉外部拖放。
  于是文件拖放**全部**走 `onDragDropEvent`，拿到的是**真实磁盘路径**。
- **`false`**：处理器不注册 → `onDragDropEvent` 永不触发；但 WebView2 保留默认外部拖放，
  文件落到页面上是一条普通 HTML5 `drop` 事件，`dataTransfer.files` **有字节、没有路径**。

早先为了「拖图片进来插到文档里」选了 `false`，代价是拖任何文档都只能提示用户走菜单。
现在按原生通道实现（`app.js` 的 `setupDrop`）：

- 图片 → 复制进 `assets/`，**保留原文件名**（`copy_image_to_assets`）；
- 其它文件 → 直接开标签，多选就开多个；
- `enter` / `leave` 事件驱动 `.drop-hint` 浮层——这条通道下页面收不到 `dragover`，
  不自绘提示的话拖到窗口上完全没反馈；
- 无文件的内部拖拽（标签换位）走 HTML5 DnD，与 `AllowExternalDrop` 无关，**不受影响**。

**已知取舍**：`SetAllowExternalDrop(false)` 是全局的，从别的程序往编辑区拖一段选中文字也
会一起失效（只能 Ctrl+C/V）。换来的是「拖 md 直接打开」和「图片原名落盘」，值。

移植时：mac / Linux 保持 `dragDropEnabled: true` 即可，三平台走同一条通路；`onDragDropEvent`
在 Linux 上由 GTK DND 提供，拖入过程是否给全路径【待实测】。

### C3 无边框窗口

`decorations: false` + 自绘标题栏 + 自绘 －□✕，是 Windows 的做法。换平台后：

| 平台 | 问题 | 建议 |
|---|---|---|
| macOS | 交通灯（红黄绿）在左上角，是**系统画**的；自绘按钮在右上角，两边各一套 | `decorations: true` + `titleBarStyle: "Overlay"` + `hiddenTitle: true`，让系统交通灯浮在自绘标题栏上；前端按平台隐藏 `.win-ctrl`，标题栏左侧留 ~78px 给交通灯 |
| Linux | 无边框窗口在多数 WM 下**不能拖边缩放** | 加 8px 边角热区，`mousedown` 时调 `getCurrentWindow().startResizeDragging('East'...)`；权限补 `core:window:allow-start-resize-dragging` |

mac 的配置（Tauri 2 支持，字段名已核对）：

```jsonc
{
  "decorations": true,
  "titleBarStyle": "Overlay",     // 内容铺到标题栏下面
  "hiddenTitle": true,            // 不画系统标题文字
  "trafficLightPosition": { "x": 12, "y": 12 }
}
```

前端配合：`body[data-os="mac"] .win-ctrl { display: none; }`，并给 `.titlebar`
加左侧内边距。`data-os` 可以由 `navigator.userAgent` 判，也可以让 Rust 在启动时
通过 `window.__os` 注入（更可靠，一次性）。

> 注意：`titleBarStyle: Overlay` **要求 `decorations: true`**。也就是说 mac 上
> 不能既 `decorations:false` 又要系统交通灯 —— 只能二选一。选 Overlay 的代价是
> 窗口圆角与阴影交回系统（其实是好事）。

### C4 macOS 会出现两套菜单

Tauri 2 在 `menu` 为空且 `enable_macos_default_menu` 为 true（默认）时，会给 macOS
自动建一套系统菜单（App / File / Edit / View / Window / Help）。而本应用又自绘了
一份菜单栏画在窗口里 —— mac 用户会同时看到屏幕顶上和窗口里两套菜单。

两种收敛方式：

- **推荐**：mac 上改用系统菜单承接全部命令，窗口里那行只留「品牌 + 窗口标题 + 交通灯」
  （即 `body[data-os="mac"] .menubar { display: none }`，并用 Tauri 的 `Menu` API
  建一套带 `accelerator` 的原生菜单）；这样 ⌘ 快捷键也能显示在系统菜单里。
- **省事**：`.enable_macos_default_menu(false)`，只保留窗口内自绘菜单。代价是
  ⌘Q / ⌘H / ⌘M 没有菜单归属（仍然可用，但不符合 macOS 习惯）。

Linux 没有系统菜单栏，现状（自绘）就是对的。

### C5 快捷键显示是 `Ctrl`，行为却是 `⌘`

好消息：**匹配逻辑已经兼容**。`comboOf()` 把 `ctrlKey || metaKey` 折成 `mod`，
`kbdToCombo()` 也把 `ctrl / meta / cmd` 都映射成 `mod`。所以 macOS 上按 ⌘S 能存盘。

坏消息：**显示文案全是硬编码 `Ctrl`**，约 130 处：

| 位置 | 数量 | 例子 |
|---|---|---|
| `src/js/app.js` | 69 | `{ id: 'save', kbd: 'Ctrl+S' }`、标签右键菜单 `shortcut: 'Ctrl+W'` |
| `src/js/welcome.js` | 32 | 欢迎文档里的快捷键说明 |
| `src/js/i18n-dict-src.js` | 15 | 词条里的 `Ctrl+Shift+8` 这类文案 |
| `src/js/wysiwyg.js` / `compare.js` / `history.js` / `math.js` | 6 | 提示文案 |
| `src/index.html` / `src/compare.html` | 8 | `title="新建标签 (Ctrl+T)"` |

**改法（一次到位，别逐处 if）**：

1. 数据层统一写 `mod+shift+s` 这种「平台无关」形式（`kbdToCombo` 已经能吃 `Ctrl+…`，
   但反过来更好：**存 `mod+`，显示时渲染**）。
2. 增加一个渲染函数，只有它认识平台：

```js
const IS_MAC = navigator.userAgent.includes('Mac');
export const kbdLabel = (combo) => String(combo).split('+').map((p) => {
  if (p === 'mod')  return IS_MAC ? '⌘' : 'Ctrl';
  if (p === 'alt')  return IS_MAC ? '⌥' : 'Alt';
  if (p === 'shift') return IS_MAC ? '⇧' : 'Shift';
  return p.length === 1 ? p.toUpperCase() : p;
}).join(IS_MAC ? '' : '+');   // mac 上不写加号：⌘S
```

3. `comboToKbd()`（`app.js:3513`）现在是 `p === 'mod' → 'Ctrl'`，改成走 `kbdLabel`。
4. i18n 词条里的 `Ctrl+…` 要改成 `{kbd}` 占位符 + 运行时填 —— 否则九种语言各写一遍
   平台相关文案。这一项改动面不小，可以**分两步**：先让代码层（菜单、提示）正确，
   欢迎文档与词条留在后面。

### C6 POSIX 绝对路径被当成相对路径

```js
// src/js/markdown.js:30
if (/^[a-z]:[\\/]/i.test(src) || src.startsWith('//')) return src;   // 已经是绝对路径
const abs = docDir.replace(/[\\/]+$/, '') + '/' + src.replace(/^\.\//, '');
```

`/Users/me/notes/a.png` 既不匹配盘符也不以 `//` 开头 → 被拼成
`/Users/me/notes//Users/me/notes/a.png`，图片显示不出来。

**改法**：

```js
const isAbs = (s) => /^[a-z]:[\\/]/i.test(s) || s.startsWith('/') || s.startsWith('\\\\') || s.startsWith('//');
```

顺带检查这两处的同类写法（都已经是 `[\\/]` 兼容的，无需改）：
`app.js:1867`、`backend.js:24`、`filetree.js:14`、`diffpanel.js:131`、`exporthtml.js:28`。

## 6. 移植后必须重测的指标

《架构设计.md》§11 那套数字**不能直接沿用**，三个内核的性能特征差得多：

| 指标 | 为什么必须在目标平台重测 |
|---|---|
| 单次击键延迟（600 段） | WebKitGTK 的 DOM 操作比 WebView2 慢，可能要重新调整视口窗口大小（`MAX_WIN = 600`） |
| 10MB 文档视口渲染 | WKWebView 的滚动事件节流策略不同，`_windowAt` 的补偿量可能要从头校一遍 |
| 常驻内存 | 三个 WebView 的基线差 50～200MB |
| 冷启动 | mac 上首次启动要过 Gatekeeper 校验，明显更慢（只在首次） |
| 字体度量 | 同一份 CSS，`PingFang SC` 与 `Noto Sans CJK` 的行高不同 → **正文区高度、大纲定位的 ±1 行误差都要重新验** |

对应地，`test/` 里的截图基线需要按平台分开存（现在只有一套 Windows 基线）。

## 7. 测试工具链：一半能直接跑，一半要重写

项目有两套测试，可移植性完全不同：

| 套件 | 组成 | 可移植性 | 移植时要做的事 |
|---|---|---|---|
| **离线行为套件** | `test/run.mjs`、`run-units`、`run-editor`、`run-menu`、`run-i18n`、`run-filetree` | **高**：起静态服务 + headless Chrome + CDP，纯 Node | 见下面三处小改 |
| **真机套件** | `test/real/*.ps1`（UIA + SendInput + PrintWindow + BitBlt）、`gen-*.mjs` | **零**：Windows API 专用 | mac 用 AppleScript/`cliclick`/`screencapture`；Linux 用 `xdotool`/`import`。或整体改用 `@playwright/test` |

离线套件要改的三处：

1. `test/harness.mjs:28` 的 `CHROME_CANDIDATES` **已经包含** mac 与 linux 路径，不用改；
   但 `killChromeWhere()`（`harness.mjs:82`）在非 Windows 上直接 `return` ——
   上一轮残留的 Chrome 会占着端口，报「端口已被占用」。需要补 `pkill -f` 分支。
2. Linux 上以 root 跑 headless Chrome 需要 `--no-sandbox`（容器 CI 常见）。
3. `test/real/TEST-PLAN.md` 与 `RESULTS.md` 里所有坐标、窗口尺寸（那些 `-7, 0` 的结论）
   都是 Windows 实测值，**在 mac/Linux 上一条都不成立**，必须重建。

建议把真机套件重构成两层，只重写「输入层」：

```
断言层：CDP（Runtime.evaluate 读状态 + Page.captureScreenshot）  ← 三平台通用，已经写过
输入层：合成点击 / 按键 / 截图                                    ← 平台化（每平台 100 行左右）
```

这也是原项目里最值钱的经验之一：**给每个复杂功能留一条绕过 UI 的直开通道**
（`--compare 左 右` 就是），移植时它能让断言层完全不依赖窗口。

## 8. CI 矩阵

现在 `.github/workflows/release.yml` 只有一个 `windows` job。扩成三个时注意：

```yaml
jobs:
  windows:
    runs-on: windows-latest
    # 现状不变：nsis + portable zip
  macos:
    runs-on: macos-latest        # arm64 机器
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: pnpm }
      - uses: dtolnay/rust-toolchain@stable
        with: { targets: aarch64-apple-darwin,x86_64-apple-darwin }
      - run: pnpm install --frozen-lockfile
      - run: pnpm tauri build --target universal-apple-darwin
      # 签名 + 公证（需要 5 个 secrets：证书 p12、密码、App Store Connect key/id/issuer）
  linux:
    runs-on: ubuntu-22.04        # 必须是 22.04：webkit2gtk-4.1
    steps:
      - run: |
          sudo apt-get update
          sudo apt-get install -y libwebkit2gtk-4.1-dev libgtk-3-dev \
            libayatana-appindicator3-dev librsvg2-dev patchelf
      # 其余同 windows
```

三点经验（都是本仓库已经踩过的）：

- **发版仍以 tag 为唯一触发**：`git tag -f -a vX.Y.Z && git push -f origin vX.Y.Z`，
  版本号只从 `tauri.conf.json` 读（现状已经这么做，三个 job 复用同一个「读取版本号」步骤）。
- **构建失败要能匿名读到错误行**：现有 workflow 用 `::error::` 注解把错误行吐出来，
  新 job 照抄这个模式（Actions 完整日志需要管理员令牌，注解不需要）。
- **产物要在三个 job 里都 `upload-artifact`**，Release 那一步单独一个 job 汇总，
  否则某个平台失败会连累其它平台已经构建好的产物。
