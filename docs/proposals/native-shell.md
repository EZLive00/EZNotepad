# 不用 WebView 实现 EZNotepad：可行性评估

> 状态：**提案，未采纳**。写于 2026-11-06，触发原因是「常驻内存超过 500 MB」。
> 这份文档只回答一个问题：**为了省内存而脱离 WebView，值与不值。**
> 里面的数字全部是本机实测，不是估算；凡是没有实测的地方都标了「估计」。

---

## 0. 结论先行

> **一句话答案：不用重写。**
> 500 MB 里最大的那 300 MB 是**屏幕像素的函数，不是代码的函数** —— 工作电脑实测，
> 换一台低分辨率显示器就从 300 MB 降到 **59 MB**，一行代码没改（§1.6）。
> 剩下 200 MB 是 WebView2 运行时地板，重写能省掉大部分，但代价是 1.6 万行和 6～18 个月。

1. **技术上完全可行，但那不是「换一层壳」，是重写这个程序。**
   这套程序 1.96 万行前端里，约 1.6 万行依赖浏览器白送的能力（排版、断行、光标与选区、
   IME、剪贴板 HTML、打印分页），或者依赖四个只在 JS 生态里存在的引擎
   （CodeMirror 6 / highlight.js / prettier / mermaid）。**能原样搬走的纯逻辑只有约 3000 行。**

2. **在开发机（1920×1200）上，500 MB 里约 380 MB 是 WebView2 的地板**，跟文档大小无关。
   空载（欢迎页，一个空白窗口）就是 409 MB 工作集，减去我们自己的 28 MB 就是地板。
   三个参数实验最多榨出 5%，`--disable-gpu` 甚至是负优化（543 → 641）。
   ⚠️ 这个地板**本身也含屏幕相关的部分**（GPU 那 95 MB），低分屏更低、高分屏更高 —— 见 §1.6。

3. **报障场景里那 300 MB 的 GPU 是 tile 纹理，不是泄漏**（§1.5）。它随「视口像素面积」
   变化，与 DOM 大小无关，也不会因为改前端写法而下降。**工作电脑已实测坐实**：
   换到低分辨率显示器后 300 → **59 MB**（§1.6）。唯一能动的旋钮是
   `--force-gpu-mem-available-mb` —— 但它**不是硬上限**，只有压到实际用量的 1/7 左右才触发，
   且收益只有 GPU commit 的 −17～27 MB（§1.5 实测）。

4. **多开标签不是元凶。** 45 个标签和 3 份大文档的内存几乎一样（562 vs 543），
   JS 堆始终在 12～18 MB。省内存去改标签管理，方向是错的。

5. **重写能到多少：60～150 MB**（估计，参照 Sublime Text / Qt / 自绘方案的实际量级），
   不是 16 MB —— 16 MB 是「空窗口」的地板，不是「带富文本排版和编辑的编辑器」的地板。
   **收益约 400～480 MB，代价 6～18 个月 + 丢掉 mermaid / 格式化 / 成熟编辑器内核。**
   而且换 Sciter 这类「仍然 GPU 合成」的引擎，**tile 成本省不掉多少**。

6. **建议：不重写。** ① 高分屏上若在意内存，试 `--force-gpu-mem-available-mb=32/16`
   （**注意 128/192 这种档位实测无效**，见 §1.5；本质是拿画质/帧率换内存，要自己看手感）；
   ② **应用侧其余优化已实测到底**（§1.7：低内存模式是假瘦身、低端模式只 −25 MB、对比窗口只占 47 MB），
   不要再去挖这 100 多 MB —— 不存在；③ **不做 B/C/D** —— 为了省一个「换台显示器就能省掉
   240 MB」的数字，去重写 1.6 万行、丢掉 mermaid 与成熟编辑器内核，不成立。§5 的 spike 保留，只在将来真有别的理由时才用。

## 1. 实测：内存到底花在哪

### 1.1 环境

| 项 | 值 |
|---|---|
| 机器 | AMD Ryzen 7 7840HS / Radeon 780M / 15.2 GB 物理内存（测量时已用 71%） |
| 版本 | 1.1.7 release 构建，`AdditionalBrowserArgs` 只带生产参数 |
| WebView2 配置目录 | 全新空目录（避免恢复历史 45 个标签干扰） |
| 测量口径 | `WorkingSet`（工作集）与 `WorkingSetPrivate`（专用工作集）分别记录 |
| 测量工具 | `tools/measure-memory.ps1`（按镜像名过滤，避免 PID 复用的系统进程混入） |

⚠️ **先分清两个数**：任务管理器「进程」页的「内存」列是**专用工作集**，
同一个应用的子进程会被折叠成一行求和；而把 7 个进程的工作集直接相加会得到接近翻倍的
数字（共享的 DLL、字体缓存、D3D 资源被重复计入）。两者都列在下表，别混着比。

### 1.2 五个状态

| 状态 | 进程数 | 工作集合计 | 专用工作集合计 |
|---|---|---|---|
| 原生 Win32 空窗口（对照，见 §1.4） | 1 | **15.9 MB** | **2.1 MB** |
| WebView2 空载（欢迎页，零文档） | 7 | **409 MB** | **142 MB** |
| 打开 3 份大文档（共约 500 KB） | 7 | **543 MB** | **259 MB** |
| 45 个标签（探针残留实例） | 7 | 562 MB | 263 MB |
| 3 份大文档 + `--disable-gpu` | 7 | 641 MB | 364 MB |

空载那行的 7 个进程里含 `EZNotepad.exe` 自己 28 MB，所以 **WebView2 部分是 381 MB**；
打开 3 份大文档后多出来的 134 MB 几乎全在 renderer（95.5 → 225.8）。

### 1.3 分解：543 MB 是怎么凑出来的

| 进程 | 工作集 | 它是谁 |
|---|---|---|
| renderer | 225.8 MB | 页面渲染（**JS 堆只有 12.7 MB**） |
| browser | 114.8 MB | Chromium 主进程（网络栈、IPC、合成器协调） |
| gpu-process | 94.8 MB | GPU 合成 —— **空白窗口也要 94.6 MB** |
| utility（NetworkService） | 36.4 MB | 网络服务 |
| EZNotepad.exe | 27.9 MB | 我们的 Rust/Tauri 壳 |
| utility（StorageService） | 22.7 MB | 存储服务（localStorage / IndexedDB） |
| crashpad-handler | 21.1 MB | WebView2 崩溃上报 |

**关键一行**：renderer 里 JS 堆 12.7 MB、DOM 节点 14344、布局对象 12908。
也就是说 **213 MB 花在「浏览器怎么把字排上去」上，不是花在我们的代码上。**
换任何前端写法都动不了这块 —— 它不是内存泄漏，是运行时本身。

### 1.4 对照：一个原生窗口有多轻

同一台机器上编译一个 30 行的 Win32 空窗口（`CreateWindowEx` + 默认消息循环）：

```
原生空窗口: WorkingSet 15.9 MB, 私有 2.1 MB, 4 线程
```

15.9 MB 里绝大部分是 `user32` / `gdi32` / `dwm` 的**共享**页，真正独占只有 2.1 MB。
这就是「不用 WebView」的上限诱惑：**409 → 16，看起来是 25 倍。**

但这个 16 MB 只能证明「窗口很轻」，不能证明「这个程序很轻」。真正吃掉内存的是
排版与编辑内核 —— 见 §3。

### 1.5 工作电脑上的「GPU 300 MB」：tile 纹理，不是泄漏

实际报障的场景：**空闲 240 MB，滚动时 GPU 进程 300 MB + 页面进程 100 MB + 其他几十 MB ≈ 500 MB。**

开发机（1920×1200 @100%）复现不出这个量级：同一份 190 KB 文档，
GPU 进程 90.4 MB，滚到 1/3、底部、再回中段，只在 92～108 MB 之间波动，**不累积**；
GPU 真实资源用量（`\GPU Process Memory(*)\Local Usage`）46～52 MB。

差异在**像素面积**。用 CDP 把渲染缩放改成 2 倍（窗口逻辑尺寸不变）后，
同一页面的 GPU 纹理 46.4 → **69.7 MB**（+50%）。据此推断工作电脑：
若 2560×1440 @150% 或 3840×2160 @200%，视口像素面积是开发机的 4～9 倍，
tile 纹理落在 200～400 MB —— 与观察到的 300 MB 吻合。

**四条结论：**

1. 这 300 MB 是 Chromium 为滚动**提前栅格化**的 tile，面积 ∝ 视口像素 × DPR² × 预栅格屏数。
2. 不是泄漏。滚动后不回落是因为 tile 缓存被保留，属设计行为，不是 bug。
3. 与 DOM 大小几乎无关：开发机上 renderer 反而从 349（刚打开）降到 245（滚动后），
   初始那 100 MB 是一次性的字体栅格化与样式计算。
4. 唯一能压的旋钮是 `--force-gpu-mem-available-mb=<N>`，但**它不是硬上限**。
   开发机把窗口拉到 1918×1160（2.22 Mpx）后实测：

   | 预算 | 纹理 Local | GPU commit | 滚动帧时间 |
   |---|---|---|---|
   | 不设 | 90.5 MB | 127 MB | 18.5 ms |
   | 64 MB | 90.5 MB | 135 MB | — |
   | 16 MB | **66.5 MB** | **110 MB** | 18.8 ms |

   64 MB 完全无效，16 MB 才生效 —— 阈值在「实际用量的 1/7 左右」。**它按比例降级，
   不是封顶**（钉 16 MB 后仍用 66 MB）。收益也只有 GPU commit 的 −17～27 MB：
   90 MB 里大头是纹理池、shader、D3D 缓冲这类固定开销，面积相关的部分只占一半。
   ⚠️ 开发机上滚动帧时间没有退化（18.5 → 18.8 ms），但那只代表 2.22 Mpx 的压力；
   4K 上降级更激进，**必须实测手感，不能只看数字**。

   同时证伪：`--max-tiles-for-interest-area=64` 在 WebView2 里被忽略，无效果。

### 1.6 决定性验证：只换显示器，300 → 59 MB

把窗口拖到一台低分辨率显示器上，**GPU 进程从 300 MB 降到 59 MB**（约 5 倍）。
同一台机器、同一个版本、同一份文档，**只有屏幕变了**。

这条证据的分量：它排除了「代码写重了」「内存泄漏」「WebView2 有 bug」三种解释，
把 300 MB 唯一地归因到**屏幕像素面积**。推论有三条：

1. 这 300 MB 不是「程序重」，是「屏幕大」。在低分屏上整机常驻回到 **260 MB 量级**，
   本来就在《架构设计》§11 的 250 MB 指标附近。
2. 高分屏上想同时要「低内存 + 不开画质降级」，**做不到** —— tile 是像素的函数，
   不改渲染策略就减不掉。想减只能压预算，而压预算就是拿画质/帧率换内存。
3. 因此「为省这 300 MB 重写整个程序」的性价比极低：**换一台低分屏就省了 240 MB，
   代价是零行代码；重写要 6～18 个月。**

**这一条为什么重要**：它证明 300 MB 与我们的代码无关，是一个**能被环境改变的量** ——
下一节的实测把这一点钉死。
而「用参数压下来」这条路没有想象中好走：§1.5 的预算实验只拿到 17～27 MB，§1.7 又否掉了
其余四种手段。**这块内存既不是代码造成的，也不是代码能救的。**

⚠️ 顺带修正一个直觉：**换 Sciter 也可能有 tile** —— 只要它用 GPU 合成，就同样要为屏幕面积付纹理钱，
只是没有 Chromium 这么激进（没有多进程、没有这么宽的预栅格）。**「换引擎」不等于「免掉合成成本」。**

### 1.7 应用侧还能压多少：四个实验，全部为负或接近零

决定「不重写」之后，把剩下的候选逐个实测。**结论是应用侧已经到边界。**

| 手段 | 实测 | 代价 | 采纳 |
|---|---|---|---|
| `SetMemoryUsageTargetLevel(Low)`（官方 API，ICoreWebView2_19） | 工作集 569.5 → **201.1 MB**，但 Commit 354.6 → **354.9 MB** | 见下 | ❌ 假收益 |
| `--enable-low-end-device-mode` | 543 → 517.7 MB（−4.6%） | 关闭一批视觉效果、降图像质量 | ❌ 不值得 |
| 对比窗口（多开一个） | +1 renderer，**+~90 MB 工作集 / +~47 MB commit** | 功能本身 | 保留 |
| 45 个标签 | 562 vs 543（≈ 0） | — | 无需处理 |

**低内存模式为什么是假的**：它把渲染进程的页扫出物理内存（browser 进程只剩 2 MB、
GPU 进程只剩 0.5 MB —— 这个数字本身就是信号），任务管理器上很好看，但 Commit 一 MB 没少。
文档是常驻编辑区一直要用的，一滚动就得 page fault 回来，**收益是负的**。这段实验代码已回退，
仓库里不留。判别方法记住一条：**看 Commit，不看工作集。**

**纹理面积关系的定量验证**（同一台机、同一份文档，只改窗口物理尺寸）：

| 窗口 | 像素面积 | GPU commit | 纹理 Local |
|---|---|---|---|
| 640×420 | 0.27 Mpx | 92.1 MB | 42.4 MB |
| 1280×820 | 1.05 Mpx | 94.6 MB | 47.9 MB |
| 1918×1160 | 2.22 Mpx | 137.1 MB | 92.6 MB |

面积相关的增量约 **28～38 MB / Mpx**。外推到 4K（8.29 Mpx）是 **230 MB 上下**，
与工作电脑实测的 300 MB 同量级 —— 这条曲线把「屏幕大」这件事从推测变成了可计算。

**顺带纠正一个曾经的猜测**：报障场景里那 240 MB 差额**不是对比窗口造成的**
（实测只占 47 MB commit）。它从头到尾就是屏幕面积。

## 2. 参数层能榨出多少（三个实验，全部实测）

| 实验 | 结果 | 判断 |
|---|---|---|
| `--disable-gpu` | 543 → **641**（GPU 进程 94.8 降到 51.7，renderer 却 225.8 涨到 376.1） | ⛔ **负优化**。软件合成把负担全推给 renderer，还慢 |
| `--enable-low-end-device-mode --disable-breakpad --disable-extensions --disable-background-networking` | 543 → **515**（省 5%） | ⚠️ 有效但有限，且低端模式会降图像质量与动画 |
| 限制 JS 堆（`--js-flags=--max-old-space-size`） | 无意义 | JS 堆本来只有 12.7 MB，不是瓶颈 |

**结论：WebView2 的固定成本约 380 MB**（空载 409 MB 减去我们自己的 28 MB：
browser 116 + GPU 95 + renderer 空页 95 + utility 62 + crashpad 13），
这是架构决定的，常规参数动不了。**想要「< 200 MB」只有换引擎一条路。**

**唯一例外**是 tile 纹理预算（§1.5）：`--force-gpu-mem-available-mb` 能在大屏上削掉一部分 GPU 占用，
且不需要改一行代码。但它不是硬上限 —— 实测要压到实际用量的 1/7 才触发，开发机上收益是
GPU commit 的 −17～27 MB，4K 上的收益按面积比例更大，但**代价是 tile 降级**。
它是唯一一个真正动到分配策略的开关，也是唯一一个需要在目标机器上亲自试的开关。

## 3. 「不用 WebView」到底要重做什么

拿《实现规格》§1.2 的十个必写组件逐块算账。判据是：
**这块能不能原样搬走？搬不走的话，替代品在原生世界存不存在？**

| # | 组件 | 现规模 | 能搬吗 | 原生方案要做什么 |
|---|---|---|---|---|
| 1 | 状态与持久化 | 100 行 | ✅ 纯逻辑 | 直接翻译 |
| 2 | 平台服务桥 | 前端 140 + 宿主 1700 | ✅ 已经是原生的 | Rust 侧本来就干这个 |
| 3 | Markdown 解析 | 470 行 | ✅ 纯逻辑 | 直接翻译（或换 pulldown-cmark，但要在指标核对） |
| 4 | 块序列化 | 含在 3、5 | ✅ 纯逻辑 | 直接翻译 |
| 5 | **所见即所得编辑器** | **4300 行** | ⛔ **搬不动** | **见 §3.1，这是全部代价的核心** |
| 6 | 代码编辑器 | 340 行 | ⛔ 搬不动 | 340 行是因为有 CM6。自写要高亮 + 光标 + 虚拟滚动 + 折叠，3000 行起 |
| 7 | 差异引擎 | 360 行 | ✅ 纯逻辑 | 直接翻译（LCS / 唯一行锚点都是纯算法） |
| 8 | 对比窗 | 2900 行 | ⚠️ 一半 | 行模型与 diff 可搬；**几何测量与渲染要重写**（见 §3.2） |
| 9 | 外壳 | 4400 行 | ⚠️ 逻辑可搬 | 菜单、标签、侧栏、设置全要重画 |
| 10 | 样式 | 1500 行 CSS | ⛔ 作废 | 原生没有级联、没有 flex/grid，全部改成布局代码 |

### 3.1 核心难点：所见即所得编辑器为什么搬不走

`wysiwyg.js` 4306 行能存在，是因为 Web 平台白送了下面这些。**没有一项是小事**：

| 浏览器白送的能力 | 自己实现的难度 |
|---|---|
| 块级 + 行内两级布局（一行一个 `w-block`，行内有粗体/链接/代码） | 要写一个小型排版引擎：行内盒模型、基线对齐、浮动、BFC |
| CJK 断行与避头尾（`。`「」`不能出现在行首） | DirectWrite 的断行不按中日韩习惯来，规则要自己补 |
| 字体回退链（中文 / emoji / 数学符号混排） | 逐字符 fallback + 缓存，踩坑期以月计 |
| `contenteditable` + Selection API（跨块选区、拖放、点击落点） | 光标模型、命中测试、跨块选区坐标换算 |
| IME 组字（`compositionstart` / 中文输入法候选窗） | Windows 的 IMM32 / TSF 集成，是出名的雷区 |
| 富文本剪贴板（`text/html` + `text/plain` 多 MIME） | 自己拼 CF_HTML 格式，还要解析别人给的 HTML |
| `@page` + `break-inside` 打印分页 | 分页算法自己写（现在靠 WebView2 `PrintToPdf`） |

项目里 **53 条不变量**有一大半是这块踩出来的（`renderedTabId`、`caretAfterBlock`、
`convertBlock` 的 COW、`handleClick` 的 target 语义……）。这些不是「写完就有的代码」，
是「被真实用户点出来的行为」。**重写等于把坑重新踩一遍**，而且新平台会送一批新坑。

### 3.2 对比窗反而可能是原生更舒服的部分

`compare.js` 里最别扭的几处 —— 「折行靠 `可用宽 ÷ CHAR_W` 估」「行高不等要维护前缀和」
「`pos[k]` 逐字符记区间」—— 全是因为浏览器不给精确的文本度量。
原生用 DirectWrite / Skia 可以直接拿到每段的真实宽高，**这部分会变简单**。
这是原生方案唯一天然占优的地方，但它只占 2900 行里的一小半。

### 3.3 生态：四个引擎的替代品现状

| 引擎 | 现用途 | 原生替代 | 判断 |
|---|---|---|---|
| CodeMirror 6（1.16 MB） | 代码编辑区、55 门语言 | 无成熟等价物（`ropey` + 自写渲染） | ⚠️ 3～6 个月 |
| highlight.js | 预览 / 导出 / 代码块着色 | **`syntect` 可用**（Sublime 语法） | ✅ 有替代 |
| prettier（2.2 MB） | 格式化 | `dprint` 只覆盖部分语言，`biome` 不是同一套规则 | ⚠️ 能力打折 |
| **mermaid（5.12 MB）** | 图表 | **没有任何原生等价物** | ⛔ **要么砍功能，要么内嵌 JS 引擎** |
| KaTeX | 数学公式 | `RaTeX` 早期，覆盖不全 | ⚠️ 能力打折 |

**mermaid 是死结**：它是纯 JS 生态，脱离 JS 引擎就没有替代品。
原生方案要么砍掉图表功能，要么内嵌一个 JS 引擎 —— 那就是又请回一个浏览器内核，
只是换了个更差的（内存省不了多少，稳定性差很多）。

---

## 4. 五条路线

| 路线 | 常驻内存（估） | UI 复用 | 引擎生态 | 工期（估） | 风险 |
|---|---|---|---|---|---|
| **A. 现状 + 内存工程** | 450～515 MB | 100% | 100% | **1～2 周** | 低 |
| **B. Sciter**（HTML/CSS 引擎，~10 MB） | 70～120 MB | HTML/CSS **可复用**，脚本全改 | 全丢 | 3～6 月 | 中高 |
| **C. Qt**（QTextDocument / QML） | 80～150 MB | 全重写 | 有内建富文本引擎，但无 CSS / 无 CM6 | 6～12 月 | 高 |
| **D. 纯 Rust 自绘**（winit + cosmic-text） | 50～100 MB | 全重写 | 全丢，富文本内核从零 | **12～24 月** | 极高 |
| **E. Servo / Verso** | 200～300 MB | 部分 | CM6 / prettier / mermaid 大概率跑不起来 | 不可行 | 极高 |

### 各路线的一句话评价

- **A**：唯一能在两周内拿到结果的。目标 543 → 450 左右，**到不了 200**。
- **B**：内存最划算的一条（省 420 MB），因为 HTML/CSS 那 1500 行样式**能直接复用**，
  这是它对比 C/D 的独特优势。代价是 TIScript 重写全部脚本 + 商业授权 + 四个 JS 引擎全丢。
- **C**：Qt 的 `QTextDocument` 是唯一「白送富文本」的原生引擎，但它的 HTML 子集远弱于 CSS，
  现在这套 `w-block` 布局要重做；且 CM6 / mermaid 一样没有。
- **D**：工作量最大且最难估的一条。**「编辑器」是全行业公认最难写对的东西**，
  4300 行的现有实现是几个月的真实调试换来的，不是一周能重写出来的。
- **E**：内存只省一半，兼容性风险最高。**不推荐**。

## 5. 如果一定要做：两周 spike 的验收标准

不要直接立项。用两周做一个**只验证内核、不做界面**的原型，回答「富文本到底多难」：

| # | 验收项 | 通过标准 |
|---|---|---|
| 1 | 打开一份 200 KB 的中文 md | < 300 ms，内存 < 80 MB |
| 2 | 显示：标题 / 段落 / 粗体 / 行内代码 / 列表 / 代码块 / 表格 | 七种块全部正确排版，中英混排不断错行 |
| 3 | 中文输入法 | 用微软拼音连续输入 20 字，候选窗位置正确，无丢字 |
| 4 | 光标与选区 | 点任意字落点准确；跨块拖选高亮正确 |
| 5 | 一次编辑的往返 | 改一个字，序列化回文本与原文件只差这一字 |
| 6 | 复制粘贴 | 从浏览器粘贴一段带格式文字进来，块结构正确 |

**六项全过才谈立项。** 任一项要花超过 3 天，就说明这条路线的真实成本是年为单位。

## 6. 建议

**结论：不做 B/C/D（Sciter / Qt / 纯 Rust 自绘），也不立项重写。**

1. **300 MB 是屏幕的函数**（§1.6）。同一台机器换低分屏 → 59 MB，零行代码。
   为一个「换显示器就能省掉」的数字重写 1.6 万行，账算不过来。
2. **剩下约 200 MB 是 WebView2 运行时地板。** 重写能省掉它，但要 6～18 个月，
   并且丢掉 mermaid（无原生替代）、prettier、CM6。**用 18 个月换 150 MB，不划算。**
3. 真要在高分屏上把内存压下来，**唯一手段是压 tile 预算**，本质是拿画质/帧率换内存 ——
   这是产品取舍，不是技术债，应该由用户自己决定开不开，而不是靠重写绕过。

### 若决定压 tile 预算（A 路线 0 号动作）

用 `tools/try-gpu-budget.ps1` 在目标机器上 A/B 三档（不设 / 192 / 128），
每档滚同一份长文档，**同时看任务管理器的数与眼睛看到的手感**。参数在
`src-tauri/tauri.conf.json` 的 `additionalBrowserArgs` 里，与环境变量那串必须保持一致。

### renderer 侧还能拿的（按需，最多几十 MB）

| # | 动作 | 预期收益 | 代价 |
|---|---|---|---|
| 1 | **恢复会话时限制标签数**（比如最多恢复 8 个，其余进「最近」） | 去掉「45 标签」这类场景的隐性负担 | 用户体验微调 |
| 2 | **切到 edit 模式或隐藏时 drop 掉 wysiwyg 的记录与预览 DOM**（已有 `dropPreviewDom()`，要扩大覆盖面） | 大文档场景 20～40 MB | 需回归光标/撤销 |
| 3 | 大文档（≥ 1 MB）默认进 edit 模式，不自动 wysiwyg | 避免一次 100 MB+ 的爬升 | 产品决策 |
| 4 | 评估 `--enable-low-end-device-mode`（实测省 27 MB） | 27 MB | 图像质量下降，需逐项比对 |

### 一个必须先说清的前提

**「500 MB」是按哪个口径看到的，决定了这件事要不要做。**

- 若看的是任务管理器「内存」列（专用工作集）：本机实测是 **259 MB**；
- 若把 7 个进程的工作集手动相加：**543 MB**（共享页被重复计算）；
- 若开了更多文档 / 对比窗口：会更高。
- **工作电脑的实测是「空闲 240、滚动 500」，其中 GPU 300** —— 这个组合说明主要成本在 tile，
  不在文档内容，见 §1.5。

**重写之前，请先确认这个数字的来源** —— 如果 500 MB 是「7 个进程相加」，
那它有一半是重复计算的假象，投入 12 个月重写的性价比需要重新算。
