## 0. 一句话概括

一个**单进程、多窗口、无边框、零 UI 框架**的 Tauri 桌面应用：前端是约 1.67 万行
原生 ESM，后端是约 1700 行 Rust，中间只靠 29 条命令说话。能力边界很清楚——

- **前端不知道文件在哪**：所有磁盘操作都过 Rust，前端只拿到字符串路径与内容。
- **后端不知道界面长什么样、说什么语言**：Rust 只回错误**码**，句子由前端拼。

这条边界是后面所有设计的前提。跨平台移植时它也是最大的帮手：**换操作系统主要是在
换「Rust 那 1700 行里的系统调用」和「窗口外壳」，业务逻辑一行不用动**。

## 1. 产品边界

目标用户是自己写 Markdown / 改配置文件 / 比对两段文本的人。产品赌注是
**启动快、体积小、不联网**，而不是功能多。

功能只分三类，新增功能必须先归到某一类：

| 类别 | 内容 | 对应模块 |
|---|---|---|
| **写** | 所见即所得、源码编辑、预览、格式化、查找替换、表格/公式/图片、大纲、多标签、速记 | `wysiwyg.js` `plain-editor.js` `preview.js` `format.js` |
| **看** | 语法高亮、编码与换行识别、字数统计、历史快照、导出（HTML / PDF） | `highlight.js` `history.js` `exporthtml.js` `pdf.js` |
| **比** | 行级 + 字符级 diff、文件夹对比、三方合并、两扇独立对比窗 | `diff.js` `compare.js` `foldercmp.js` `mergewizard.js` |

**明确不做**（不是没来得及，是不打算做）：图床、账号体系、云同步、插件市场、
多窗口拆分编辑、二进制对比。判断一个新需求该不该做，问三句：

1. 这个功能每天都会用到吗？
2. 能不能在不联网、不登录的前提下做完？
3. 它会不会让「打开一个 md」变慢，或让安装包明显变大？

任何一个答案是「否」，就不做。第 3 问是硬约束——体积和启动时间是这款软件的核心
卖点（见 §11）。

## 2. 技术选型

| 决策 | 选择 | 为什么 | 代价 |
|---|---|---|---|
| 运行时外壳 | Tauri 2（系统 WebView） | 不打包 Chromium，主程序 5MB | 三个平台的 WebView 内核不同，行为有差异（见《实现规格》§10） |
| 前端构建 | **无**（裸 ESM） | `frontendDist` 直接指向 `src/`，零构建配置 | 改前端必须 `cargo build`；第三方库要预先打成单文件入库 |
| UI 框架 | **无** | DOM 量可控（视口内 ≤600 块），手写比框架更快更小 | 没有响应式，所有刷新靠手写 `render*()` |
| Markdown 渲染 | 自研（`markdown.js`，469 行） | 只要 GitHub 风味子集；可控转义与图片路径解析 | 新语法要自己写解析分支 |
| 所见即所得 | 自研 contentEditable 块模型 | 没有现成库能同时满足「行=块 + 零延迟 + 大文件」 | 光标、退格、粘贴要自己兜（项目里最复杂的一块） |
| 代码/纯文本编辑 | CodeMirror 6（预打包成 `src/vendor/cm6.js`） | 语法高亮、缩进、撤销开箱可用 | 打包步骤多一步 `pnpm build:cm6` |
| 数学公式 | KaTeX（懒加载） | 只读渲染，不需要编辑期解析 | 首次渲染有 ~200KB 加载 |
| 多语言 | 自研 `tt()` + 生成式词条表 | 键=中文原文，代码里直接看得懂上下文 | 改文案要同步词条表（有测试兜底） |
| 打包 | Tauri bundler | 与 Tauri 一体 | 各平台产物格式不同（nsis / dmg / deb、AppImage） |

**为什么坚持不用打包器**：`src/` 里的每个文件都是运行期直接加载的模块，
`index.html` 里一行 `<script type="module" src="js/app.js">` 就是全部构建配置。
好处是 vendor 里的第三方库（Tauri API、CodeMirror、KaTeX、Lucide 图标）提交进仓库
后**永远可复现**，不怕上游改版或 CDN 挂掉；坏处只有一个：改完前端得重新编译，
因为资源是编译期内嵌进二进制的。

### 2.1 当初立的四条规矩

**1. 纯 ESM、无打包器，`src/` 编译期内嵌进二进制。**
前端没有 vite/webpack，浏览器直接吃原生 ES Module。代价是必须 `cargo build`
才能看到前端改动；换来的是：零构建配置、改哪看哪、vendor 的第三方库
（CodeMirror、KaTeX、lucide）提交进仓库后**永远可复现**，不怕 unpkg 改版。

**2. 模块边界按「谁独占某个 API」划，不按功能划。**
CodeMirror 6 的状态是一坨全局单例，任何地方散用 `EditorState` 都会出诡异 bug。
所以规定：**CM6 API 只有 `plain-editor.js` 能碰**，其他模块只调它暴露的
`value / selection / revealOffset`。同理序列化只认 `markdown.js`。这条边界
整个项目没破过一次，后来排查问题也从不用怀疑「是不是两处各改了一份状态」。

**3. 性能约定先立后写。**
「输入路径禁止全量重算」是项目早期就写死的规矩：normalize 只扫光标块 ±1、
大纲 250ms 防抖 + 结构签名、标签栏签名比对。后期加对比窗口、加 callout 时
新代码照抄这套模式，没有出现过「加了功能打字变卡」的回退。

**4. 每功能一提交，约定式前缀 + 一句话说清「改了什么」。**
回溯某个 bug 是哪次改动引入时，`git log --oneline` 一眼可读，比「fix bug」式提交
省一个数量级的翻找时间。（2026-11-02 起提交信息统一用英文，见《构建说明.md》§九。）

## 3. 运行时结构

### 3.1 进程与窗口

一个进程，最多两个窗口，靠 `tauri-plugin-single-instance` 保证全局只有一个实例
（第二个进程发现已有实例就把命令行里的文件交给它然后自己退出）。

```
进程 EZNotepad（单实例）
├── main 窗口（index.html）                        ← 双击文件 / 命令行参数进入
│   ├── WebView A：全部业务逻辑（约 30 个 JS 模块，1.67 万行）
│   └── Rust：文件 / 目录 / 监听 / 编码 / 窗口系统
├── compare 窗口（compare.html，按需创建）          ← 菜单「比较」/ Ctrl+Shift+N 进入
│   └── WebView B：独立 JS 上下文（compare.js）
└── foldercmp 窗口（foldercmp.html，按需创建）      ← 工具菜单「文件夹对比…」
    └── WebView C：独立 JS 上下文（foldercmp.js）
```

**两个 WebView 是两个互不相干的 JS 世界**：模块、全局变量、localStorage 之外的一切
都不共享。跨窗口只有三条路，项目里三条都用到了（各取所长）：

| 通道 | 用途 | 代码位置 | 注意 |
|---|---|---|---|
| Rust 状态 `Mutex<Option<T>>` + `take_*` 命令 | 打开工具窗口时把「左/右路径」传过去 | `CompareRequest` / `FolderCompareRequest` + 各自的 `take_*` | **不要走 URL query**：中文路径双重编码后与磁盘路径对不上 |
| 窗口事件 `emit` / `listen` | 窗口已存在时推新数据（复用窗口） | `compare:load` / `foldercmp:load` / `open-files` | 事件名是契约，改名要两边一起改 |
| localStorage | 主题、语言、设置 | `state.js` 的 `LS` | 两个窗口各读一份，改设置后另一窗不自动刷新 |

### 3.2 主线程规则（血泪级）

> **凡是「建窗口 / 弹原生对话框」的命令，必须是 `async fn`。**

Tauri 的同步命令在主线程上执行，而 `WebviewWindowBuilder::build()` 要等 WebView
回调；主线程被自己占着，`build()` 卡到超时——症状极具迷惑性：**窗口壳子、标题、
尺寸全对，页面永远不加载，整扇窗纯白**。

命令行入口 `--compare 左 右` 那条路走 `setup()`，本来就在主线程外，所以同一份代码
一条路好、一条路坏——这也是当初排查花了最久的原因。

### 3.3 启动流程

```
main.rs → lib.rs::run()
  ├─ 装单实例插件（必须第一个：要在建窗口前认出「已经有一个在跑」）
  ├─ 装 dialog / opener 插件，注册 29 条命令，manage 三份状态
  ├─ setup()
  │   ├─ 给主窗口套系统圆角（仅 Windows 11）
  │   └─ 解析 argv：有 --compare 就直接开对比窗，主窗口不显示
  └─ app.run()（当前为空回调 —— 见《实现规格》§10.4 A3，macOS 要在这里接文件打开事件）
```

命令行参数解析集中在两个纯函数（有单测）：`file_args()` 过滤掉开关与不存在的路径，
`compare_args()` 认出 `--compare 左 右` 并把这两个文件从「要开成标签」的列表里剔除。

### 4.2 五条依赖规则（违反就会出诡异 bug）

| 规则 | 具体约束 | 破了会怎样 |
|---|---|---|
| **R1 CM6 独占** | 只有 `plain-editor.js` 能 import CodeMirror；其他模块只能调它暴露的 `value/selection/revealOffset` | CM6 状态是全局单例，两处各改一份 → 光标乱跳、撤销失效 |
| **R2 HTML 只从 `markdown.js` 出** | 任何要插进 DOM 的 HTML 字符串都必须经过 `escapeHtml` / `inline()` | 一处漏转义 = XSS（预览是 `innerHTML`） |
| **R3 invoke 只从 `backend.js` 出** | 别处不许直接 `invoke()` | 绕过 `localizeError()`，用户看到英文/错误码原文 |
| **R4 不许循环 import** | 裸 ESM 下循环引用会让 `const` 停在 TDZ，表现为 `Cannot access before initialization` | 小概率、难复现，且只在某个模块先加载时炸 |
| **R5 状态只经 `state.js`** | 全局只有一份 `tabs` / `settings` | 两份真相 = 保存时写错标签（这个坑真踩过，见 §5.2） |

### 4.3 app.js 的内部结构

`app.js` 是唯一「知道所有事情」的模块，内部按功能分成若干段落，读它的顺序就是
界面的装配顺序：

```
导入 → DOM 引用表 el → 状态与视图切换(setMode/activate)
     → 标签栏刷新 → 工具条/状态栏刷新 → 大纲
     → 命令表 commands{id: fn} → 菜单树 menuTree() → 快捷键 setupKeys()
     → 初始化：setupDrop / setupSplitters / setupKeys / restoreSession
```

**所有功能入口都归到 `commands` 一张表**：菜单项、快捷键、命令面板、右键菜单，
四者只产出命令 id，执行统一走 `commands[id]()`。加功能时只加一条命令 + 引用它的
菜单项 / 键位，不要各写一份逻辑。

## 5. 状态模型

### 5.1 标签（`state.js::createTab`）

| 字段 | 含义 | 谁写 |
|---|---|---|
| `id` | 自增整数，界面里的 `data-id` | `createTab` |
| `path` | 磁盘绝对路径，未保存为 `null` | 打开/另存为 |
| `name` | 显示名（未保存时是「未命名.md」） | 改名/保存 |
| `content` | **源文本**，就是磁盘上应该有的那串字符 | 编辑器落账 / 打开 / 撤销 |
| `savedContent` | 上次读写磁盘时的内容，只用来算脏 | 保存成功 / 打开 |
| `encoding` `bom` `eol` | 读盘时探测到的编码与换行；保存时原样写回 | 打开 |
| `mode` | 当前模式（`wysiwyg` / `edit` / `preview`），按扩展名自动决定 | `setMode` |
| `scrollTop` `caret` | 切回来时恢复位置 | 切标签前 |
| `readonly` | 只读（大文件、二进制误判、外部结果） | 打开 |
| `external` | 是否为外部生成（对比结果 / 合并结果），保存时要问路径 | 对比/合并 |
| `mtime` | 上次读写时的修改时间，用于发现「别的程序改了它」 | 保存/监听 |

### 5.2 源文本是唯一真相（本项目最容易搞错的一条）

`t.content` 是权威数据，编辑器的 DOM 只是它的**投影**。由此推出三条纪律：

1. **落账（flush）必须在正确的时机**：输入走 600ms 防抖 + 失焦兜底，结构性编辑
   （Enter/Backspace/Tab/粘贴）立即落账。**每加一条写路径，第一件要问的是「脏标记在哪」**——
   早期漏掉 `applyEdit` 的脏标记，导致 `Ctrl+S` 判定「无改动」直接丢数据。
2. **DOM 有归属**：`wysiwyg.ownerTabId` 在渲染时钉住「这块 DOM 属于哪个标签」，
   `onChange` 只写回自己的标签。少了它，切标签那一刻旧 DOM 的 blur 会把旧内容
   写进新标签（**跨标签内容串台**，真机抓了半天的 bug）。
3. **落账后要封口**：`markCommitted()` 清掉 `_edited` / 待执行的 flush 定时器，
   迟到的 blur 不再冲第二次。

还有一条反直觉的：**没有未落账的编辑时，绝不读回 DOM**。判断「脏」用的是
`content !== savedContent`，不是「DOM 和 content 像不像」——读回 DOM 会把
DOM 的规范化差异（软换行、空白）当成用户改动，产生假脏标记。内存里统一按 LF
比较（`toLF()`），否则 CRLF 文件一打开就是「已修改」。

### 5.3 设置与迁移

设置是 `localStorage['snp.settings']`，默认值在 `state.js::DEFAULTS`，**改默认值必须
bump `__v`**：老用户 localStorage 里存着旧默认值，光改 `DEFAULTS` 对他们无效；
`__v` 变了才按新默认覆盖一次（并顺手清掉已经变成「粘滞值」的键）。

当前 `__v = 4`。测试或脚本要钉死设置时，写入的对象必须带 `__v: 4`，否则会被迁移逻辑
改写（这是测试环境的经典陷阱）。

### 5.4 数据落盘位置

| 数据 | 位置 | 说明 |
|---|---|---|
| 设置 / 草稿 / 会话 | `localStorage`（前缀 `snp.`） | 由 WebView 的 profile 目录承载 |
| 历史快照 | `<app_data_dir>/history/<fnv1a(路径)>/*.txt` | 一个文件一个目录，目录名是路径的哈希（避免路径里的非法字符）；`name.txt` 存原始文件名方便人看 |
| 粘贴/拖入的图片 | `<文档所在目录>/assets/` | 用相对路径引用（`![](assets/x.png)`），换机器不断链。**未保存的文档直接拒绝**并提示先存盘——没有「同目录」可放 |
| 速记 | `<app_data_dir>/quicknote.md` | 固定一份，不跟文档走；路径由后端 `quick_note_path` 给（见 §5.6）。探针用 `EZNOTEPAD_QUICKNOTE` 改到 `%TEMP%`，绝不碰用户那份 |

`app_data_dir` 由 Tauri 按平台给出（Windows `%APPDATA%`、macOS
`~/Library/Application Support`、Linux `~/.local/share`），**代码里没有任何硬编码路径**
——这是移植时少数不用管的地方。

### 5.5 撤销：两套实现，按文档大小分流

| 文档 | 快照内容 | 代价 |
|---|---|---|
| < 1MB（DOM 即模型） | 记录型快照（文本或块引用） | 每步约 60KB，上限 200 条 |
| ≥ 1MB（视口模式） | `records` 数组的浅拷贝 | **记录写时复制**，未变的块共享引用；8 万块约 304KB |

写时复制是这里的地基：`records` 里的块对象视为只读，`_syncWindow` 只在内容真变时
换新对象，于是 `records.slice()` 就是零成本快照。**绝不能往记录上挂 DOM 引用**
（`rec.el = el` 会让 COW 失效，快照退化成深拷贝）。

**入口只有一条路。** 三种入口（`Ctrl+Z`、工具行两个箭头、编辑菜单 / 命令面板）都落到
`editCmd('undo' | 'redo')`，它按模式分派到各自的栈：`wysiwyg` 走 `wys.undo()`，纯文本走
CM6 的 `undo(view)`。这里**不许用 `document.execCommand('undo')`** —— 它操作的是浏览器
原生栈，而所见即所得的 DOM 是受控重绘的，两套栈各记各的：混着用会退到谁也没预期的位置
（内容退一半、光标乱跑），比没有撤销更糟（见不变量 27）。

按钮和菜单项的可用状态来自 `canUndo()` / `canRedo()`（wysiwyg 读 `hIndex`，纯文本读
CM6 的 `undoDepth` / `redoDepth`），到栈底就变灰。**"点了没反应"是最差的反馈** ——
用户分不清是软件坏了还是自己记错了。

### 5.6 速记：一份「不用保存」的文件

固定位置的一份 Markdown（`<app_data_dir>/quicknote.md`，路径由 `quick_note_path` 给），
不选位置、不按保存。它仍是普通标签，只有三处刻意不同：

| 普通文档 | 速记 |
|---|---|
| 脏标记 = 内存 ≠ 磁盘 | 永远算干净（`isDirty` 直接放行）—— 它没有「保存」这个动作 |
| 关窗时逐份问「要保存吗」 | 不问；关标签 / 退出前先 `flushQuickNote()` |
| 进「最近打开」、进会话恢复 | 都不进：它是「随时能回去的地方」，不是「上次打开的文件」 |

身份靠标签上的 `quickNote` 标记，**不靠路径比较** —— 路径比较要在每个用到的地方重新
问一次后端，而标记在建标签时就定下了。

关闭前必须 flush：打字 → 落盘是 350ms 防抖，打完最后一个字就关窗的话，`content` 里
可能还差几个字。这条和「永远算干净」是配套的：**正因为不显示脏标记、不弹确认框，
沉默丢字的窗口必须由代码自己关掉**，否则「不用保存」就成了「悄悄丢」。

速记只有一份：`openQuickNote()` 先找带标记的那个标签，`openPath()` 命中速记路径时也
改道过去（文件树、拖放、最近打开都会走到这里）。两个标签写同一个文件，后保存的会把
先保存的盖掉。

「另存为」对速记意味着**导出一份副本**：绝不改 `t.path`，否则接下来的自动保存会写到
副本上，速记本身从此不再更新。

菜单栏上的「速记」是一个**动作项**（跟「设置」同类：`action` 而不是 `items`），点一下
就打开。曾经它是下拉菜单，第一项才叫「打开速记」—— 用户的第一反应是「我明明已经点了
速记」，于是要连点两次。辅助动作（插入当前时间 / 在文件夹中显示 / 复制路径 / 清空）
频率低得多，放在「文件」菜单末尾的「速记」小节，不再借「打开」占用户第二次点击。

**高频入口排在菜单栏最右边**：`文件 / 编辑 / 格式 / 插入 / 视图 / 工具 / 设置 / 帮助 /
速记 / 对比`。速记和对比（文本 / 文件夹 / 三向合并）原来分别躲在「文件」的第二位和
「工具」的中段，天天点的东西不该让人在菜单栏上找 —— 位置固定、伸手就到才是它们需要的。
同一个命令不在两处各列一遍，所以「工具」里那三项已经删掉（命令面板仍然全部收得到，
它是从 `menuTree()` 走出来的，分组名跟着菜单走）。

### 5.7 标签条溢出（十几个标签之后）

标签条本身能横向滚动（`overflow-x: auto`），但滚动条被藏起来了
（`scrollbar-width: none` 加 `::-webkit-scrollbar { display: none }`，一条横向滚动条
会把标签挤扁）。于是标签一多，界面既看不出「后面还有」，也没有可抓的东西 —— 用户
以为标签丢了。补三个入口，都很轻：

| 入口 | 做法 | 注意 |
|---|---|---|
| 滚轮横滚 | `wheel` 里把 `deltaY` 当横向位移；`deltaMode === 1`（按行）要 ×16，否则一格只动 3px | `passive: false` 才 `preventDefault` 得掉 |
| 拖标签贴边自动滚 | `dragover` 里按指针距左右边缘的距离定速度，**必须用 `requestAnimationFrame` 自己循环** | 指针不动就不会再来第二个 `dragover`，靠事件驱动会停在半路 |
| 「全部标签」下拉 | 右侧那颗按钮只在 `scrollWidth > clientWidth` 时出现，点开给一份带滚动条的清单（当前项 `✓`、脏项 `●`） | 菜单要传 `stayOnScroll`，见不变量 47 |

**当前标签必须自动滚进视野**（`syncTabOverflow`）：新建的排在最后，不滚过去，界面上
就是「点了新建没反应」。溢出判定用 rAF 合并，`renderTabs` / `resize` 各调一次即可。

## 6. 渲染管线

### 6.1 三种模式

| 模式 | 适用 | 实现 | 数据流向 |
|---|---|---|---|
| `wysiwyg` | Markdown 默认 | `wysiwyg.js`（一行=一个 `.w-block`） | md → 块 DOM ⇄ md |
| `edit` | 纯文本 / 代码 / 想要源码视图 | `plain-editor.js`（CM6） | 字符串 ⇄ 字符串 |
| `preview` | 只读看渲染结果 | `preview.js` | md → HTML 字符串 |

md 文件默认落在 `wysiwyg`（`modesFor()` 的首项）；`lastMode` **只记忆用户手动切换过
的模式**，自动落位不写入——否则默认值首次启动就会被粘滞成别的模式。

### 6.2 md → 块

`parseMarkdown(md)` 产出 `DocumentFragment`，每个块带类型与元数据：

| 块 | class | 备注 |
|---|---|---|
| 标题 | `.w-h1`…`.w-h6` | 哈希把手 `.w-hash` 是 `contentEditable=false`，绝不进 `.w-text` |
| 段落 | `.w-p` | |
| 列表项 | `.w-li` | `gap` 标记空行、`li` 标记层级 |
| 引用 | `.w-bq` | 连续 `.w-bq` = 一个引用组，组首行打 `data-bq-start` |
| 提示块 | `.w-bq[data-callout]` | `> [!info] 标题`，标题行 `.w-co-head` |
| 代码块 | `.w-code` | 语言存 `data-lang` |
| 公式 | `.w-math` | 块级独立成块 |
| 表格 / 分割线 | `.w-table` / `.w-hr` | 表格不可拖拽、没有「转为其它块」 |

**空行不是块**：块之间的空行由序列化按类型生成。空标题原地降级（不 `replaceWith`，
否则光标错位）；正在敲 `###` 时不降级。

**输入入口先看宿主，再决定怎么改模型。** 同一个 `paste` 事件落到不同块上，语义完全不同：

| 落点 | 怎么处理 | 为什么不能走别的路 |
|---|---|---|
| 普通段落 / 空行 | 多行 → `parseMarkdown` 成块，顶替空行或插在块后 | 从别处粘一段带标题/列表的文字，结构要保留 |
| **列表项 / 引用行** | **在容器里续行**（`pasteLinesInContainer`）：逐行等价于按回车，li 续同 kind 同缩进、bq 续同缩进并接住提示块颜色 | 按段落插在块**后面**会把容器拦腰截断：`- 第二项` 之后冒出三个普通段落、每段还隔一个空行，列表就此结束 |
| 表格单元格 | 只取第一行，`insertText` | 多行会把表格结构塞进一个格 |
| **代码块 / 公式块** | **原文进块**（`insertRawText`），换行落成 `<br>` | 走 Markdown 解析时，空块会被 `replaceWith` **整块换掉**（粘一段 JSON 代码块凭空消失），非空的则把段落插到块**外面** |
| 图片文件 | 交给外层落盘，回填 `![](assets/…)` | webview 里 `<img src=blob:>` 存不住 |

代码块内部没有「行」这个概念（一个 `.w-code` 里全是文本节点 + `<br>`），所以粘贴只能
在光标处插节点：换行**一律用 `<br>`** —— 往文本节点里塞 `'\n'`，Chromium 下一次输入会把
行尾那个吃掉，光标漂到换行前面；末尾再垫一个零宽空格，否则以换行结尾的粘贴会让光标停在
行尾的 `<br>` 上，接着打字跑回上一行（`codeNewline` 踩过同一个坑）。空块里那个占位 `<br>`
要先摘掉，不然粘进来的内容前面多一个空行。

**点击的分支要按坐标判，不能只看 `event.target`。** 跨块拖选之后，浏览器把 `click` 派发给
**按下点与松开点的最近公共祖先** —— 选到两行以上就是编辑区根节点，和「点了正文空白」
长得一模一样。旧代码照空白处理：在文末补一个空段落、把光标搬进去，用户刚选好的一段字在
松手那一刻就没了（表现为「所见即所得选不了多行」）。现在两道闸：选区非空直接返回；
真要按空白处理时再用 `elementFromPoint` 问一下这一点到底命中谁，命中任何块就按「点在字上」。

**容器里的粘贴：一行 = 一项。** 列表项和引用行是有「兄弟关系」的块，多行粘贴必须往容器里续，
而不是往容器后面插。实现上就是把每一行当成一次回车（`splitBlock`），整段只 flush 一次 ——
逐行 flush 在万块文档上是一次几百毫秒的全量序列化，所以 `splitBlock` 多了个 `batch` 参数，
批量调用时把收尾的 `renumber` / `flush` 交给调用方。空行不占一项：容器里空行只是排版，
而空的 li / bq 在模型里存不住（序列化直接丢掉），真造一个只会留下看不见的空位。

**带边界的块要有明确的出口，但方向键绝不改文档。** 光标走到这些块的**最后一个
可编辑位置**时，↓ 和 → 的语义只能是**出块**。两个键都走 `caretAfterBlock()`，
它只移动光标并记状态，落点按顺序取第一个成立的：

1. 块后已经是空段落 —— 停进去，绝不重复开行；
2. 块后还有能站人的块 —— 光标落到它开头，同时记下一次性的「块后待插入」(`gapAfter`)；
3. 块后什么都没有，或紧跟着没有光标位的分割线 —— 光标保持不动，同样记下 `gapAfter`。

用户**按回车 / 打字 / 输入法组字 / 粘贴**时，`materializeGap()` 才在块与下一块之间插一个
真段落、`flush()` 落库。点击、其它方向键、Tab / 退格 / 快捷键、失焦、重渲染都把 `gapAfter`
清掉。1.2.6 之前是「出块即插行」，按一下方向键文档就变脏、撤销栈多一条 —— 用户判定
这种擅自新增不符预期；改完之后既不动文档，又保住了「出块后回车加一个空行」。

哪些块算「带边界」由 `endsBounded()` 判定，判据不是外观而是**光标能不能在块内继续往后走**：

| 块 | 判据 | 为什么要管 |
|---|---|---|
| 表格 | 最后一格末尾（`tableInfo` 行列都到底） | 一个 contenteditable 宿主，格内没有更靠后的位置 |
| 代码块 / 公式块 | 末行末尾 | 同上，且末尾常垫着零宽空格 |
| 引用 / 提示块 | 本行没有 `data-bq-tail`，即**这一组的最后一行** | 一行一块，组内还有下一行时浏览器自己会走 |
| 列表 | 下一个兄弟不是 `li`，即**最后一项** | 同上 |
| 分割线 | 光标在它**上一行**的末尾（它自己放不了光标） | 没有光标位，落在文末时是一条走不过去的墙 |
| 普通段落 / 标题 | 不算 | 它本身就是出口的落点，末尾再长行只会让文档越按越长 |

引用与列表是「一行一块」的容器：组内还有下一行时**必须让浏览器自己走**（折行了几行、要不要
顺手滚动，只有它知道），只有走到组的最后一行才轮到我们接管。`data-bq-tail` 由 `renumber()`
按记录算出来，正好是「后面还跟着同一组的引用行」。

分割线是唯一「自己放不了光标」的块，所以它不按「块内最后一个位置」判，而是**站在它上面那一行**
判：末尾按 ↓ 会穿过它 —— 有下一块就落进去，没有就在它下面新开一行（否则文末那条 `---`
就是一道走不过去的墙）。

第 1 条里「空段落就停进去」是判重的关键：以前无条件 `insertEmptyAfter`，表格下面本来就空着
一行时按一下又冒一行，文档末尾越按越长（空段落不进 Markdown，但屏幕上真真切切多一行）。
第 2/3 条把插入推迟到用户真要写入的那一刻：下一块哪怕是表格 / 代码块 / 引用，这一下回车
也由 `gapAfter` 接管到块后，不会变成在下一块内部加行；直接打字则先建行再落字，不会写成
`新后一段`。用「临时占位块」绕开 records 模型会在窗口化重铺时悄悄消失，把 Range 悬在
子节点间隙假装有一行则会在 WebView2 里被吞掉，都不是正路。

**「走到头」按眼睛看到的算。`isCaretAtEnd()` 除了剥掉垫脚用的零宽空格，还必须剥掉
代码块 / 公式块正文末尾那一个 `\n`**：`pre-wrap` 不给末尾换行生成可点击的行，浏览器把行尾
点击映射到它前面（`offsetIn === end - 1`）。旧判据把它算进 `end`，末尾留过一次回车的代码块
就永远判成「不在末尾」，`handleArrow` 不接管、浏览器原生把光标甩进下一块 —— 表现为
「代码块后面有内容时出不了块，别的块都行」（表格 / 引用 / 列表的正文没有裸 `\n`）。
只剥末尾这**一个**：再往前的每个 `\n` 都对应一条看得见的空行，全剥会让用户在倒数第二行
就被弹出去。

↓ 与 → 在块内最后一个位置做同一件事不是偷懒 —— 走到头的下一步就是出去，让它原地打转才是
违背直觉的。同理，`→` 也必须在 `handleKey` 里派发到 `handleArrow`，否则表格右下角压根没有
出口，只能动鼠标。

**鼠标点文末空白走的是同一条语义**：不是「在这儿加一行」，而是「把光标送到文末能打字的地方」。
要不要垫一行由 `needsLineBelow()` 判 —— 代码块 / 公式块 / 表格 / 分割线把光标包在自己的结构里
（表格还得进格子，分割线连光标位都没有），点在它们下方的空白上没有可写位置，才 `insertEmptyAfter`；
段落、标题、引用末行、列表末项本身就是可写位置，`placeCaretEnd()` 就够。补出来的空段落立刻
成为新的末块，所以再点几次也只多那一行。块尾的插入指示线跟着同一个判据亮，因为它的全部意义
就是预告「点这里会多一行」—— 判据一变还照旧亮，就是在骗人。

**代码块的着色一个 DOM 节点都不动。** 编辑态的代码块是 `contenteditable` 里的一段纯文本
（`.w-code` 里只有文本和 `<br>`）：往里插 `<span>` 会同时毁掉三样东西 —— 光标（Blink 会把
光标从 span 里踢出来）、撤销记录（按块存，结构一变就不是同一个块）、序列化（多处逻辑假定
子节点是 text / br）。所以着色走 **CSS Custom Highlight API**（`codehilite.js`）：它给
「文本区间」上色，和查找高亮（`domfind.js`）是同一套机制。

区间直接从 `highlight()` 的输出来 —— 在离屏节点里走一遍，把每个 `.tok-x` 的文本节点换算成
源码偏移。因此编辑态和预览看到的是**同一份着色**，没有第二套分词实现。换算有一处必须小心：
`<br>` 在源码里是换行、占一位却没有文本节点，零宽空格（`codeNewline` 垫的垫片）在 DOM 里
是一位、源码里根本没有。要逐字符记位置（`pos[k]`），直接拿 `textContent.length` 会整体错位，
颜色就涂到别的字上。

重算交给一个 `MutationObserver`（childList + characterData，防抖 120ms）：输入、粘贴、撤销、
`render`、视口搬家全都落到同一个出口，不必在每个路径上各挂一次。它不碰 DOM，所以不会自激。
单块超过 4 万字符直接放弃着色 —— 打字流畅比彩色重要（highlight.js 40k 约 40 ms，
旧的正则实现更快但只会 17 门语言；这笔交易是明知而为）。

**没标语言的代码块自己认。** `detectLang()` 给每种语言记一组特征正则，命中加权、取最高分
且过门槛（3 分）的那个；JSON 能 `JSON.parse` 就直接认，不必打分。识别结果只用于着色和
语言条显示，**绝不回写 Markdown** —— 往用户文件里补一句 ```` ```js ```` 会让首次打开就标脏，
存一次就改了人家的文件。

### 6.3 序列化

`blocksToMd()`（DOM → md）与 `recordsToMd()`（记录 → md）是两条独立实现，必须给出
**逐字节一致**的结果——所有 round-trip 测试断言的就是这件事。**改任何一个块类型，
两个序列化函数 + 两个解析入口（`parseMarkdown` / `parseRecords`）要同时改**，
这是本项目最容易漏的一处（提示块曾经在两条路径上行为不一致）。

### 6.4 预览

`renderPreview(kind, text, lang, target, docDir)` 按类型分流，绝不糅合：
md 走 `renderMarkdown`，json 走格式化 + 错误定位，代码走 `highlight.js`，其余纯文本。

`markdown.js::inline()` 的**顺序是有意的**：行内代码 → 公式 → 转义。先抽出代码与公式
（它们内部的字符不再参与 Markdown 解释），再统一转义，否则 `` `a<b` `` 会被吃掉。

**大纲提取**（`preview.js::extractOutline`）只看结构，不猜内容：md 认 `#`（跳过围栏代码），
json 认缩进层级，代码认函数/类定义；纯文本只认 `# `、Setext 下划线（`===`/`---`，标题在上一行）、
`【章节】`、`第X章/节/条`、以及多级编号（`1.1` 按点号段数分级）。**单级编号必须「空行断组后
只剩它一条」才算章节**——否则一份 `1. 2. 3.` 的清单会把每行都变成大纲，这正是旧实现的问题。
csv/tsv 一行一条记录，不提取。收完统一做一次「不许跳级」归一化，避免 h3 上面没有 h1/h2 时缩进悬空。

### 6.5 视口渲染（> 1MB）
超过 `BIG_DOC_CHARS = 1000 * 1000` 字符的文档换一条路径：

- **`records` 是唯一真相**（每块存 md 原文切片 + 标记），DOM 只放窗口内（约 4 屏，
  上限 600 块）。
- 窗口外的高度用 `.wysiwyg.virtual::before/::after` + `--vpad-top/bot` 撑出来。
  **绝不能用 `padding`**：`clientHeight` 含 padding，会把滚动容器自己撑高。
- 必须 `overflow-anchor: none`：浏览器的滚动锚定会和自己的 delta 补偿各补一次。
- 视口模式下 `Ctrl+A` 走**逻辑全选**（标记整篇 + 拦截 beforeinput/copy/cut），
  原生全选只覆盖窗口内容，随后打字会把窗口外几万块当「未选中」删掉。
- `_render()` 里任何分流分支**结尾必须补 `silent = false`**，漏了会让编辑不进
  `tab.content`、不变脏、不自动保存。

### 6.6 性能纪律（写进代码注释的硬约定）

1. **输入路径禁止全量重算**：normalize 只扫光标块 ±1。
2. 大纲 250ms 防抖 + 结构签名（签名没变就不重建）。
3. 标签栏刷新前先比签名，没变就返回。
4. 大纲定位用二分（标题位置单调递增）；`syncOutline` 同理。
5. 判「结构变化」只看块类型（`typeFrom`/`typeTo`），不看文本——纯文本编辑不算结构变化。

### 6.7 对比窗口（`compare.html` 独立页面）

**坐标只有一套**：虚拟滚动、当前块框、预览条全都问同一组几何函数（`rowTop()` /
`rowH()` / `rowAtY()` / `totalHeight()`），不许在任何地方再写 `下标 × 行高`。
换行（默认）时行高不等，这组函数读的是前缀和 `S.y`（每行顶边，长度 = 行数 + 1）
与 `S.hh`（每行高），`rowAtY()` 在 `S.y` 上二分反查行位；不换行时所有 `hh` 都等于
`ROW_H`，行为与旧的「下标 × 行高」逐像素一致。

**折行数是算出来的，不是量出来的**：等宽字体 + `word-break: break-all` +
`overflow-wrap: anywhere` + `line-break: anywhere` ⇒ 一行能放几个字只取决于可用宽度，
`layout()` 拿「可用宽 / `CHAR_W`」得到列数，再把每行的显示宽度（`S.uL` / `S.uR`，
单位是半角单元，全角算 2）除以列数向上取整就是折几行。所以 `recompute()` 里一次算好
`uL`/`uR`，滚动时只是查表 —— 不去 `getBoundingClientRect()` 量每一行：5 万行文档量一次
就是几千次重排。`layoutKey`（`行数:版本:列数:行高`）没变就直接返回；`buildView()` 末尾
清空它强制重算（折叠开关会改行数而不改版本号）。

预览条的轨道从**滚动区顶部**起算（不是从预览条自身顶部——每栏顶上还有 26px 的文件名条），
高度取 `min(可视高度, 内容高度)`，所以短文档时预览条只有几行高，也不会出现
「视口框比容器还高」的假象。点击/拖动的换算必须和绘制用同一个 `rulerGeom()`。

**行显示模式是全局设置，两个窗口共用**（`settings.wrap`，默认开）：主窗口与对比窗口
都读同一份 localStorage。CSS 只写「不换行」这一侧（`body[data-nowrap]`）—— 换行是浏览器
的默认行为，正面写一遍反而会和 `white-space: pre-wrap` 之类的既有声明打架。属性用
`toggleAttribute` 而不是 `dataset.nowrap = ''`：后者写的是空字符串属性，选择器
`[data-nowrap]` 虽然能命中，但再想「关掉」只能 `delete`，容易漏。切换时**要保住视口
顶部那一行**（记 `rowAtY(scrollTop)`，重排后滚回 `rowTop(keep)`），否则在 2000 行文档
的第 21 行上打开换行，屏幕会跳到第 2 行。编辑器那边是一个 CodeMirror 的
`Compartment` 热替换 `EditorView.lineWrapping`，不重建 state ⇒ 撤销历史和选区原样留着。

**滚动路径禁止扫全表**：差异段位置在 `recompute()` 里折成 `S.items`（`difflist.js`），
`drawRuler()` 只遍历差异块。5 万行、501 处差异时滚动处理 3.6ms/帧；改回「每帧扫所有行」
会直接掉到十几毫秒，滚动发黏。

**上限是产品参数**：单文件 8MB / 5 万行（`MAX_BYTES` / `MAX_LINES`）。读取前先用
`file_size` 问大小，超限不读、不加载，在正文上方给一条可关闭的提示条（文件名、实际值、
上限、建议），同时 toast 一次。引擎本身很快（5 万行 160ms、两份无关的 5 万行 85ms），
卡的是读入、每行一个对象的行模型和导出报告。

**差异清单**（`difflist.js` + 工具栏按钮）把每个差异块摊成一行：位置、类型、行数、摘要。
表头三列都能点，同一列再点切换升降序；筛选按 修改/仅左/仅右。超过 300 条只渲染前 300 条
并明说，不假装全列出来。

**并排对齐补出来的空位是「可写的位置」，不是空白**：`buildSideBySide` 会把短的一侧
补齐成占位行（`row.l` 或 `row.r` 为 `null`）。这些行必须满足三件事，少一件用户就卡在
「贴完一边，另一边动不了」：①编辑态下同样带 `contenteditable`；②写下去等价于**在这一侧
插入一行**（插入位置 `row.fL`/`row.fR` = 前面最后一个本侧行号 + 1，`flush()` 走
`splice(at, 0, ...)`）；③点击必须落在这**一条对齐行**上——占位行的行号列是空的，
按行号取 `+'' === 0`，`focusAt` 会把它夹成第 1 行，表现就是「点第 3 行，字进第 1 行」。
占位行按对齐索引走 `focusRowIdx()`，不经过行号映射。视觉上编辑态给一道极淡的斜纹
（`--cmp-void-band`）+ 行号位的 `·`：只读时不该暗示可写，编辑时要让人看出「这里缺了几行」。

**跨行替换的边界是字符偏移，不是行号**。全选/拖选之后粘贴、删除、打字都落到
`replaceSpan()`：它把两端换算成「本侧正文里的字符偏移」再替换，占位行取紧邻的行界
（`fL/fR - 1` 那条线，尾部占位就是正文末尾）。这条不换成偏移就会漏掉最常见的一种
情形 —— 一侧粘进来的行比对面**多**，于是对面在对齐表尾部多出一串占位行，全选时
选区末端正好落在占位行上；按行号取会「两端都必须有本侧行号」，整段替换静默放弃，
用户看到的是「全选之后按粘贴毫无反应」，而先改的那一侧却一切正常。

**预览条只有两种颜色，语义不许重叠**：红 = 这一行有差异；灰框 = 你正看着的这一屏。
红标记是**细线**（10px 宽、1px 高，画在 22px 轨道的正中），不再是铺满轨道的色块，
也**不再给「当前这一处」涂第二种颜色**：差异位置本来就靠红线的疏密看出来，多一种颜色
只会让人问「蓝色是什么」。两种含义写进 `#ruler` 的 `title`（九种语言）。

**预览条上一行一条细线，不画粗段**（`diffMarks()`）：早期按「差异块」画成整段红柱 ——
一段 20 行就是一根 20px 高的色块，看着像滚动条的影子，也分不清到底是哪几行。
现在逐行 1px（`per >= 2.5px` 且差异行不超过 4000 条时；再密就退回按段并一条），
「有多少行不一样、密不密」能直接数出来。标记列表按
「版本 / 总行数 / 轨道高 / `LAYOUT_VER`」缓存，滚动时不重算。
逐行标记的高度**永远是 1px**，位置才走 `S.y` —— 折行后一行占 80px，按行高画就变成一根
粗柱子，正是「不要用粗线」要避免的东西。

**差异只把字标红，不铺底色、不画色块**：改行（`chg`）只有 `inlineDiff` 那段 `<mark>`
是红的，新增/删除行（`add`/`del`）整行都红。底色、行框、行内色块全部去掉 ——
一屏几十处差异时，铺底色会让整页发红，反而看不出是哪几个字变了（参考 notepad-- 的做法：
差异要一眼看见，但**看见的应该是字**）。

**宽度是这个控件好用与否的第一件事**：栏宽 34px、槽宽 22px（`--cmp-ruler-w`）。
一开始是 22px 的栏里塞 10px 的槽，三样东西（差异段、当前段、视口框）抢十来个像素，
点起来像瞄靶 —— 用户的原话就是「预览条太窄，很不好用」。丢给正文的 12px 换这些划算。
另外视口框在「内容只比一屏多一点」时不画（`contentH <= viewH * 1.12`）：那时框几乎
顶满整条槽，剩下的只是把整条轨道染灰。

**「只看差异」把相同行收起来**（`buildView()` → `S.view`）。大文件里 20 处改动散在
2000 行之间，滚动的成本比读的成本还高；折叠后 2000 行只剩 49 行，差异一眼可数。
这引入一条硬规矩：**凡是「哪一行在哪、有多高」的地方都必须走 `S.view` + 几何函数**
（`rowTop(vi)` / `rowH(vi)`），再拿 `S.rows` 的下标当行位就会错开被折掉的那些行 ——
渲染、滚动定位、`focusAt`、当前块覆盖层、预览条的比例、`gotoBlock`、点击兜底，
一个都不能漏。同一个理由：换行后行高不等，任何「下标 × 行高」也一样会错。

折叠有两个必须钉住的特例：①**光标所在的行**（`S.pin`）永远保留 —— 把左边改成和右边
一样，这一行就从「修改」变成「相同」，随即会被折掉，光标当场消失，表现为「键盘不管用了」；
②**查找跳到的命中行**同样保留，否则按「下一个」屏幕只滚到一片接缝，命中行还藏着。

**查找**（`Ctrl+F`，浮在文件名条那一行上，不占正文）：对比窗口的查找和编辑器有一处不同 ——
命中的是**两栏**，同一条对齐行可能两边都有，所以 `hits` 按对齐行去重，否则「下一个」
会在左右两栏之间原地打转。高亮只做**行级**：差异行的 `inner` 是 `inlineDiff` 生成的
高亮 HTML，再往里插 `<mark>` 会把两边的高亮互相踩掉。命中色是蓝、当前命中再加一条左侧
竖线，和差异红刻意分开 ——「哪里不一样」和「你找的那个词在哪」是两件事。

**滚动时「第几处」跟着视口走**（`followScroll()`）：不然滚到第 5 处，状态栏还写着
「第 1 / 22 处」，按 F8 从第 2 处继续 —— 用户看到的是「导航不认我滚到哪」。只改
`curInfo` 和那个框，**不调 `updateStats`**：后者要重扫全篇统计行数，每帧跑一次 5 万行就卡了。

**关闭必须过 `onCloseRequested`，不是「点 × 的时候才查」**：对比窗口是独立窗口，Alt+F4、
任务栏关闭都绕开按钮。`onCloseRequested` 里先 `flush()` 把防抖中的那行并回模型，再判
`dirtySides()`；有脏数据就 `preventDefault()` 并显示顶部确认条（保存并关闭 / 不保存 / 取消）。
粘贴进来的文本没有磁盘目标，「保存并关闭」在这种情况**不显示**——给一个按了也没用的
按钮比没有按钮更糟。用户确认后 `forceClosing = true` 再 `close()`，否则会被自己拦第二次。

**窗口是复用的**：清单的排序/筛选会留在上一次的状态，`probe-compare` 断言前会先归零。
「打开一对新文件」则必须重置两侧（见不变量 25）。

**打开一对文件就直接可写**：只读是一个可主动切换的状态，不是打开时的默认值。
默认只读的代价是「点一下正文没反应」，用户会以为窗口坏了 —— 而误改有三层兜底：
行上的脏标记、`Ctrl+Z`、关窗前确认。

**没带文件打开时，直接给两个空白编辑区**（`startPairText()`）：不再有「选择左侧文件 /
选择右侧文件 / 粘贴两段文本」那个浮层。对比窗口最常用的用法就是「贴两段文本比一比」，
先摆一屏按钮等于让人点两次才开始。光标落在左侧第一行，`Ctrl+V` 就能用；想比文件就点
槽位上的**文件夹图标**（有图标才看得出那里能点）。只带一个文件打开时，另一侧补成空白
文本（`blankSide()`），仍然两侧都能写。读文件失败时那一侧也清成空白可写区 ——
既不留上一轮的旧内容（那会给出一个看似正常的结论），也不留一块点不动的死区。

**「复制到另一侧」的单位是一处差异**（`pushBlock`）：不是一行、也不是整个文件。
这两头之间的那一档才是对比工具真正被用到的粒度 —— Beyond Compare 的 Copy to
Other Side 复制「选中的行或当前段」，WinMerge 的 `Alt+←/→` 复制的是 difference，
Meld 中栏的箭头是整块 replace+delete+insert。实现上就是把源侧这一段的文本数组
`splice` 进目标侧同一个对齐位置（目标侧在这一处没有行时，插入点用 `recompute()`
算好的 `fL`/`fR`，和占位行写字同一套）。`Ctrl+Alt+←/→` 推完再跟到下一处，
一路按下去就是连续合并。

**箭头长在中间那道缝里，不在工具栏上**（`syncGutter()`）：这是用得最多的动作，
放在顶部等于让鼠标从正文跑回顶上再跑回来。分栏中间留一条 26px 的车道（`--cmp-gut`），
`←`/`→` 两个方钮常驻其中，纵向跟着**当前这一处**差异走（滚出视口就夹在可见范围内）。
方向就是箭头指向，不再随光标所在侧翻转 —— 一个按钮说两件事，两边都说不清（不变量 37
因此只作用于键盘的 `Alt+←/→` 与撤销落点）。只在「编辑态 + 两侧都有内容 + 确实有差异」
时出现。

**撤销要能落到「刚才改的那一侧」**：同步改的是另一栏，光标却还在原处，
`undo(side)` 按光标那一侧找历史会空手而归 —— 现象是「刚同步完按 Ctrl+Z 没反应」。
`undoEither()` 先试光标侧，没有历史就落到另一侧。

**窗口开在主程序所在的那一块屏上，铺满的也是那一块屏**：`work_area_of()` 用
`MonitorFromWindow(hwnd, MONITOR_DEFAULTTONEAREST)` + `GetMonitorInfoW().rcWork`
问窗口自己；建窗时问的是**主窗口**的显示器。绝不能用 `SPI_GETWORKAREA` —— 它只认
主屏，主程序在副屏时对比窗口会开在主屏，拖过去再点最大化又被打回主屏（不变量 36）。
Tauri 的 `position` / `inner_size` 收的是**逻辑像素**，所以要按那块屏的
`GetDpiForWindow` 缩放换算一次。

**编辑态一行一个可编辑单元**：`.cmp-tx` 是 `contenteditable="plaintext-only"`，
浏览器不能跨两个宿主删除，所以行首/行尾的合并（`mergeUp` / `mergeDown`）、拆分、
缩进都得自己算。按键分支的第一件事是**判选区是否折叠**——三击一行的锚点就在行首，
只看锚点会把「选中了一行」误判成「光标停在行首」（不变量 26）。

**选区跨不过「编辑宿主」，所以跨行的选区是我们自己管的**（不变量 49）：Blink 的选区
不许跨出一个 `contenteditable` 宿主 —— 拖到第二行就停住，`range` 设进去也会被掐回
第一行（实测：设 201 行，读回来只剩 17 个字）。三条路都靠同一招：**先把这一侧每行的
`contenteditable` 摘掉**（`stripSide()`），文本仍可选，但 Blink 不再拿某一行当编辑宿主。
①`Ctrl+A`（`selectAllSide()`）先关掉「只看差异」，再全选这一侧；②拖选（`dragMove()`）
在指针跨出按下的那一行时接管，之后每次移动按「按下的位置 → 指针位置」重建选区；
③Shift+点击（`currentAnchor()` + `dragBegin(e, anchor)`）从已有锚点直接扩到点击处 ——
它同样是「一次到位的拖选」，只是没有中间的移动过程；④接管/全选之后 `S.hold` 置位，
`renderRows()` 只往两端**补**行（`growRows()`）绝不重建，否则选中节点会跟着
`innerHTML` 一起被摘掉。

重建选区一律用 `sel.setBaseAndExtent(anchor, focus)`，**不要手工 `setStart`/`setEnd`**：
后者只表达「正向区间」，向上扩的那一次会把锚点悄悄换到点击处，接着按 Shift+点击
就扩不动了（表现是「再点一次，选区反而缩回一行」）。

摘掉可写属性有个必须一起做的收尾：**没有编辑上下文，浏览器既不删选中的内容也不会替你
插入字符**。所以跨行选区上的按键由 `crossSelKey()` 落进模型（`replaceSpan()`：删选区 /
替换成敲的字 / 粘贴的内容），单行内的编辑仍交给浏览器（原生撤销粒度保住）。可写在
下一次点击（`mousedown`）、切编辑态、或重建 DOM 时惰性恢复（`restoreEditables()`）。

**粘贴是这条链上唯一的例外：不能自己读剪贴板。** `navigator.clipboard.readText()` 在
WebView2 里既不 resolve 也不 reject（实测 1.2 秒后仍在等），用户看到的是「按了没反应」——
这也正是「一边改完、另一边全选后粘不进去」的根因。唯一不依赖权限的读法是 `paste`
事件里的 `clipboardData`，可没有编辑宿主浏览器根本不派发 `paste`（实测整条链只剩一个
`keydown`）。两步接上：`crossSelKey()` 先把选区记进 `pendingPaste`、`restoreEditables()`、
把光标摆到选区起点，然后**放行**这次按键（拦了就没有 `paste` 事件）；`document` 上的
`paste` 监听再 `preventDefault()` 并用 `clipboardData` 调 `replaceSpan()`。剪切同理，
只是复制那一步交给 `execCommand('copy')` —— 选区是真的，它不需要编辑宿主。

**按字典排序**（`linesort.js` + 工具栏按钮）把有内容的一侧或两侧重排，空行沉到末尾。
比较器是 `Intl.Collator('zh-CN', {numeric: true})`：中文按拼音、`a9` 在 `a10` 前——
码位序（`<` / `>`）下中文既不可读也不合直觉。排序键跟着「忽略空白 / 忽略大小写」两个
开关走，否则「diff 认为相同的两行」会被排到两处。排序会改内容，所以只读态点它会先
进编辑态；`Ctrl+Z` 一次还原两侧（`S.lastSort` 快照），只还原一侧会留下「一边排好
一边没排」的中间态。

**撤销粒度分两条路**（不变量 28）：打字走 `pushUndo`，700ms 内的连击并成一步；
换行、行首合并、缩进、删选区这些结构性编辑走 `recordUndo`，一次算一步、永远记。
两边共用一个 `S.lastSort` 开关：任何一条写入模型的路径都要先把它清掉，否则「排序后
打几个字再按 Ctrl+Z」会连排序一起退回。

**快捷键挂在 `document` 上，不挂在两块画布上**：点过排序、编辑开关之后焦点在按钮上，
画布上的监听收不到按键，现象就是「Ctrl+Z 没反应」。落哪一侧先跟光标，光标不在行里
就跟 `S.lastSide`（最近一次改动落在哪），再兜底左边。

**撤销之后光标留在原处，视口也不动**：`undo()` 先记位置再换内容。位置有两级来源 ——
实时选区（键盘那条路最准），以及 `S.lastCaret`（选区一变就记一份）。第二级不是多余的保险：
**滚动会重建行 DOM，选区跟着指向脱落的节点**，于是点工具栏按钮那一刻 `caretPos()` 什么
都拿不到，回落成「第 1 行」，屏幕一跳到底。`focusAt()` 再把行号列号夹进当前范围（文档
可能变短）；不夹的话 `lineRow.get()` 取不到行会直接 `return`，而 DOM 刚被重画过 ——
焦点就掉到 body 上，表现为「撤完键盘没反应」（不变量 50）。

**撤销/重做不主动滚视口**（`focusRowIdx` 的 `keepScroll`）：用户可能正看着文档别处，
撤一步就把画面拽走是打断。光标行不在屏幕上时，把光标夹到视口正中那一行 —— 视口不动，
但焦点必须留在正文里，掉到 body 上比光标差几行严重得多。

**脏标记是算出来的，不是攒出来的**：每侧留一份 `st.base`（打开时、存盘后各记一次），
`updateMeta()` 里逐行比字符串引用 —— `slice()` 只复制数组，没改过的行还是同一批字符串，
8MB / 5 万行也不会多一份拼好的长字符串。撤销回到原样时「未保存」必须自己消失，
否则再按一次 `Ctrl+S` 就把一模一样的字节又写一遍（不变量 29）。

**工具栏上的撤销 / 重做按钮不是第二套实现**：`doUndo()` 调的就是 `Ctrl+Z` 那条路上的
`undoSort()` + `undo()`，落哪一侧用同一个 `undoTarget()`（光标侧 → `S.lastSide` → 左边）。
可用性由 `syncHist()` 从**真实历史栈**算：两侧的 `undo`/`redo` 长度 + `S.lastSort`，只读态
一律灰。历史栈空了按钮却亮着，比没有按钮更让人上火。

**工具栏按真实溢出量降级，不按窗口宽度猜阈值**：工具栏是 `overflow: hidden` 的单行 flex，
窗口一窄，最右边的「导出报告」被静默裁掉，没有任何提示（760px 窗口实测被裁）。`fitTools()`
先去掉两级折叠，量一次 `scrollWidth > clientWidth`；溢出就加 `.tight`（按钮只留图标，靠
`title` + `aria-label` 兜底），还溢出再加 `.tighter`（勾选项也收成方框）。**为什么不用容器
查询**：同一份布局在九种语言下宽度差 100px 以上，按像素猜出来的阈值必然在某种语言下裁掉
东西；测量一次只需读一次 `scrollWidth`，比开一堆媒体查询阈值更省也更准。调用时机是
`resize`、`document.fonts.ready`（字体没就绪时量出来偏窄）、以及 `updateMeta()`（统计文字
「12 处差异」比「完全一致」长得多）。统计与当前序号本身允许收缩 + 省略号，让它们先让位
给按钮 —— 信息和动作抢地方时，动作优先。

### 6.8 文件夹对比窗口（`foldercmp.html`）

**为什么从浮层搬到独立窗口**：浮层只有一栏「状态 / 路径 / 大小」，看不出左右两侧各自
是什么，也点不进两侧目录。独立窗口里**左右各列自己那一侧的文件**，同一行就是同一对，
一行行看过去就是「谁多了、谁少了、谁改过」。

| 决定 | 理由 |
|---|---|
| 布局是**一个滚动区里的两列**（`grid-template-columns: 1fr 1fr`），不是两个各自滚动的列表 | 对齐是这扇窗存在的唯一理由；两边各滚一下就全错位了。中缝用一条 `background-size: 1px 100%` 的渐变画到底，行本身再加 `inset 0 -1px` 底边 —— 只有几行时中缝不会断在半空 |
| 行内只存**索引**（`data-i`），路径不进 `data-*` | 路径里的 `& < "` 要转义好几层，索引是唯一不会出错的做法 |
| 「相同」靠 `compare_file_pairs` 读内容 | 大小一样、时间又挨着的文件改过也判成「相同」，而「只看差异」默认勾着（不变量 46） |
| 单侧存在的格子画 -45° 淡斜纹，不是留白 | 与文本对比窗口的「这一侧没有内容」用同一套语言，不用再看图例 |
| 差异只红字，不铺底色 | 与文本对比窗口一致（不变量 43） |
| 行数超 4000 截断并明说 | 2 万行 DOM 会卡住半秒，而「能不能看全」用户得知道 |
| 点行：两边都有 → 开文本对比窗；只有一边 → 在主窗口打开（`open_in_main`） | 这个窗口只回答「差在哪儿」，改内容交给各自该在的地方 |

刻意不做：批量同步、三栏合并、目录递归下去逐层展开。需求真来了用户会去用专门的工具；
这里做深了，维护成本会和「打开看一眼」的价值迅速失衡。

## 8. 错误模型

后端**不说人话**，只说三样东西：

```rust
AppError { code: "io.read", vars: {"name": "a.md"}, detail: "系统原始报错" }
```

- `code` 是稳定错误码（`io.read` / `entry.exists` / `name.path_sep` / `recycle.failed` …），
  一旦发布就不能改语义。
- `vars` 是模板参数，供前端填空。
- `detail` 是 `std::io` / Win32 原文——**它本来就是系统按自己的语言给的，不归我们翻**。

前端 `errors.js::ERR_TEXT` 把码映射到词条键（键里带 `{detail}` `{name}` 占位符），
`localizeError()` 拼整句；`backend.js` 的 invoke 出口统一过一道，**调用方 catch 到的
一定是带人话 `message` 的 `Error`**。

三条纪律：

- **冒号不拼接**：`前缀 + '：' + 细节` 这种拼法每种语言都错（中日全角、法语冒号前有空格）。
  整句（含冒号）做成一条词条。
- **防二次翻译**：`localizeError` 产出的 `Error` 带 `message` 无 `code`，天然不会再被翻一遍。
- **没收录的码要露出来**：宁可显示 `[io.foo] boom`，也不要静默吞掉。
  `test/run-i18n.mjs` 做双向对账：`ERR_TEXT` 的每条模板都在词条表里；Rust 里出现的
  每个 `AppError::code` 前端都有模板。

### 8.1 为什么不是「让后端回中文，前端翻译」

i18n 第一版就是那么做的：Rust 回中文句子、前端用 `ttBackend()` 拿字符串匹配翻译。
两个毛病绕不过去：① **字符串匹配天然脆弱**——后端补个标点、改个措辞，前端整条失配，
静默退回中文，用户不吭声你就发现不了；② **带变量的句子永远匹配不上**——
`「a.md」已经存在` 里的 `a.md` 是运行时才知道的，想匹配就得连变量一起匹配，等于没匹配。
所以改成「后端说发生了什么（语义），前端说怎么说（语言）」，也就是上面那套
`code` / `vars` / `detail`。

三个坑已在上面（冒号别拼接、防二次翻译、没收录的码要露出来）。补一个端到端验证法：
真机 CDP 里 `import('/js/backend.js')`，故意触发四类失败（读不存在的文件 / 读二进制 /
名字带路径分隔符 / 同名条目），检查 `code`、参数填充、`detail` 透传；再 `setLang('en')`
跑一遍确认句子换语言而 `detail` 不变。

## 9. i18n

- **键 = 简体中文原文**（gettext 思路），代码里 `tt('保存')` 一眼知道上下文。
- 词条源 `i18n-dict-src.js` 是 **7 列**（英/日/韩/法/德/西/葡），**繁体不手写**，
  由 `tools/build-i18n-dict.py` 用 OpenCC `s2twp` 生成 → 产物 `i18n-dict.js` **只读**。
- 静态 HTML 用 `data-i18n` / `-title` / `-ph` / `-aria`，`applyDom()` 统一刷。
- **JS 会赋值 `textContent` 的节点绝不能挂 `data-i18n`**（对话框标题、草稿状态、文件名…），
  否则切语言那一刻会被刷回静态词。
- 带 `tt()` 的**顶层常量必须写成函数**（`const modeMeta = () => ({...})`），否则在模块
  加载那一刻就求值了，切语言后不生效。
- 取词函数叫 `tt` 不叫 `t`——`t` 是「当前标签」，会被局部变量遮住。
- 后端错误码的词条要显式登记进词条表（`ERR_TEXT` 里的键同样受覆盖率检查）。

新增文案后的固定动作：`node test/run-i18n.mjs`（查覆盖率、列数、占位符）。

### 9.1 七个坑的经过与判据

上面是结论，这里是每条结论背后的现象与判据 —— 改 i18n 相关代码前读一遍能省一轮返工。

**1. 键用「简体中文原文」，不用 `menu.save`。**
gettext 那套做法的好处是永远不会出现「键叫 save、值写着删除」的漂移，翻词条时
直接在代码里看得懂上下文；代价是原文改动要同步词条表。所以必须有自动化兜底：
`test/run-i18n.mjs` 会把「源码用了但表里没有」的键全部列出来，改文案忘同步会红。

**2. 顶层常量会把文案定死。**
`const MODE_META = { ... label: tt('预览') }` 在模块加载那一刻就求值了，切语言后
工具栏还是旧语言。凡是带 `tt()` 的顶层常量都要改成函数（`const modeMeta = () => ({...})`），
调用点补 `()`。这一轮改了 6 个：modeMeta / newTypes / menuTree / fileFilters / list /
blockKinds / blockInserts。

**3. 取词函数不能叫 `t`。**
`app.js` 里 `t` 是「当前标签」，几百处 `t.path`、`closeTab(t.id)`。叫 `t` 会被局部变量
遮住，而且 `t('关闭')` 读起来像「把标签对象当函数调用」。用 `tt`。

**4. `data-i18n` 只能挂在「文字由静态 HTML 决定」的节点上。**
对话框标题（`#dlgTitle`）、草稿状态（`#stDraft`）、文件夹路径、合并向导里的文件名、
预览标题 —— 这些是 JS 运行时写的，挂上 `data-i18n` 后 `applyDom()` 会在切语言那一刻
把它们改回静态词（现象：设置面板里的标题从「Einstellungen」变回「Hinweis」）。
判断标准很简单：**JS 里有没有对它赋值 textContent**，有就不挂。

**5. 换语言时菜单要 `update()`，不要重建。**
`createAppMenu()` 会往 `document` 上挂「点外面就关」的监听，重建等于叠一层，
多点几次菜单开始自己闪。appmenu.js 因此加了 `update(next)`，只换顶级标签文字。

**6. 繁体不手写，走 OpenCC `s2twp`。**
`文件→檔案`、`设置→設定`、`保存→儲存`、`字符→字元` 这些是短语级转换，手写五百条
必然前后不一致。源表只维护 7 列（en/ja/ko/fr/de/es/pt），繁体由
`tools/build-i18n-dict.py` 生成 —— 产物 `src/js/i18n-dict.js` 是只读的，
改词条请改 `i18n-dict-src.js` 再跑脚本。

**7. 后端的错误文案不带语言。**
Rust 侧 65 条错误信息是中文，后端不认识界面语言。真正干净的做法是返回错误码，
但那要改遍所有命令和调用点。折中做法是在 `backend.js` 的统一出口过一道
`ttBackend()`：整条命中词条就整条翻；「前缀：系统细节」只翻前缀 —— 细节那半是
Windows 自己给的（本来就跟随系统语言），翻了反而错。

**顺带一条工程纪律**：这一轮的 368 处自动包装是脚本做的（`tools/i18n-wrap.py`，
状态机跳过注释/模板字面量/对象键），但**模板字面量里的 HTML 必须手工拆**——
脚本按行匹配会把 `<button title="关闭">` 的属性也包进 `tt()`，直接炸 DOM。
自动化的边界要认得清：机械替换交给脚本，判断结构交给人。

| 合成层 | ≤ 6 层 | 4 层，其中 3 层全屏（1.05M 像素） | `about:gpu` / CDP `LayerTree` |
| 导出 PDF | < 3s / 页级文档 | 1.7s，68KB，`%PDF-1.4`，1 页 | 真机探针计时 |
| 大文档 | 10MB 可编辑 | 视口模式实测可用 | 生成 8 万块夹具 |

跨平台指标另算——三个 WebView 内核不同，**这些数字必须在目标平台上重测**，
不能直接沿用（见《实现规格》§10.6）。

**内存有两套口径，别混用：**

- **「现在占多少」看 `WorkingSetPrivate`** —— 任务管理器那一列，用户感知的就是它；
- **「这次改动有没有真省」看 `PrivateMemorySize64`（Commit）** —— 工作集可以被主动 trim 到
  接近 0 而 Commit 一 MB 不变。WebView2 的 `SetMemoryUsageTargetLevel(Low)` 就是这么干的
  （工作集 569 → 201 MB，Commit 354.6 → 354.9 MB），对常驻读缓冲区的编辑器是**负收益**，
  别被数字骗。判别方法只有一条：**改动前后都看 Commit。**

**GPU 那两行强依赖屏幕，不是代码指标**：合成纹理 ∝ 窗口像素面积，实测约 28～38 MB / Mpx
（同一台机只改窗口尺寸：2.22 Mpx 比 0.27 Mpx 多 45 MB，见 `docs/proposals/native-shell.md` §1.7）。
4K@200% 上 GPU 进程到 300 MB 属正常，**不是性能回归**；同一份代码换到 1080p 显示器就回落到 60 MB 量级。

## 13. 已知设计债

按「什么时候会咬人」排序：

1. **快捷键文案写死 `Ctrl`**（约 130 处）。匹配逻辑是 `ctrlKey || metaKey`，所以 macOS 上
   **能用但显示错**。移植前应统一成 `mod+` 存储 + 按平台渲染。
2. **`app.run(|_, _| {})` 是空回调**。macOS 必须在这里接文件打开事件，否则「双击 md
   打开」在 mac 上完全不通。
3. **菜单在 macOS 上会重复**：Tauri 默认会给 macOS 建一套系统菜单栏（App/File/Edit/…），
   而应用又自绘了一份 —— 窗口里一套、屏幕顶上一套。移植时要么改用原生菜单承接所有命令，
   要么 `enableMacosDefaultMenu: false` 后自己补最小 App 菜单（⌘Q / ⌘H 仍需归属）。
4. **打印依赖 `window.open` + `win.print()`**。Windows（WebView2）可行，macOS（WKWebView）
   很可能不行，Linux（WebKitGTK）待实测。需要一层抽象。
5. **`delete_file_impl` 的非 Windows 分支是永久删除**，与产品语义（进回收站）不符。
6. **构建配置写死 `bundle.targets: ["nsis"]`**，在 mac / Linux 上构建会直接失败。
7. **测试工具链分两层，一半是 Windows 专属**：离线套件（CDP + headless Chrome）可移植；
   真机套件（UIA + SendInput + PrintWindow 截图）是 Windows 专用 PowerShell，需要重写。
8. **无边框窗口的「最大化」是自己算矩形**：`tao` 的 `maximize()` 在无边框窗口上不可用
   （标志位先写后跳过），现在靠「窗口所在显示器的工作区」+ `SetWindowPos` 手动铺满，
   还要按 DWM 隐形边框外扩。这套绕法只在 Windows 上验证过，mac / Linux 应换成
   各自的正规做法（macOS 的 `toPhysical`/`setFrame`、Linux 的 GTK 最大化）。
9. **i18n 词条里含着快捷键文案**（`i18n-dict-src.js` 15 条），改了键位要连带改词条。

## 14. Tauri / Windows 窗口：这一轮最深的水

这一节全是「API 不按文档说的做」时踩出来的。要动窗口相关的代码，先看这里。

**1. tao 的 maximize 在无边框窗口上是坏的（最大的一个坑）。**
`decorations:false` 的窗口，tao 的 `WindowState` 在窗口还没 VISIBLE 时就把
MAXIMIZED 标志位写成 true，却跳过 `ShowWindow(SW_MAXIMIZE)`；此后任何
`maximize()` 都因「标志位没变化」被直接忽略。实测四种时序
（builder `maximized(true)` / 建完立刻 / `on_page_load` / 前端调用）全部无效。
**结论：别跟窗口状态较劲，直接算矩形。** 用 `SPI_GETWORKAREA` 拿工作区 +
`SetWindowPos` 摆位，注意还要按 DWM 隐形边框外扩 8~9px，可见区才正好贴边。

**2. 建窗口的命令必须是 `async fn`（血泪第二课）。**
症状极具迷惑性：窗口壳子、标题、尺寸全对，**页面永远不加载，整扇窗子纯白**。
根因：Tauri 的同步命令在主线程上执行，而 `WebviewWindowBuilder::build()` 要等
WebView2 回调 —— 主线程被自己占着，`build()` 卡到超时。命令行参数路径走
`setup()`、本来就在主线程外，所以同一份代码一条路好一条路坏。
**教训：凡是「建窗口 / 弹对话框」的命令，一律 async。**

**3. 没有日志时排查窗口问题，别猜，往流程里埋点。**
把关键节点（spawn start / building / page started / fill ok）追加到
`%TEMP%` 下的日志文件，一次真机运行就能看出卡在哪一步。注意**不能用窗口标题
输出诊断** —— 测试工具按标题找 HWND，改标题会让工具失明。

**4. 多窗口的权限要单独登记。**
第二个窗口必须在 `capabilities/default.json` 的 `windows` 数组里出现，否则
所有 `core:window:*` 调用静默失败（不报错，只是不生效）。前端窗口操作大面积
失效时先查这里。

**5. 跨窗口传参别走 URL query。**
中文文件名经过双重编码后跟磁盘路径对不上。改成 Rust 侧放一个
`Mutex<Option<T>>` 状态 + 前端 `take_xxx` 命令取一次，简单可靠。
窗口已开时复用：`unminimize + show + set_focus` 再 `emit` 推新数据。

**6. WebView2 的参数黑名单。**
`--disable-gpu` / `--in-process-gpu` / `--enable-low-end-device-mode` 它一概
不吃，参数层压不动内存。真正需要的是 `--disable-gpu-sandbox`（否则 GPU 沙箱
崩溃）。内存口径用 `WorkingSetPrivate`，`PrivateMemorySize64` 虚高 60MB。

## 15. 工程纪律：五十九条踩出来的规矩

按**发生的顺序**排，不是按主题 —— 相邻几条往往出自同一轮排查，连着读才看得见因果。
要按主题找，用 §19 的索引。每条都对应一个真机抓到的 bug 或一次返工，不是「最佳实践」式的空话。
§15.1 / §15.2 的 1～59 是经验条目编号；§15.3 / §15.4 标题里的 75～79 指 §10 的不变量编号，
两套编号不是一回事。

### 15.1 编辑器与选区（1～20）

**1. contentEditable 的光标是易碎品。**
任何「重建 DOM」的操作都会丢光标，所以规矩是：打字路径只动光标所在块 ±1；
需要整块替换时（如标题降级）先记光标偏移再 `restoreCaret`；`contentEditable=false`
的子元素（如 `###` 哈希把手）绝不混进 `.w-text`，且所有白名单 sweep 都要带上它。

**2. 「编辑态」的脏标记必须覆盖所有写路径。**
本轮真机抓到的丢数据 bug：打字走 `flush()` 会标脏，但 Enter / Backspace 并行 /
Tab 这类结构性编辑走 `applyEdit()`，忘了标脏 → `Ctrl+S` 判定「无改动」直接丢。
**教训：每加一条写路径，先问「脏标记在哪」，写测试时每条路径都要有落盘断言。**

**3. 虚拟滚动三个关键件缺一不可。**
固定行高（CSS 变量，字号缩放同步重算）、可视区 ±6 行的窗口渲染、
`top = i * ROW_H` 的绝对定位。另一个容易踩的：行容器和「当前块」覆盖层必须
分开两个 div —— 高亮写在行上会被逐行画成表格格子。

**4. 行尾与快照校验的「假失败」。**
`core.autocrlf=true` 时磁盘文件是 CRLF，脚本生成的字符串是 LF，内容一致也判
不一致。所有「自己生成的字符串 vs 磁盘文件」的比较，读取时统一
`.replace(/\r\n/g,'\n')`。**症状识别：校验失败但 `git diff` 该文件为空。**

**5. diff / 比较类功能的边界永远比主体难写。**
空行算不算块、忽略空白后行号怎么对齐、「仅左」「仅右」「修改」三态与行内
mark 的组合、块区间从起点扫到第一个 `same` 为止（不能用「下一块起点 -1」）——
这些边界都要在夹具里有一行对应的用例。

**6. 「看起来像」的启发式，最后一定会被用户当成 bug。**
大纲面板最初对纯文本用「像标题的行」规则（`1.` `2.` `3.` 开头、`====`、`【】`），
结果一份带序号的清单或日志就是「每行都是大纲」，而且统统压成同一级；`====`
自己还成了空标题。用户第一句话就是「txt 每行都当做大纲了吧」。
正确做法是先问「这个格式里**什么是结构**」，再只认那些标记：`#`、Setext 下划线、
`【章节】`、`第X章/节/条`、多级编号（点号段数就是层级）。单级编号更微妙 ——
`1.` 既可能是章节也可能是一张清单，用「空行断组后只剩它一条」区分。
把「猜」换成「认」，规则反而更短、更好解释，空态也能说清「缺什么」而不是
含混的「没有可提取的结构」。

**7. 一行一个 `contenteditable`，选区就出不了这一行。**
对比窗口每一行都是独立的编辑宿主（这样才能按行映射模型、按行做行内 diff）。
代价是 Blink 的两条硬规矩：选区**不许跨出编辑宿主**，以及「全选」只认得当时
DOM 里摆着的那几行。用户看到的就是「Ctrl+A 只选中一屏」「按住往下拖，选区
停在第一行」。
踩过的四条路，只有最后一条成立：
①`active.blur()` / `sel.collapse(body,0)` / `body.focus()` 想让浏览器忘掉宿主 ——
全无效（读回来仍是那一行的 17 个字）；②把 `contenteditable` 摘掉再设
`range` —— 成立，但**打字、删除、粘贴全变成「没反应」**：没有编辑上下文，
浏览器连 `beforeinput` 都不发；③拖到一半再摘 —— 原生拖动当场死掉，选区归零；
④**摘掉之后整段接管**：拖选由 `mousemove` 自己按 `caretRangeFromPoint` 重建，
按键由 `keydown` 落到模型（`replaceSpan`），单行内的编辑照旧交回浏览器。
关键是别只做一半：只摘属性不接管按键，看起来能选能复制，实际一敲字就露馅。

**8. 拖选途中任何一次 `innerHTML` 重建，选区都会凭空消失。**
虚拟滚动每次滚动都想重建可见行（`renderRows`）。拖动期间必须改成
「只往两端 `insertAdjacentHTML` 补行，已有节点一个不动」，否则滚一格，
选中节点连同选区一起被摘掉 —— 鼠标还按着，高亮没了。补行的时机也不能挂在
画布的 `mousemove` 上：指针到了边缘就落在滚动条上，画布根本收不到事件
（这也是「拖到底边什么都不会发生」的真正原因），要挂到 `document`。

**9. 按住文字往下拖，浏览器可能当成「拖放」而不是「选字」。**
文本一旦被选中，Blink 会起一个 OS 级拖动会话：之后的 `mousemove` 全被它吞掉
（`moves` 计数直接停住），松手还可能把那段文字**挪**到别处 —— 对编辑器就是
一次静默的数据破坏。一行 `dragstart → preventDefault()` 解决。
症状识别：拖选开始时选区正常，指针再动就再也不更新，`drag.y` 停在按下那一刻。

**10. 滚动会重建行 DOM，选区跟着作废 —— 别在那一刻读 `getSelection()`。**
撤销「跳回顶部」这个 bug 就是这么来的：`undo()` 本来就会先记光标位置，键盘按
Ctrl+Z 一切正常；但用户点**工具栏按钮**时会先滚一下，滚动让 `renderRows()` 重建
了整屏 `innerHTML`，原来的文本节点被摘掉，`getSelection().anchorNode` 指向一个
已经脱离文档的节点，`closest('.cmp-tx')` 返回 null → 位置回落成「第 1 行」→
`focusAt(1, 0)` 把屏幕滚到顶部。
两个教训：
- **靠一份 `lastCaret`（`selectionchange` 里记）兜底**，不要指望「点按钮那一刻
  的选区还在」；
- 「不滚动」不能只靠不设 `scrollTop`：`element.focus()` 自己就会把目标滚进视野，
  必须 `focus({ preventScroll: true })`。而光标行若不在屏幕内（虚拟滚动只摆一屏），
  焦点又会掉到 body 上、键盘当场失灵 —— 这时把光标**夹到视口中央那一行**，
  视口不动、焦点还在正文里，两头都保住。

**11. 「固定行高」是虚拟滚动的隐形地基，一旦要支持换行，地基得先换掉。**
对比窗口原来满篇都是 `top = i * ROW_H`（`ROW_H` = 20px，字号一改就重算一次）。
加「自动换行」时第一反应是「在渲染时读一下 `.offsetHeight` 不就行了」——
但滚动路径每帧都要算行位，逐帧布局读一次就是几千次强制重排，5 万行文档直接卡死；
而且虚拟滚动只摆一屏 DOM，屏幕外的行根本没有元素可量。
正确的换法是**把行位从算术关系升级成前缀和**：`recompute()` 时一次算好每行的显示宽度
（`S.uL` / `S.uR`，单位是半角单元，全角算 2），`layout()` 用「可用宽 ÷ 字符宽」得到列数，
向上取整就是折几行，累加进 `S.y`（每行顶边）与 `S.hh`（每行高）。
之后 `rowTop()` / `rowH()` / `rowAtY()`（`S.y` 上二分）/ `totalHeight()` 四个函数
把原来散落各处的 `i * ROW_H` 全部收口 —— 换行时它们不等高，不换行时全部等于 `ROW_H`，
行为逐像素退回旧实现，两种模式共用同一条代码路径。
**判断标准：任何一个「第 i 行在哪 / 多高」的除法或乘法都是隐患，全部换成查这四个函数。**
（不改的后果很具体：行号跳了位置没跳，点哪行都不是那行、滚动条到不了文末。）

**12. 「算出来的布局」比「量出来的布局」稳，前提是把折行规则钉死。**
上面那套前缀和只有在「折几行是可预测的」时候才成立。默认的
`overflow-wrap: break-word` 不行 —— 它是「单词放不下才折」，一个长英文单词会自己占一行，
列数算不准。要的是**硬折**：`word-break: break-all` + `overflow-wrap: anywhere` +
`line-break: anywhere`（最后一条管中文标点），配合等宽字体，每行恰好放
`可用宽 ÷ CHAR_W` 个字符，一个不差。中文全角占两个单元，所以宽度一律按半角单元记。
代价是英文单词会在词中间断开（对比工具里这是可接受的，看到断在哪比看到「这一行没对齐」重要），
换来的是滚动、点击定位、预览条比例三处都不用测量。

**13. `click` 的 `target` 不是「你点的那个元素」，是「按下点和松开点的最近公共祖先」。**
这个规范细节平时看不出来（点一下，两边是同一个元素，target 就是它），
只有当用户**拖选一段跨行的文字**时才现形：mousedown 打在第 1 行、mouseup 打在第 4 行，
浏览器把 `click` 派发给两者最近的公共祖先 —— 对「每行一个块、块都在同一个编辑宿主里」
的结构，那就是编辑区的根节点。代码里 `if (e.target === root)` 本来写的是「用户点了正文
空白处」，于是这次拖选被当成点空白：在文末补一个空段落、把光标搬过去。
用户看到的是「明明选中了三行，一松手就没了」，而读代码一切正常 —— 真机打点才看到
`pointerup` 之后紧跟一条 `selectionchange → len 0`，栈顶是 `handleClick → placeCaretStart`。
两条闸都要有：①选区非空就当「这是一次拖选的收尾」，直接返回；②真要按空白处理时，
用 `elementFromPoint(clientX, clientY)` 问一下这一点命中谁，命中任何块就按「点在字上」。
只做①的话，「从空白拖到空白」（松手时选区已折叠）仍会被误判；只做②的话，
多一层坐标判定能挡住，但把「刚选完就动 DOM」这种危险动作留在了主路径上。

**14. 「粘贴」不是一个动作，是一组按落点分派的行为。**
同一个 `paste` 事件，落在段落上要按 Markdown 解析成块（保留标题/列表结构），
落在表格格里只能取第一行（否则表格结构被塞进一个格），落在**代码块里必须原文照抄** ——
代码块内部没有「行」的概念，一个 `.w-code` 里全是文本节点和 `<br>`，任何解析都会毁了它。
旧实现只分了「单元格 / 单行 / 多行」三档，代码块被归到「多行」那档，于是：
空代码块被 `replaceWith` 整块换掉（粘一段 JSON，代码块凭空消失），
非空块则把解析出来的段落插到块**外面**（粘了，但内容跑到块下方）。
同一档漏掉的还有**容器块**：列表项和引用行也是「多行」的一种落点，按段落插在块后面
就等于把列表拦腰截断 —— 实测 `- 第二项` 末尾粘三行，结果是 `- 第二项` + 三个普通段落、
每段还隔一个空行。容器要的是「续行」：每一行等于按一次回车（li 续同 kind 同缩进、
bq 续同缩进并接住提示块颜色），整段只 flush 一次。
诊断很便宜 —— 打印 `blocks()` 的 `data-type` 列表就能看出块数从 3 变成 7。
修的时候有一个反直觉的细节：换行要落成 `<br>`，**不能往文本节点里塞 `'\n'`**
（Chromium 下一次输入会把行尾那个吃掉，光标漂到换行前面），
末尾还要垫一个零宽空格，否则「以换行结尾」的粘贴会把光标留在 `<br>` 上，接着打字跑回上一行。
**判断标准：粘贴的实现如果只有一条路径，它一定在某个宿主上是错的。**

**15. 切换一个布局类设置，要保住用户「正看着的那一行」，不是保住 `scrollTop`。**
换行开关一按，同样的 `scrollTop` 指向的是另一行：2000 行文档停在第 21 行（`scrollTop` 1600，
行高 80），关掉换行后 1600 落在第 80 行，用户看到屏幕「跳走了」。
正确做法是切换前后都换算成**行**：`keep = rowAtY(sc.scrollTop)` 记下行位，重排后
`sc.scrollTop = rowTop(keep)`。这条对「字号缩放」「宽度变化」「折叠开关」全都一样 ——
凡是会改变行高的动作，都不能直接沿用像素偏移。
同理，编辑器那边切换行要用 CodeMirror 的 `Compartment` 热替换
`EditorView.lineWrapping`，**不要重建 `EditorState`**：重建等于把撤销历史和选区一起扔掉，
用户改了个显示方式，`Ctrl+Z` 却撤不回去了。

**16. 给光标「自动补一个落点」之前，先看看有没有现成的；带范围的块，入口和出口要成对设计。**
表格最后一格按 ↓ 出去、在下面继续写 —— 这是对的。问题是实现只有一句
`insertEmptyAfter(block)`：不管下面有没有东西，先插一个空段落再说。于是
「表格下面本来就空着一行」时按一下又冒一行，文档末尾越按越长（空段落不进 Markdown，
但屏幕上真真切切多一行，而且光标在一次次的空行里往下沉）。

改法是把落点按优先级排出来，新建只能是最后一档：
**块后已有的空段落 → 复用；没有 → 只记「块后待插入」，等用户真要写入时才开一行**。
凡是「给光标找地方站」的代码都该按这个顺序写 —— 用户已经摆好的结构，不要用新节点去顶，
更不要在用户只是移动光标时就替他把行建好。

后来这条又补了一次：曾经为了「方向键不许改文档」，把「块后是正文」也并进第一档，
光标直接落到后文开头。表面省下一次编辑，实测出块后直接打字写成 `新后一段`、
按回车插出了空行却仍把光标留在后文里 —— **落脚点不属于块后，用户接下来两个最直觉的
动作都会落到别人的内容上**。当时的结论是「宁可让方向键插一个真空行」，于是 1.2.6
真的在出块时插行；用户试用后明确判定「擅自新增一行不符预期」。

最终解法不是二选一，而是把「落点」和「插入」拆成两步：**方向键零改动** —— 块后已有空行
就停进去，没有就把光标送到下一块开头（文末保持原位），只记一个一次性的 `gapAfter`；
**用户按下回车 / 打字 / 粘贴时**才在两块之间插真段落并 `flush()`，`handleKey` 在
`handleEnter` 之前把这一下回车接管过来。这样标签不会因移动光标变脏，下一块哪怕是表格 /
代码块，回车也仍然是「在块后加一个空行」。「临时占位块」会在窗口化重铺时消失，
把 Range 悬在子节点间隙假装有一行则会在 WebView2 里被吞掉，都不是正路。

还有第三个坑：**末尾判据要按「眼睛能点到哪」算，不是按 `textContent.length`**。
除了垫脚的零宽空格，代码块 / 公式块正文末尾那个 `\n` 在 `pre-wrap` 下不生成可点击的行，
浏览器把行尾点击映射到它前面。旧判据把它算进 `end`，于是「末尾留过一次回车」的代码块
永远被判成「不在末尾」，`handleArrow` 不接管、浏览器原生把光标甩进下一块 —— 用户报的是
「代码块后面有内容时出不了块，别的块都行」，其实与后面接什么块无关，只与代码块自身
末尾有没有裸 `\n` 有关（表格 / 引用 / 列表的正文是 `<br>` 或单元格边界，没有裸 `\n`）。
只忽略末尾这一个换行：再往前的 `\n` 都对应看得见的空行，全剥会让用户在倒数第二行
就被弹出去。

同一条还牵出第二个坑：**出口本来只做了 ↓**。`handleKey` 里只派发 `ArrowUp/ArrowDown`，
`→` 压根到不了 `handleArrow`，所以表格右下角按 → 光标在格子里原地打转，想出去只能动鼠标。
「带边界的块」内部没有「更靠后的位置」，两个方向走到头的语义都是出块 —— 派发和判断要一起
补齐，只补一半等于没补（而且看起来像「这个键就是没反应」，连带着让人以为键盘坏了）。

**「带边界」是按光标能不能继续往后走定义的，不是按外观。** 第一版只认表格和代码块，漏了
引用、提示块和列表 —— 它们的边框一眼就能看出来，但**一行就是一个 `.w-block`**，所以判断要
落到「这是不是这一组的最后一行」：引用看 `data-bq-tail`（组内还有下一行就有），列表看下一个
兄弟还是不是 `li`。组内还有下一行时**必须让浏览器自己走**，接管过头会跳过折行、把光标直接
扔到下一行去 —— 那比不管更糟。反过来说，普通段落不该进这个名单：它本身就是出口的落点，
末尾再长行只会让文档越按越长。

**17. 「读剪贴板」不要自己调异步 API —— 等 `paste` 事件，那是唯一不要权限的路。**
对比窗口的「`Ctrl+A` → `Ctrl+V`」有时没反应，而且只在**跨行选区**上出现。代码看着没毛病：
`navigator.clipboard.readText().then(replaceSpan).catch(() => {})`。真机一测就露馅 ——
`readText()` 在 WebView2 里**既不 resolve 也不 reject**，1.2 秒过去 promise 还挂着，
`catch` 永远不跑，用户看到的就是「按了没反应」（而 `catch` 里那句空语句让这个失败
连日志都没有）。

`paste` 事件里的 `clipboardData` 是浏览器从系统剪贴板直接读的，不要任何权限。代价是
**必须先有编辑上下文**：跨行选区把 `contenteditable` 摘掉之后，整条链只剩一个
`keydown`（实测），所以顺序要反过来 ——

1. `keydown` 里记下要替换的选区，把这一侧恢复可写、光标摆到选区起点；
2. **不要 `preventDefault()`**，放行这次按键 —— 拦了就没有 `paste` 事件了；
3. `paste` 监听里 `preventDefault()`，拿 `clipboardData.getData('text/plain')` 落到模型。

顺带一条同源的：`navigator.clipboard.writeText` 在没有用户激活时同样 `NotAllowedError`，
所以「剪切」也别用它 —— 选区是真的，`document.execCommand('copy')` 就够。

**18. 「扩选」的锚点必须留在按下那一端 —— `setStart`/`setEnd` 表达不了反向区间。**
Shift+点击要「从原来那一点扩到这儿」。重建选区时手工写
`if (a 在 b 之前) setStart(a), setEnd(b); else setStart(b), setEnd(a);`，看起来只是
把方向捋顺，实际把**锚点换到了点击处**：往回（向上）扩一次之后，再 Shift+点击就是
从新锚点出发，选区原地打转、扩不动。

正确做法是 `sel.setBaseAndExtent(anchorNode, anchorOffset, focusNode, focusOffset)`：
base 是锚点、extent 是焦点，反着放也合法。锚点不动，连续 Shift+点击才和浏览器原生
行为一致。另一个坑：读出锚点要放在**恢复 contenteditable 之前** —— 一恢复可写，
Blink 立刻把跨行选区掐回一行，锚点跟着没了（表现为「Shift+点击一下，选区直接消失」）。

**19. 「兜底」不等于「默认」—— 两条路径做同一件事就得共用一条判据。**
块尾那片空白是给「带边界的块后面光标出不去」留的兜底：代码块、表格垫底时点一下，
在下面开个空段落当落脚点。后来它被写成 `if (点在最后一块下方) insertEmptyAfter(...)` ——
判据从「这块能不能落脚」退化成「点得够不够靠下」，于是**在文末空白随便点几下，文档就多几行**
（空段落不进 Markdown，屏幕上却真真切切多出来）。用户对兜底的预期是「点一下把光标送回文末」，
不是「每点一下加一行」。

修法是把判据抽成一个函数（`needsLineBelow()`），鼠标点击和块尾指示线**共用它**：末块是段落 /
标题 / 引用末行 / 列表末项时 `placeCaretEnd()` 就够，只有块内没有可写尾位的那几种才补一行；
补出来的空段落立刻成为新的末块，所以再点几次也只多那一行。指示线尤其不能自己另判一套 ——
它存在的全部意义就是预告「点这里会多一行」，行为收窄了它还照旧亮，就是在骗人。

**20. 「只上色、不动结构」在 contenteditable 里只有一条正路：CSS Custom Highlight API。**
代码块要高亮，最直觉的做法是把 `highlight()` 的输出（`<span class="tok-key">`）塞进块里。
在 contenteditable 里这一步会同时毁掉三样东西：光标（Blink 把光标从 span 里踢出来，下一次
输入就落在别的字上）、撤销记录（按块存，子节点一变就不是同一个块了）、序列化（多处逻辑写死了
「子节点只能是 text 或 br」）。

`CSS.highlights` 给的正是缺的那块：给**文本区间**上色，DOM 一个节点都不动。代价是得自己把
「源码偏移」换算成 Range —— 这里的两个陷阱都不显而易见：`<br>` 在源码里是换行、占一位却没有
文本节点；编辑器垫的零宽空格在 DOM 里是一位、源码里根本没有。必须逐字符记位置，拿
`textContent.length` 硬算会整体错位，症状是「颜色涂在别的字上」—— 看起来像高亮器坏了，
其实是映射坏了。

顺带记一个更阴的坑：**`Ctrl+A` 别指望浏览器的 SelectAll。** 在「已经选中某个内联块」之后再
执行一次全选，WebView2 会把选区整个吃掉 —— `document.execCommand('selectAll')` 返回 `true`，
选区却是空的（anchor 从 `SPAN` 掉回 `#text`、collapsed）。所以「代码块里第一下选本块、第二下
选全篇」两步都得自己算：第一下 `setStart(firstText, 0)` / `setEnd(lastText, len)`（边界落在
**文本节点**上，落在元素上同样会触发上面那个塌缩），第二下自己从首块铺到末块。

### 15.2 对比窗口、撤销、测试、着色、高亮语义（21～59）

以下是后续几轮追加的，编号接在上面之后。

**21. 退化分支最危险的不是慢，而是"看起来正常"。**
`diff.js` 里有一条规模保护：`n*m > 4M` 时不再跑 LCS，改成"这行在对方文件里
存不存在"。它还给不匹配的行编了个 `b = -1` 冒充"相同"。后果是：两个 2000 行
的文件一比较，右栏**整页空白**，所有新增堆在文末 —— 界面上不报错、不转圈，
就是安静地给出错误答案。这类问题极难被用户描述清楚（"对比好像没生效"），
也极难被测试发现（没有断言过 `same` 行的行号有效性）。

三条规则：
- 退化路径的输出必须**和正常路径同一语义**。算不动就说"这段整段替换"，
  不要伪造"相同"。
- 退化路径要有**自己的断言**。现在 `run-units` 里有十条守它：行号在范围内、
  没有 `undefined` 文本、修改成对、无关文件不出现 `same`。
- 阈值附近的规模要**主动测**。4M 单元格对应约 2000×2000 行 —— 这不是极端
  用例，是"两份会议纪要"就会踩到的日常规模。

改进后的做法：段小就精确 LCS；段大到放不下 DP 表，就先找"两侧都只出现一次
的行"当锚点，用最长递增子序列保证顺序一致，再逐段递归。2000 行级文件 11ms，
3000×3000 全无关文件 12ms，都不会退回假结果。

---

**22. "部分成功"比"整体失败"危险得多。**
对比窗口打开一对文件时，如果左侧文件因为超限没读进来，而右侧读成功了，
旧实现会**保留左侧上一轮的内容**。界面上一切正常：有行号、有差异、有统计，
只是左栏是新文件的"前世"。用户没有任何线索知道这个结论是拿两个不相干的
文件比出来的。

规则：**一次操作要么完整生效，要么把受影响的输入清空**。不能只更新成功的
那一半。失败的一侧要显式回到「未选择」，并用一条常驻提示说明原因——toast
会消失，消失之后用户只会记得"它比较过了"。

同理，状态跨操作残留也要防：对比窗口是复用的，差异清单的排序/筛选会留在
上一次的状态里。产品上这是合理的（用户偏好），但任何断言都得先归零，否则
"点了位置列顺序没变"可能只是因为它本来就在按位置降序。

**23. 定位控件要和被定位的内容共用一套坐标。**
预览条原先按自身高度映射行位置，可它和正文区顶上都还有一条 26px 的栏头——
底部 26px 的行永远画不到，点击也差一截。短文档更糟：内容只有 100px 高，
映射却按 800px 的容器算，视口框比容器本身还高。
（那条栏头后来删了：名字与顶部槽位重复。几何约束不因此松动——只要还有任何
一条固定行压在滚动区上面，`margin-top` 这种手算偏移就会再次对不上。）

改法是把几何收进一个 `rulerGeom()`：轨道起点取滚动区的 `getBoundingClientRect().top`，
高度取 `min(可视高度, 内容高度)`，绘制、点击、悬停提示全用它。预览条 DOM 的高度
也跟着设成内容高度，短文档时它就是一小截——**控件本身的尺寸也要服从内容**，
不是把容器拉满再往里画。

性能上还有一个反例值得记：`drawRuler()` 原本每帧扫一遍所有行去拼差异段，
5 万行时光这一项就吃掉十几毫秒。改成用 `recompute()` 已经折好的差异块列表后，
每帧降到 3.6ms。**滚动路径里不要出现 O(总行数) 的循环**，哪怕它看起来只是
"扫一遍数组"。

**24. 测试需要的能力，先找平台开关，别改产品配置。**

真机探针要 CDP 端口，一直是「临时改 `tauri.conf.json` 的 `additionalBrowserArgs`
和 `lib.rs::spawn_compare_window` 两处 → 全量重编 → 跑 → 撤掉再重编」。
前端是编译期内嵌的，所以一轮探针两次 `cargo build`，50~100s 一次，还外带
「忘了撤销就把调试端口提交了」的风险。

其实 WebView2 认 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS`，而且是**进程级**的：
主窗口和随后打开的对比窗口都会带上。于是改成启动时注入，零改配置、零重编。
一般化的教训是——**为了测试去改产品代码，通常说明还没找对平台的运行时可调项**。
退而求其次的"临时改 + 事后撤销"，除了慢，还会留下"忘了撤"这一类必踩的坑。

同一处还踩了两个细节，都写进了 `test/lib/appctl.mjs`：

- **端口通 ≠ 应用可用**。`/json/version` 一通就去断言，只会拿到
  `window.__snp` 未定义的报错（WebView2 起来了，前端脚本还没跑）。就绪判据得是
  `document.readyState === 'complete' && !!window.__snp`。
- **收尾要用 `taskkill /T`**。`Stop-Process` 只杀主进程，`msedgewebview2`
  渲染进程会变成孤儿挂着吃内存（实测残留 6 个、约 400MB），而且它们的父 PID 会被
  系统回收给别的进程，事后看像"别人的进程"，很难判断该不该清。

**25. 按键处理的第一件事是分「选中」和「光标」，不是看光标在哪。**

对比窗口三击选中一行再按 Backspace，只删掉上一行的换行，选中的内容一点没动。
分支写的是 `if (e.key === 'Backspace' && pos.col === 0) mergeUp()` —— 逻辑没错，
错在 `pos.col` 来自 `selection.anchorNode`，而**三击给的选区锚点就在行首**
（实测 anchor.col=0、focus.col=11）。于是「选中了一行」被当成「光标停在行首」，
`preventDefault` + 合并上一行，用户看到的就是「换行被删了，内容还在」。

这类 bug 的特点是**从现象倒推比从代码正读快**：现象说「删除的是换行」，
那唯一会删换行的路径就是 `mergeUp`/`mergeDown`，再问「什么情况下会走进去」，
锚点/焦点一测就水落石出。如果先去读「选区怎么高亮」「contenteditable 怎么写」，
会绕很远。

两条可以直接搬走的经验：

- **选区非折叠时，`Backspace`/`Delete` 的语义是「删这段」**，任何"光标在行首/行尾"
  的行合并都必须排在它后面判断。同理，跨 `contenteditable` 宿主的选区浏览器删不了，
  要么自己按行号算，要么明确不做——不能装作能删。
- **`pos` 这类"当前位置"的取值，要写清是从锚点还是焦点取的**。三击、Shift+方向键、
  双击拖选都会让两者不同，只取一个就等着在某条路径上错位。

验证也得用真实输入：`dispatchEvent(new KeyboardEvent(...))` 合成的按键不会触发浏览器
默认行为，测不出这个 bug；必须走 CDP 的 `Input.dispatchMouseEvent({clickCount:3})`
+ `Input.dispatchKeyEvent`，那才是用户的手。

**26. 「垃圾/噪音」类问题，先把每一条的原始路径列出来，再下结论。**

我数出「一批探针往回收站加了 11 条」，就写下「WebView2 每次会话的日志/锁，任何一次
启动应用都会产生」。数量是对的，归因是含糊的。用户的反问一针见血：**「那用 WebView2
的软件岂不是满电脑垃圾？」** —— 这个反驳是合理的，说明我的解释站不住，得往下挖。

三步就挖到底了，而且都很快：

1. **模拟用户，不跑测试**：直接起一次应用（无参数、无调试端口）、`WM_CLOSE` 关掉，
   同样 10 条。所以不是测试代码删的。
2. **列出原始路径**：`Session Storage\{LOCK,CURRENT,MANIFEST-000001,LOG}`、
   `Code Cache\js\index-dir\todelete_1d6da9af8987947c`、`Network\<guid>.tmp`、
   `ProvenanceData*`。注意 `todelete_` 这个前缀是 **Chromium 自己**加的。
3. **找同类对照**：Chrome 的 `Default\Session Storage` 里是同一组文件，
   连 `LOG.old` 都在 —— LevelDB 正常关闭把 `LOG` 改名成 `LOG.old`，下次启动删掉旧的。
   「删除」就是这么来的。

结论不是「测试脏」，也不是「我们的代码脏」，而是：Chromium 家族每次会话都会重建这点
东西，而本机的删除钩子（深信服 SGuard）把它们重定向进了回收站。Windows 上
`DeleteFile()` 本来**不进**回收站（只有 `SHFileOperation`/`IFileOperation` 才进），
所以别的机器上看不到这个现象 —— 用户的直觉在别处是对的。

治本不是「想办法少写缓存」（试过 `--disable-application-cache`、`--disk-cache-size=1`，
对这 10 条完全无效），而是**换目录**：把探针的 WebView2 数据目录设到
`%TEMP%\eznotepad-probe`（`WEBVIEW2_USER_DATA_FOLDER`）。SGuard 对 `%TEMP%` 下的删除
不做重定向，同一目录连跑 4 次 0 条；顺带把「探针写用户真实配置、残留状态让断言假红」
这个更要紧的问题一起解决了。

两个可以直接搬走的点：

- **数量只能说明「有变化」，「原始路径」才能说明「谁干的」**。遇到"某某产生了 N 条垃圾"
  这种结论，先问自己：我能列出这 N 条的确切路径吗？列不出来就别写进文档。
- 读回收站 `$I` 元数据时，**offset 24 的长度字段是字符数，不是字节数**（×2 才是字节）。
  我按字节读，路径被静默截断成 `C:/Users/.../com.simple.not`，于是"文件名"这一栏
  整整一轮都没看见 —— 而这恰好是唯一能定性的信息。

**27. 用户说「没有某功能」时，先把它跑一遍再动手 —— 十有八九是入口问题。**

用户问「本程序缺少 Ctrl+Z 撤销吗」，第一反应当然是去加一套撤销栈。实际一测，
`probe-undo` 头 8 条全绿：所见即所得有完整的 200 条 / 8MB 双上限历史栈，纯文本走 CM6
的 history，`Ctrl+Z`、`Ctrl+Y`、`Ctrl+Shift+Z`、菜单命令都通，焦点在侧栏时也通。

真问题是三个小的：

1. **工具行没有入口**。撤销/重做只躺在「编辑」菜单里，而工具行只有模式/查找/保存三颗
   按钮 —— 用户不会去翻菜单确认一个「应该天生就有」的功能。
2. **菜单走的是另一套栈**。`editCmd('undo')` 对 wysiwyg 一律 `document.execCommand('undo')`，
   操作的是浏览器原生栈，而那份 DOM 是受控重绘的。它**能用**（简单输入下 Chromium 的
   原生 undo 恰好对），但这正是最坏的情况：两套记录各记各的，再叠上块级操作、格式命令、
   视口重绘，总有一个序列会错位，而那时用户看到的是「撤销把内容退成了没见过的一坨」。
3. 对比窗口的 `Ctrl+Y` 传的是 `undo(side, false)` —— 照着上一行的 `Ctrl+Z` 抄下来，
   参数没改，于是「按重做反而又退一步」。

三条可以直接搬走的：

- **「没有」常常是「没看见」或「按了没反应」**。先写个探针把功能跑一遍（这次 15 分钟），
  比闷头重写一套撤销栈省太多 —— 而且重写会覆盖掉一套已经调好 COW、合并、双上限的实现。
- **判断双栈问题不要问「它会不会坏」，要问「这里有几个真相源」**。同一件事有两份记录，
  哪怕当前测试全绿，也已经是 bug 的温床（不变量 27）。
- **相邻分支复制粘贴，参数要逐个对**。`Ctrl+Z` 和 `Ctrl+Y` 只差一个布尔值，抄漏了不会
  报错、不会崩，只会「按了以后朝反方向走」—— 只有真机按键测试能抓到。

**28. 上一个修复的「相邻空格」，是这次 bug 的老家 —— 撤销只修了一半就发版了。**

第 27 条修完就宣布「撤销通了」，第二天用户问「对比页面是不是没有 Ctrl+Z」。补两条
探针立刻红了：

1. **回车断行之后按 Ctrl+Z 撤不回来**（8 行还是 8 行）。上一轮只给「打字」这一条路径
   记了快照：`pushUndo` 写在 `onInput` 里，而 `splitLine` / `mergeUp` / `insertText` /
   `deleteSpan` 直接改模型、一个快照都不记。于是撤销栈里根本没有这一步，按下去什么
   都不发生。
2. **焦点在工具栏上时 Ctrl+Z 完全没反应**。监听挂在两块画布（`cv.addEventListener('keydown')`）
   上，点过排序或编辑开关之后焦点在按钮上，事件根本到不了处理函数 —— 而这正是排序之后
   最自然的动作（排完想撤回）。

修法不是加两行 if，而是把「记快照」和「按快捷键」两件事各自收敛到一个地方：

- `recordUndo()`（结构性编辑，一次一步）与 `pushUndo()`（打字，700ms 合并）分开。
  原来那个节流计时器是**模块级**的，左侧打完字 700ms 内改右侧，右侧连第一步都记不下；
  现在计时器跟着 `st.undoAt` 走，每侧独立，加载新文件时清零。
- 快捷键从画布挪到 `document`：落哪一侧先跟光标，光标不在行里就跟 `S.lastSide`，
  再兜底左边。同一个文件里 `Ctrl+S` 早就这么处理了（注释写着「焦点不在可编辑行时也要能存」）
  —— 一个按键需要这样处理的理由，对隔壁的按键同样成立。

教训：**「撤销能用」要按「写模型的路径有几条」逐条验，不是按「试了几个键」验**。
这次探针从排序 1 条扩到 8 条（打字、重做、连撤、回车、焦点在按钮、只读态），
`probe-compare` 31 → 39 条。发版前那次 499 条离线断言全绿也没抓到 —— 它根本不跑快捷键。

**29. 「撤销能用」之后还有两件事：光标在哪，以及文件到底脏没脏。**

第 28 条修完撤销，又往下问了一句「撤完体验对不对」，挖出两个都是**看得见但没人报错**的：

1. **撤销后光标固定回第 1 行**。`undo()` 一直调 `applyEdit(side, 1, 0)`。2000 行的文档里
   按一次 Ctrl+Z 就跳回顶部，用户得自己滚回去找刚才那行 —— 这跟「撤销」两个字承诺的
   正好相反。修法：撤销前先 `caretPos()`，撤销后按原行原列放回去，并让 `focusAt()`
   统一把行号列号**夹进当前范围**（撤销会让文档变短）。不夹的后果比跳位置更糟：
   `lineRow.get()` 返回 undefined 时 `focusAt` 直接 return，而 DOM 刚被重画过，
   焦点掉到 `body` 上 —— 界面看上去就是「撤完以后键盘没反应了」。
2. **撤到原样，脏标记不消失**。`st.dirty` 是一个一路 `= true` 的布尔量，没人负责把它
   改回 `false`。于是撤销回原样后仍然显示「未保存」、保存按钮可点，再按 Ctrl+S 就把
   一模一样的字节又写一遍 —— 用户会以为文件真变了。修法：每侧留一份 `st.base`
   （打开时、存盘后各记一次），`updateMeta()` 里逐行比。逐行比字符串引用就够：
   `slice()` 只复制数组，没改过的行还是同一批字符串对象，8MB/5 万行也不会多存一份
   拼好的长字符串。

共同的教训：**状态量能算出来就别攒**。布尔量 `dirty` 和「光标默认放第 1 行」都是
「省事」的默认值，功能测试全绿也发现不了，只有真按一遍、真看一眼才会发现。
`probe-compare` 这一轮从 39 条扩到 50 条（其中 6 条专门测光标位置和脏标记）。

**30. 「加两个按钮」这件事，一半的功夫在按钮之外。**

给对比窗口工具栏加撤销 / 重做，起因是「键盘能用但看不见入口」。动手前先量了一次
宽度预算，才发现真正的问题比按钮大：工具栏是 `overflow: hidden` 的单行 flex，
**880px 窗口下最右边的「导出报告」已经被静默裁掉了**——加按钮之前就这样，只是没人
把窗口拉那么窄试过。窗口最小可以到 760px，也就是说这个缺陷一直在射程内。

于是这轮做了两件事，只有一件是「加按钮」：

1. **按钮必须认「排序」这一步**。排序不往两侧的撤销栈里压快照，它存一个 `S.lastSort`
   整体快照（一次撤销还原两侧）。`syncHist()` 要是只看 `st.undo.length`，排完序按钮
   就是灰的——用户刚做完一个可撤销的动作，工具却说「没得撤」。可用性从**真实历史栈**
   算，不从「有没有打开文件」猜。
2. **折叠不能按窗口宽度猜阈值**。第一版想用容器查询分档，估了个 940px 的阈值。这个数
   在中文下大概对，但界面有九种语言：英文 "Previous / Diff list / Export report" 比
   「上一处 / 差异清单 / 导出报告」宽 100px 以上，德文更长。按像素猜的阈值必然在某种
   语言下把最右边的按钮裁掉——**而裁掉是静默的**，用户只会看到按钮不见了。
   改成量真实溢出：`fitTools()` 去掉折叠、读 `scrollWidth > clientWidth`，溢出就
   降一级。调用点是 `resize`、`document.fonts.ready`（字体没就绪时量出来偏窄）和
   `updateMeta()`（统计文字「12 处差异」比「完全一致」长得多）。

顺带一个同源的取舍：`.cmp-stat` 原来 `white-space: nowrap` 且不可收缩，空间不够时它是
硬邦邦地把按钮顶出去。给了 `min-width: 0` + 省略号之后，**统计文字先让位**——信息和
动作抢地方时，动作优先，因为被裁掉的动作是「用不了」，被截断的统计只是「少看一眼」。

探针从 50 条扩到 64 条，新增的 14 条里只有 6 条测按钮，其余测的是**窄窗口下每个按钮
的右边界没有越过工具栏右边界**。只看 `scrollWidth - clientWidth` 不够：它只告诉你
「总共超了多少」，指不出是谁被裁；而折叠漏一个，溢出的正是那一个。断言落在每个按钮上，
失败时会直接打印 `clipped: ["save","report"]`，不必再猜。

这里还踩到一个结构上的坑：折叠规则写的是 `.cmp-btn > span`，但「编辑」「保存」「导出
报告」三个按钮的文字是**直接写在 button 里**的（没有 `<span>`，也没有图标），选择器
对它们无效——折不起来，一起溢出。所以这三个按钮先补了图标 + `<span>`，规则才成立。
**给一排按钮加「收文字」的能力之前，先看它们的结构是不是一致**；不一致就先统一，
否则规则会默默地只对一半元素生效。620px 那档专门验证第二级降级（连勾选项文字也
收起来）；它比 `min_inner_size` 还窄，属于兜底，不是用户真能拉到的宽度。

**31. 「不用保存」是一句承诺，得由代码兑现 —— 光把脏标记关掉，等于悄悄丢字。**

速记看起来最简单的一个功能：固定路径、改了自动存、菜单里开一下。真做下去，坑都在
「它和普通标签有什么不一样」这条线上：

1. **把 `isDirty` 直接放行**（速记永远干净）之后，关闭时就不会有确认框了 —— 但写盘是
   350ms 防抖，打完最后一个字立刻按 `Ctrl+W` 或关窗口，`content` 里还差那几个字，
   而界面不会给出任何提示。**「不追问」和「不丢字」必须一起做到**：关标签、
   `confirmQuit()` 两处都先 `flushQuickNote()`。这条写成了不变量 31 —— 否则将来谁改
   关闭流程，都会把它悄悄改回去。
2. **同一个文件被两个标签写**。速记从菜单打开是一份；但用户还可能从文件树点它、把它
   拖进窗口、从「最近打开」点它 —— 那几条路都走 `openPath()`。只要 `openPath` 不认
   速记，就会开出第二个编辑器，两边各写各的，后保存的把先保存的盖掉。改法是让
   `openPath` 命中速记路径时改道 `openQuickNote()`，身份判定用标签上的 `quickNote`
   标记（路径比较要在每个调用点重新问后端）。
3. **「另存为」的语义变了**。普通文档另存为就是改 `t.path`；速记要是也改，接下来的
   自动保存就全写到副本上，速记本身从此不再更新 —— 用户以为在记笔记，其实在写另一个
   文件。所以速记的另存为只「导出副本」，`t.path` 一个字节都不动。
4. **探针差点写到用户真正的笔记上**。速记默认落在应用数据目录，而探针会往里打字。
   「跑完再恢复原文件」这种方案一次崩溃就赔掉用户内容，不能考虑；正确做法是让后端
   留一个**只改路径**的环境变量（`EZNOTEPAD_QUICKNOTE`），探针整轮跑在 `%TEMP%` 里。
   凡是「功能默认写到用户数据目录」的东西，测试都该先问一句：它写到哪、怎么隔离。

还有一条是断言写法上的：第一版探针写「新字落在最后一行」，一跑就红 —— 编辑器末尾
本来就有个空段落等着你写，字落在新段落里。行为其实是对的，错的是断言贴着实现写。
改成「新内容落在文档末尾」，同时验证编辑器和磁盘两边，才是用户看到的那句话。

`probe-quicknote` 24 条，六组探针合计 190 条 / 2 分钟；离线六套 499 条不变。

**32. 「点了没反应」十次有九次是 DOM 在点击中途被换掉 —— 一次踩到两个地方。**

对比窗口贴两段文本后「必须点第一行旁边才能插入，点别处没反应」。看着像命中区问题，实际
是两条独立的路径叠在一起，都会让浏览器「想聚焦的那一行」当场消失：

1. **blur 里同步重绘**。`cv.addEventListener('blur', …, true)` 里 `flush(); render(true)`：
   捕获阶段的 blur 发生在浏览器默认动作（把焦点交给被点的那一行）之前，此刻重建
   `innerHTML`，被点中的元素已经不在文档里，随后的聚焦落空。正确做法是 blur 只把内容
   并回模型（`flush()` + `S.ver++` + `recompute()`），**重绘交给下一次 render** ——
   那一定发生在这次点击/拖选结束之后。
2. **防抖定时器不认识「已经提前 flush 了」**。`onInput` 排了一个 300ms 后
   `flush(); applyEdit(旧行, 旧列)` 的定时器；blur 提前 flush 之后定时器照样到点执行，
   `applyEdit` 里的 `focusAt()` 把光标**硬拽回原来那一行**。修法是把
   `clearTimeout(onInput.timer)` 放进 `flush()` 自己 —— 任何提前收尾（blur、撤销、保存）
   都要顺手取消那个「稍后再来一次」的排队动作。

另外半条是纯几何：`canvas` 宽度只按内容量算，贴上短文本时 canvas 只有内容那么宽，行右侧
那片「看着还是正文」的空白其实不属于任何行，点上去落在 `.cmp-sc` 上。改成
`max(内容宽, 可视宽)`，再补上「点行号 = 行首、点行尾/下方空白 = 行末」的兜底。

**这三处都是「看起来像同一个 bug」的不同层**：一条断言（点了别处，字进哪一行）就能把
它们串起来 —— 先断言行为，再分层拆，比盯着 CSS 猜命中区快得多。

`probe-compare` 71 条（新增 7 条点击落点 + 短文本铺满整栏），`probe-quicknote` 25 条，
六组探针合计 198 条 / 2 分钟；离线六套 499 条不变。

**33. 「另一边动不了」不是焦点问题，是那一行根本不存在 —— 可写的东西必须先可见。**

用户的原话是「一边粘贴后，另一边没法选中修改了」。第一反应是去查焦点、查 contenteditable，
但真正的原因是数据模型：并排对比必然把短的一侧补成**占位行**（`row.r === null`），
而 `rowHtml` 当时写的是 `editable = S.edit && cell` —— 没有 cell 就不给
`contenteditable`。占位行在屏幕上长得跟空行一模一样，实际是块白板。

三处都得改，少一处用户还是卡住：

1. **能不能写**：占位行也带 `contenteditable`，写下去等价于在这一侧插一行
   （`flush()` 里按 `p.fill` 走 `splice(at, 0, ...)`，`at = row.fL/fR - 1`）。
   插入位置在 `recompute()` 里一次算好：前面最后一个本侧行号 + 1。
2. **点了落在哪**：`mousedown` 兜底是从 `.cmp-ln` 的文字里取行号的，占位行那里是空串，
   `+'' === 0`，`focusAt` 再夹一次就变成第 1 行 —— 用户点第 3 行，字进了第 1 行。
   占位行必须按**对齐索引**聚焦（`focusRowIdx`），绕开行号映射。
3. **看得出来吗**：改完 1 和 2，探针全绿，但截图一看右栏还是一片白 —— 用户根本不知道
   那里有 5 个位置可以写。补一道极淡的斜纹 + 行号位的 `·`，只画在编辑态
   （只读时不该暗示可写）。

**教训是顺序**：先问「这个东西在模型里存在吗」，再问「它能不能聚焦」。把「看起来是空行」
和「这一侧没有这一行」当成同一件事，就会写出一个视觉上和逻辑上都对不上界面的实现。
另外，断言只能证明「能写」，证明不了「看得见」—— 每轮改完 UI 都该截图看一眼。

**34. 守卫要装在唯一的出口上，不是装在按钮上。**

对比窗口改了字不保存、按 Alt+F4，改动就没了 —— 因为脏检查压根不存在，
而「关闭」有三个入口：右上角 ×、Alt+F4、任务栏右键关闭。只给 × 加确认框，
另外两条路照样静默丢数据。

正确的位置是 `getCurrentWindow().onCloseRequested()`：所有关闭请求都从这里过，
`preventDefault()` 之后自己决定下一步。两个细节：

- 判脏前先 `flush()`：防抖窗口里那 300ms 的输入还没进模型，不 flush 就会漏判。
- 确认后要 `forceClosing = true` 再 `close()`，否则第二次请求又被自己拦下来，窗口关不掉。

还有一个「按了也没用」的按钮：粘贴进来的文本没有磁盘目标，`save()` 救不了它，
那就不该显示「保存并关闭」——把它 `hidden` 掉，只留「不保存 / 取消」。
顺带踩到一个 CSS 坑：`.cmp-btn { display: inline-flex }` 的优先级高于浏览器默认的
`[hidden] { display: none }`，属性设了也照样显示，得补一条 `.cmp-btn[hidden]`。

关窗守卫 5 条），`probe-quicknote` 25 条，六组探针合计 212 条 / 2 分半；离线六套 499 条不变。

**35. `SPI_GETWORKAREA` 只认主屏 —— 多屏上它悄悄给出「别人的答案」。**

「对比窗口打开后不在主程序所在的屏幕」「拖到另一个屏幕，放大后也不对」，两条症状
一条根因：铺满用的是 `SystemParametersInfoW(SPI_GETWORKAREA)`。这个 API 的行为
本身没错，错的是它回答的 **不是我们问的那个问题** —— 它永远返回主屏工作区。
于是：

- 建窗时按主屏尺寸摆位 → 主程序在副屏，窗口照样开在主屏；
- `fill_work_area_when_ready` 拿主屏尺寸当「目标值」去比对副屏上的窗口，永远对不上，
  于是那一轮循环（40 次）不停地 `SetWindowPos` 把窗口拽回主屏尺寸 —— 这就是
  「拖过去放大不对」。
- `tool_set_fullscreen(label, false)` 也按主屏居中，把窗口搬回主屏。

正确姿势是问窗口自己：`MonitorFromWindow(hwnd, MONITOR_DEFAULTTONEAREST)` +
`GetMonitorInfoW` 的 `rcWork`；建窗时问**主窗口**的显示器。两个附带坑：

1. Tauri 的 `position()` / `inner_size()` 收**逻辑像素**，而 `rcWork` 是物理像素。
   150% 缩放的屏上不换算，窗口生出来就有 1.5 倍大（随后被铺满逻辑纠正，观感是闪一下）。
   换算用 `GetDpiForWindow`（拿不到再退 `GetDpiForSystem`）。
2. 判「铺满了没」的那一轮循环，目标尺寸必须**每轮按当前屏重算**。写死一个数值，
   窗口一换屏，循环就会一直判失败并反复搬运。

顺带一条：本机只有一块屏，这类改动**没法在本机实测**。能做的是把「和主窗口同一块屏」
写成探针断言（单屏时恒等，多屏时才有区分度），并把几何量成「窗口矩形 == 该屏工作区」——
至少能抓住 `screen_of()` 返回垃圾（零矩形、DPI 算反）这类实现错误。用户报的多屏问题，
必须明说「需要在你那台机器上确认」。

**36. 补功能之前先查别人怎么做 —— 而且要先搞清楚「那个动词的单位是什么」。**

用户说对比功能「整体不好用」，第一反应是加功能。查了 Beyond Compare 5 的命令表、
WinMerge 的官方快捷键附录、Meld 的官方帮助、VS Code 的 diff 文档之后才看清：
四个工具共享同一个核心动词 —— **把这一处差异挪到另一边**，而我们一个都没有。
粒度也一致，是「一处差异」（BC 的 current section、WinMerge 的 difference、Meld 的
change block），不是一行，也不是整个文件。两头之间的那一档才是这个工具存在的理由。

顺带抄到三条不用再想的约定：方向跟着**光标所在那一侧**（BC 的按钮文字就是这么做
的）；「复制并跳到下一处」是连续合并的主循环（WinMerge `Ctrl+Alt+→`）；上一处/下一处
除了 `F7`/`F8` 还有 `Alt+↑/↓`。

实现时踩到的两个坑都不在算法里：

- **「当前在哪一侧」不能靠 `S.lastSide`**。点进一行只放光标、不写模型，那条路径不经过
  任何 `lastSide = side` 的赋值 → 按钮方向用上一轮的旧值，内容推错了边。
  正解是先读**文档选区**（`getSelection().anchorNode` 往上找 `.cmp-tx`），`focusin`
  时再补记一次。
- **撤销要能落到「刚才改的那一侧」**。同步改的是另一栏，光标还在原处，
  `undo(光标侧)` 栈是空的 → 表现为「刚同步完按 Ctrl+Z 没反应」。加一层
  `undoEither()`：先试光标侧，没有历史再落另一侧。

**37. 「太窄」不是尺寸问题，是三个东西抢一个位置。** 用户说预览条不好用，第一反应是
「加宽」。加宽是对的，但先看清楚它为什么窄得难受：22px 的栏里塞 10px 的槽，而那个槽上
要同时画差异段、当前段（还要比别的宽一点以防色弱）和视口框 —— 三样东西抢十来个像素，
每一件都只能挤成一条缝。**先把「这个控件要表达几件事」数清楚，再决定它要多宽**，
比按「看起来偏窄」调一个数字可靠得多。改完 34px / 22px 之后，悬停、点击、看差异密度
三件事一起变顺，而正文只少了 12px。

顺带一条：视口框在「内容只比一屏多一点」时要**不画**。那时框高几乎等于整条槽，
画出来只是把轨道整体染灰一层，反而让人以为预览条没画差异。

**38. 虚拟滚动 + 折叠 = 行位和行号不是一回事，必须挑一个当真。** 折叠的实现只有一句话：
「把相同行从视图里去掉」。真正的工作量全在「谁还在拿 `S.rows` 的下标当行位」。
逐个找出来的有七处：`rowHtml` 的 `top`、`renderRows` 的循环、滚动高度、`focusAt`、
当前块覆盖层、预览条的比例换算、`gotoBlock` 与点击兜底。漏一处，表现都是「行号跳了
但位置没跳」——点第 3 行落到了第 5 行，或者滚到哪都对不上。

正确的做法是**只留一个行位来源**（`S.view`）并配一个 `vposOf()`，其余全部改写；
再配一个兜底：`focusAt` 找不到可见行时退到最近的一条，而不是 `return` ——
`return` 会让焦点掉到 `body` 上，界面上就是「键盘没反应了」，比位置偏一行严重得多。

折叠还有两个必须钉住的行：光标所在行、查找命中行。前者是因为「把差异改成相同」会让
这一行当场从「修改」变「相同」、随即被收走，用户正打着字光标就没了；后者是因为
「跳到被折叠的命中行」如果不放出来，屏幕只会滚到一片接缝。这两条都是先写完、跑通了，
再自己盯着屏幕想「现在最难看的一刻是什么」才补上的。

六组探针合计 244 条 / 3 分钟；离线六套 499 条不变。

**39. 预览条要画的是「密度」，不是「段落」。** 用户原话只有一句「红色块太粗了」，但问题
不在颜色浓：一段差异在 2000 行里占 60 行、就画成 60 行高的色块，看起来像「整篇都红了」，
而用户真正要问的是**差异在哪儿、有多密**。改成**一行一条 1px 细线**之后，密度自己就
显出来了 —— 改 3 行是三条线，改 300 行是一片红，扫一眼就分得清。

实现上不能退化成「每行一个 div」（几千个节点），也不能一律按段画（段一长又变成粗块），
所以 `diffMarks()` 分两档：**每行至少 2.5 个像素**时逐行 `fillRect` 出 1px 线，否则按段，
且总行数超过 4000 就直接走按段（否则一屏几百条线糊成灰带）。缓存键是
`S.ver / total / h / S.cur`，滚动不重算 —— 逐行画的数量比按段多一个量级，不缓存会拖慢滚动。

同一句话还带来一条更重要的减法：**差异只把字标红，不铺底色、不画边框**。一屏几十处差异
时铺底色会让整页发红，反而看不出哪几个字变了，而这正是对比窗口唯一要说的事。

**40. 一个按钮别说两件事 —— 尤其是「状态」这件事。** 对比窗口的「最大化 / 还原」是一颗
按钮两个状态，图标却没跟着换，用户点完根本不知道当前是哪一态（无边框窗口连系统标题栏都
没有，没有任何地方能看出来）。修法是两颗 `<svg>` 叠在同一个按钮里，靠一个 `.restored` 类
切 `display`，`title` 与 `data-i18n-title` 一起换 —— 顺手把「图标换了但提示还写着『最大化』」
这种半截状态一起解决。

更难的一步是判断依据：**无边框窗口没有 `WS_MAXIMIZE`**，`isMaximized()` 永远说没最大化，
所以「当前是否已铺满」只能问自己那套矩形（Rust 侧 `setCompareFill` 记下的布尔值）。
凡是「系统状态」和「自绘状态」并存的地方，都要先确认哪一个是真相来源。

**41. 动作按钮长在它作用的对象旁边，别长在工具栏上。** 「复制到另一侧」原本是工具栏里一颗
带文字的按钮，点之前得先确认「哪一侧是目标」。挪进中缝之后，位置本身就是答案：左箭头 = 推到
左边，右箭头 = 推到右边，跟着当前这一处上下走（`syncGutter()`），只在两侧都有文件、且真有
差异时出现。工具栏留给「对整篇生效」的动作（上一处 / 下一处、导出、排序）。

判断标准一句话：**如果一个按钮的效果取决于「你现在选中的是哪一处」，它就不该待在全局工具栏
里。** 同一轮里「打开文件」的入口也从工具栏搬到了槽位左边的文件夹图标 —— 它离「这里放哪个
文件」最近。

空态同理，不该是一道选择题。原来的空窗口给「选左侧文件 / 选右侧文件 / 粘贴两段文本」三个
入口，等于逼用户先选模式、再动手；现在打开就是两个空白编辑区、光标在左，`Ctrl+V` 就是全部
路径，选文件则退化成标题栏上的一个图标。

**42. 快捷键撞车不会报错，只会「按下去没反应」。** `Ctrl+Shift+F` 撞上了 Windows 自带的
繁简切换：谁先拿到这一次按键由系统和输入法决定，我们这边的 `preventDefault()` 管不着，
表现是「格式化时好时坏」—— 有时没反应，有时顺手把输入法切成了繁体。挑快捷键要主动避开
三类组合：**系统级**（输入法繁简、截图、虚拟桌面）、**窗口/浏览器级**
（`Ctrl+Shift+T/N/W`）、**编辑器惯例**（`Ctrl+Shift+P/F` 在 VS Code 里分别是命令面板和
全局搜索）。换到 `Ctrl+Alt+L` 之后没有第二处再用它，且「L」在 Format 里也说得通。

**43. 长表单要横着切，不要竖着堆。** 设置面板原来是十来个分组一路竖排，窗口矮一点就要
滚三屏，找「快捷键」得先盲滚一遍。改法是左边一列分类（外观 / 界面 / 文件 / 快捷键）、右边
一页内容，切换只是 `hidden` 类的加减 —— 所有 `input` 都还在原处，改哪一项都即时生效，
不需要「确定」按钮，也不存在「切走就丢值」。这个面板本来就没有保存按钮，所以「一页一页
切换」是纯粹的排版选择，不动任何数据流。

顺带一条 CSS 坑：内容页里**不要再套一层 `max-height + overflow`**。快捷键列表自己带滚动条时，
外层滚动区会把它切在半行上（截图里能看见一条被切掉一半的「改」按钮）。只留一层滚动，
内层自然撑开。

**44. 图标必须在它真实的尺寸下看，不是在设计稿的 1024px 下看。** 应用图标定稿前做了四轮：
每条正文条 66px 高（1024 画布）在 24px 下糊成一片，改成 66/300 比例 + 圆角端头才分辨得出；
折角放在右下比右上更容易和正文条抢位置，最终挪回右上、用暖米色 `#ece2d4` 压一层。
折角的色**跟着底色走而不是跟着纸走**：底是橙红时，中性暖灰会发青发脏，浅蓝更不行 ——
它表达的是「纸被翻起来露出的背面」，得比正面暖一度。做法是 `tauri icon -o <临时目录>`
生成全套，再逐个尺寸（16/20/24/32/48）放大看 —— **不要靠脑补缩小效果**，`viewBox` 里的
留白和 1px 描边在小尺寸下全部消失。

标题栏那枚品牌标同理：22px 的方块里塞 15px 的图形，只能保留「一张带折角的纸」这一个
信息，三条正文条必须去掉（那属于应用图标，不属于品牌标）。

**45. 判断两个文件「一样」，只能靠读内容。** 文件夹对比第一版按「大小 + 修改时间（前后
1.5 秒内算没动）」判，结果是：把「一」改成「二」、把 3 改成 5 —— 字节数一模一样、时间
又挨着，被判成「相同」。而「只看差异」默认是勾着的，于是**改过的文件在界面上直接消失**，
用户拿到的结论是「两边一样」。

这个错误属于「看起来对、代价是静默说谎」，比报错危险得多。改法是加一条
`compare_file_pairs`：整批一次 IPC，逐 256KB 读、一有不同立刻返回（内容真一样时是唯一
要把两个文件都读完的情况）。**修改时间从判定里彻底删掉** —— 只碰过没改内容的文件现在
正确地报「相同」，否则用户会被一堆假「已修改」逼着逐个点开确认。

**46. 事件是排队派发的，「操作 A 之后立刻做 B」才是暴露时序 bug 的路径。** 「全部标签」
下拉有一半概率点了没反应：`contextMenu` 在 window 上以 capture 监听 `scroll`（任何内容滚动
都会让菜单和它指向的格子错位，所以该收掉），而标签条刚被滚过（滚轮、或者切换标签时
`syncTabOverflow` 自己把它滚进视野），那条 `scroll` 事件**在我打开菜单之后**才被派发，
于是菜单刚出现就被收掉。

两个教训：

1. **偶发失败必须查到根因**。第一反应是「把 `sleep(100)` 改成 `sleep(300)` 或者失败重试一次」
   —— 那只是让探针不再报红，用户那边依旧一半概率点不动。真正的定位手段是在页面里挂
   `scroll` / `mousedown` / `MutationObserver` 记录「菜单被谁收掉」，一次就看清了。
2. **给菜单加一个「锚点是固定控件」的开关**（`stayOnScroll`），而不是全局去掉滚动关闭 ——
   锚在内容上的菜单（块、树节点、标签）滚一下确实该收，那是正确行为。

**47. 启动流程里，「等待用户」的那一步必须排在所有事件注册之后。**

工具窗「在主窗口打开」这个功能，一直有一半概率没反应 —— 而且只在**真攒着未保存内容
的那次**出现，手工测几乎碰不到。现场是主窗口 `#tabs` 里 0 个标签、事件推过去毫无动静。

根因在 boot 的顺序：

```js
const drafts = await restoreDrafts();   // ← 这里 await 一个模态框（「是否恢复」）
...
try { await listen('open-files', ...) } // ← 用户不点，这行永远不执行
```

`restoreDrafts` 里的 `confirmBox` 是个 Promise，用户不动它就不 resolve。于是
「先恢复，再挂监听」这个看起来很自然的顺序，实际含义是「**用户点掉对话框之前，
应用收不到任何外部推来的文件**」。第二个实例双击 .md、工具窗点「在主窗口打开」，
路径全被丢掉，界面表现就是点了没反应。

两条结论：

1. **事件注册放在 boot 的最前面**，早到的数据先攒着（`earlyOpen`），恢复完再按序打开 ——
   既不会丢，标签顺序也还和会话一致。
2. **不要用「重载页面」去验证启动期的行为**。这一条我试过：`location.reload()` 之后
   `localStorage` 里刚写入的草稿直接没了 —— WebView2 的 localStorage 是延迟落盘的，
   重载/硬杀都会丢掉最后那一批写入。于是「重载 → 弹恢复框 → 推文件」这个测试永远
   造不出对话框，却看起来"通过"。真正的守法是读源码断顺序（`run-units` 里那两条
   boot 顺序守护），要跑真机就老老实实重启进程并等落盘。

`probe-compare` 167 条（新增默认空白编辑区、预览条 1px 细线、差异只红字、缝里箭头、
最大化/还原图标五组，「编辑态 Ctrl+A 是全文本 / 拖出视口不断 / 跨行选区能删能改」，
「点工具栏撤销/重做时视口不动、焦点仍在正文」，以及「换行后行高按内容走 / 关掉回单行高 /
切换时顶部仍是同一行」，一侧粘进来的行比对面多之后另一侧再全选粘贴），
`probe-fcmp` 新增 24 条，`probe-app` 从 39 加到 117 条（设置分栏、标签条溢出的四个入口、

（`run-units` 96 → 98 是 boot 顺序守护；本轮又加到 115，多出语言表与自动识别的判据）。

**48. 「一个字符既是正文又是命令」的入口，必须给它一条明确的退路。**

`/` 起插入面板是用户提的，动机很对（手不离键盘）。但 `/` 本身是正文里高频的字符：
日期 `2026/11/05`、路径 `a/b`、分数 `1/2`。无条件拦截是最坏的做法——用户打到日期一半
弹面板，接着按的数字还会被面板吃掉变成「选标题」，等于把一次正常输入变成一次误操作。

三层防线，缺一层都会留下一个可感知的坑：

1. **只在行首或空白之后触发**（判据看光标之前那一小段的末字符）。这一条挡掉 95% 的误触，
   而且不需要用户知道规则——他的斜杠在句子中间就是普通字符。
2. **代码块 / 公式块 / 表格单元格里不触发**。那里的 `/` 是注释符、除号、路径分隔符，
   在这三处弹面板属于纯粹的错误。
3. **没选就关，字符原样还回去**。这才是真正的兜底：用户就是想在行首打一个 `/`，
   按 Esc 之后斜杠必须出现。有了这条，误触的代价从「打了个斜杠却得到别的东西」
   降到「多闪一下面板」。

实现上有三个地方写错就会前功尽弃，都是本轮真实踩到的：

- **不要「先插入再删除」**。让按键 `preventDefault`、字符从没进过正文，关面板时按
  **原偏移**插回即可。这样撤销栈里不会多出一条「删斜杠」，也不需要把光标搬来搬去。
- **原偏移 ≠ 当前光标**。用户可能点了一下别处再关面板；斜杠要回到它本来该在的位置，
  不该跟到新光标后面。光标真的还在原处时，才顺手把它推到斜杠后面接着打。
- **面板那一层要 `stopPropagation`**。编辑区的 `/` 监听如果用「菜单是否开着」来判断
  该不该接管，会看到「已经关了」，然后当场把面板重新弹出来 —— 用户按 Esc 得到的是
  「面板关了又开」，循环。

还有一条产品上的判断值得记：**别把高频项也编号**。`## ` 是 2 个字符直接到位，
面板是「开 → 看 → 按」三步。编号只该服务那些**没有短路径**的项（4 个提示块、图片、
表格自定大小）；给标题和列表也编号，等于把用户从快路赶到慢路，整体反而变慢。
字母键同理：`w`/`d`/`s`（warning / danger / success）能盲打，`a`/`b`/`c` 不能 ——
连号用一个数字位换来的只是「每次都要看菜单找第 11 项」。

**49. 用正则解析一门语言，注定只在你见过的那几个样本上正确。**

第一版高亮是手写的：一张 17 门语言的关键字表，加一个「注释 / 字符串 / 数字 / 标识符」
的扫描循环，代码块着色再把它的 HTML 摊成字符区间。它在本项目的样例上全绿，因为样例
就是照着它的能力写的。真实代码一进来就露馅：

- 模板字符串里的 `${}` 会被当成字符串外的普通字符；正则字面量 `/a\/b/g` 会被当成注释起点；
- Python 的 `f"""…"""`、Rust 的生命周期 `'a`、YAML 的多行 `|` 全都不在模型里；
- 最要命的是**它只会 17 门语言**，而用户随手打开的是 `.kt` / `.toml` / `.jsonl` —— 没在高亮，
  也没有任何提示。

换 highlight.js 之后，54 门语言、200 多个 `hljs-*` 作用域，这些细节全由语法定义负责。
我们要写的只剩下「把 `hljs-keyword` 映射到 `tok-key`」这种翻译 —— 而这部分错了会立刻
看出来（颜色不对），不会安静地错。

**格式化是同一件事的加强版，而且更危险。** 以前 `formatJSON` 会「保守修复」：全角引号改
半角、删尾逗号、删注释。听起来贴心，实际是拿正则改用户的数据 —— `"价格：1"` 里的全角
冒号会被改成半角，字符串里的 `//` 会被当注释删掉。现在一律交给 prettier：修不了就报
行列、原文一字不动。**判断标准是「错了会不会被发现」**：格式化器错了是静默的数据损坏，
所以宁可少做。

**50. 同一件事写四份，漏的那一份一定在最不起眼的角落。**

「`.jsonl` 有没有高亮」以前由四处各自回答：`highlight.js` 的别名表、`plain-editor` 的
`LANGS`、`format.js` 的 `detectKind`、`app.js` 的新建类型数组。四张表互不校验，于是：

| 症状 | 根因 |
|---|---|
| `.jsonl` 打开是白板 | 别名表里没有它 |
| `.kt` 打开是白板 | `LANGS` 里没有它（hljs 有 kotlin，CM6 的 clike 也有） |
| `.jsonl` 预览报「JSON 语法错误」 | `detectKind` 把它归成 json，`JSON.parse` 当然失败 |
| 新建里只有 10 种类型 | 这是第四张表，早就忘了同步 |

修法不是「把四张表都补全」—— 那还是四张表。改成**一张注册表**（`langs.js`）后，
四个地方都变成查表，`run-units` 里三条断言（`normalizeLang` / `langForFile` / 类型数量）
就守住了以前要靠手测发现的整类问题。

顺带记一条关于自动识别的：**门槛必须跟着库的语义走，不能拍脑袋**。`hljs.highlightAuto`
返回的 `relevance` 随代码长度线性增长 —— 同一个 `SELECT … FROM`，两行时 5 分、二十行时
12 分。所以「≥ 8 分」不是审美，是「十几行以上才稳定」的实测换算；同时要把 CSS / C 家族
这类「长得像任何代码」的语言从候选集里摘掉，否则 TypeScript 会被判成 CSS。这两条都写进
了不变量 60，改之前先跑一遍 `run-units` 里那 12 条识别判据。

**51. 一个「跟着某处走」的浮层，必须有不止一个「当前是哪儿」的来源。**

对比窗口中缝里那对「复制到另一侧」的箭头，纵向位置由「当前是第几处差异」决定。
这个状态原来只有**一个**来源：滚屏 —— 判据是「视口中心落在哪一块」。于是：

- 窗口一打开，`S.cur` 是 0 但**视口中心**先把它算成了中间那一块，箭头停在正中；
- 用户点第 5 处差异行，没有任何代码更新 `S.cur`（`mousedown` 只管放光标，
  `focusAt` 只管选区），**箭头一动不动**；
- 用户报的原话就是「应该随着鼠标点击的地方移动，现在总是偏向中间，点别的差异行没反应」。

修法是在 `mousedown` 里补上第二个来源（`pinCurAt(row)`：落在块内取那一块、落在
两块之间取**最近**一块），优先级 **点击 > 滚屏中心 > 第 1 处**。三条要记：

- **必须落在 `mousedown`**，不能放 `click`：`click` 在 `mouseup` 之后才到，期间
  `focusAt` 可能已经滚过视口，箭头会先跳到别处再跳回来（看着像闪）。
- **必须和「第几处」共用同一个状态**（`S.cur`）。如果给箭头单独一个 `anchor`，
  就会出现「箭头画在第 5 块、Alt+→ 却推了第 3 块」—— UI 在说谎，比不动更糟。
- **别顺手去改 `followScroll` 的判据**。滚屏跟中心是另一条独立需求（不变量 41：
  滚到第 5 处，状态栏就得写第 5 处）。点击优先、滚屏兜底，两者共存才对。

顺带一条同源的：**只读态也要更新它**。只读时不画箭头，但用户点过的位置得记住 ——
否则一按「开始编辑」，箭头会先出现在别处。

**52. 「交给浏览器，它更懂」这句话，只在浏览器真懂的时候成立。**

表格里的 `↑`/`↓` 最早只在「格内没有下一行」时接管，其余放行，注释写的是「交给浏览器
做纯文本的行移动，它更懂折行」。真机上这条假设只在格内**真的**有 `Shift+Enter` 打的
`<br>` 时成立；空格子里那个 `<br>` 只是 `mkCell()` 垫的光标占位，浏览器看完这一格
没有下一行，就按阅读顺序跳到右边一格。

难查的不是跳，是**时跳时不跳**：`setCaretOffset()` 把光标落在 `<br>` 后（这一支接管），
点格子左侧或删空一格则落在 `<br>` 前（这一支放行）。同一个格子按两次结果不同，
用户只能报「逻辑很乱，有时候左右移动，有时候上下」，看不出复现规律。

规矩：**浏览器默认行为在表格里没有「行」的概念，任何放行都是放行给阅读顺序。**
`↑`/`↓` 一律自己算；格内真换行也自己算（按 `<br>` 切字符区间），不借浏览器。
验证要专门造「占位 `<br>` 之前」的落点，还要把旧实现换回来跑一遍确认断言会红 ——
只测有文字的格子，旧实现照样全绿，那就是假绿。

**53. 断言里写死「环境算出来的数」，红的是测试不是产品。**

对比窗口的「滚到 1600px → 第 21 行」是早期行高与栏宽的产物；折几行是按
「可用宽 ÷ 字符宽」算的，换 DPI / 字号 / 窗口宽度就变，本机实测是第 27 行。
三条 `top === '21'` 一起红，可 `27 → 27 → 27` 恰好证明「切换换行模式不跳走」
是好的。正确的契约是：断言「确实滚到了中段」（行号落在合理区间），再拿**实测
的 `top0`** 当基准比较切换前后，并另验 `scrollTop` 真的按新行高重算过
（`setWrap` 的 `rowAtY → rowTop`）。⛔ 别把期望值改成 27 了事 —— 下次换字号又红，
而且那样只证明了断言跟着实现走。

**54. 等异步行为要等「客观前置条件」：不能只睡固定时长，也不能等到断言成立。**

拖选的自滚动由 `requestAnimationFrame` 驱动（`dragTick`）。串跑时前几个探针刚收尾、
主线程偶尔忙一拍，写死的 `10 × 110ms` 会采样到 `top=0`、选区只剩一屏 7 行，
于是「继续滚动 / 松手选区还在 / 跨行删除」三条一起假红，单独跑却全绿 —— 很容易
被误判成产品回归。改成轮询等 `scrollTop > 0`（至少推满原时长、最多 3s），断言
本身一点不放宽，产品真不滚照样红。⛔ 别把循环条件写成「等到 `dragged.top > 0 &&
lines > 40`」：那等于把断言抄进等待条件，断言就再也不会失败了。

**55. 真机几何断言集体变红，先查会话是不是「断开」了。**

`qwinsta` 里当前会话显示「断开」、只有 `console` 是「已连接」时，WebView2 拿到的是
`screen 640×480 / dpr=1 / innerWidth 644`，而 `Win32_VideoController` 仍报 1920×1200 ——
显卡模式和会话显示模式是两回事。于是「大纲生成 30 项」（虚拟滚动只渲染视口内的块）、
滚动高亮、跨块拖选坐标、工具栏折叠、对比窗口铺满工作区这些断言一起假红，看起来像
一次大回归。

**判别法（别靠猜）**：拿改动前的产物跑同一份探针 ——
`APP_EXE=src-tauri/target/release/EZNotepad.exe CDP_PORT=9355 node test/probe-app.mjs`。
旧前端也红，就是环境；顺带还能验证新加的断言在旧产物下确实会红（不是永远绿的假断言）。
⛔ 别擅自改系统显示设置，也别用 `Emulation.setDeviceMetricsOverride` 把视口糊大来「修」：
那会让真机探针不再真机，几何断言失去意义。回到活动桌面会话重跑即可。

**56. 一批红里可能混着一条真回归，别整批归给环境。**

断开会话那次全套 16 条几何假红里，夹着一条「键盘：Enter 执行末项」——
它和滚动、坐标毫无关系，是往转换面板末尾加了删除项、把 `End` 的落点顶掉了。
一次红太多，第一反应就是「都是 640×480 造成的」，差点漏过去。
**判别法**：拿旧产物跑同一个探针，逐条比对 FAIL 的**名字**而不是比数量 ——
旧产物也红的才算环境，只在新产物红的一定是回归。旧前端 `probe-bmenu` 只红
「鼠标换到下一段」一条，「Enter 执行末项」是绿的，真回归当场现形。

另一半教训：**测试段里改过的共享状态要当场复位**。为了验行号槽遮挡，在
`probe-app` 的 G 段把 `.cm-scroller.scrollLeft` 推到 260，没归零就留给后面按
`.cm-line` 可见坐标算落点的右键断言 —— 菜单根本弹不出来，凭空多一条红。
⛔ 别把这种红也记到环境账上；插状态时就在同一段收尾写复位。

**57. 「新建完接着打字」是焦点归属问题；能复现的现象未必是本 bug 的根因。**

`newTab()` → `activate()` → `setMode()` 只把内容画出来，谁都没调过 `focus()`；
而「新建文档」的类型网格是 `dialog()`，关窗只给遮罩加 `hidden`，焦点仍留在那个
`display:none` 的格子上。浏览器不会自动把它转交给编辑区，于是新建完必须点一下正文。
修法是在 `newTab()` 末尾按 `t.mode` 把焦点交出去：所见即所得的空文档用
`focusBlock(first, false)` 把光标钉在第一块首位，普通编辑器用 `plain.focus()`；
非空文档只给焦点、不重摆选区（`caret` / `scrollTop` 归 `setMode()` 恢复）。

更值得记的是**两处「看起来该修」的改动被对照实验否掉了**：对话框初始焦点那个
30ms 定时器关窗后仍会执行、`root.focus()` 在「同一文档 blur→focus」时把 900px
滚动位置拽回 0 —— 单独做实验都能复现，但把修复逐条撤掉再跑真实新建流程，
断言照样全绿，说明它们不在**这条链路**上。⛔ 别把「能复现」当成「是本因」，
也别留一条永远测不到的防御性代码再配一句夸大因果的注释。最终只留可观测收益的
改动；定时器作废按「弹层生命周期卫生」如实标注，不写进因果链。

**判别法**：新断言写完，把修复一行行注释掉跑对照。撤掉主修后 7 条断言立刻变红，
撤掉两处附带改动仍是全绿 —— 前者是真因，后者是噪音。真机还要按**当前模式**分派
断言：`lastMode` 被前面的用例留在 `edit` 时，假定新建 md 一定是所见即所得会凭空造红。

**58. 给对话框加单键快捷键，键帽要扛得住 i18n；测弹层的探针别把它的 Promise 交出去。**

未保存三选原来只有 Enter / Esc，Y / N 只能靠鼠标。通用 `dialog()` 接 `b.key`
（`'Y'` / `'N'` / `'Esc'`）时有三处容易漏：键帽**不能**内嵌 `<kbd>` ——
静态按钮（对比窗口关窗确认条）带 `data-i18n`，切语言时 `applyI18n()` 用
`textContent` 整体覆写，子元素当场消失；改成 `::after { content: attr(data-key) }`
配 `aria-keyshortcuts`，属性和 DOM 结构都不受影响。字母键只在「焦点不在输入框、
没在组字、没按 Ctrl / Alt / Meta」时接管，Escape 例外（它本来就是取消）。
对比窗口那套确认条不走 `dialog()`，键盘得自己接。⛔ 别把模态分支塞进常驻的
全局 `keydown` 再靠 `hidden` 判断：只要有一次状态没复位，正文的 Ctrl+A /
Ctrl+Z / Alt+→ 会被整批吞掉（真机一次红了九条，旧前端逐条对照才认出来）。
正解是 `showCloseConfirm()` 时把 `onConfirmKey` 挂到 document 的 capture，
`hideCloseConfirm()` 时摘掉，鼠标与键盘共用同一组出口动作；监听里还要再看一眼
`confirm.hidden` —— 窗口复用时上一轮弹的确认条可能没走 hide，隐藏状态下绝不许
碰正文按键。测试侧 `openPair()` 每次连上窗口先按「取消」复位确认条，别把模态
状态留给下一段。没有磁盘目标时「保存并关闭」是隐藏的，`Y` 也该一并失效。

更贵的一个坑在测试侧：`harness` 的 `ev()` 开 `awaitPromise: true`，
`await ev('window.__snp.commands.quit()')` 会一直等用户按完键才 resolve，
而按键又是下一条 `ev` —— 两边互相等，探针挂到超时且**一行输出都没有**
（断言是最后统一打印的）。触发弹层一律用 `(() => { cmd(); return 1; })()`
把 Promise 吞掉。⛔ 别把「测试卡住」当环境慢，先查有没有把未决 Promise 交给 CDP。

这次还顺出一个**真 bug**：`contextMenu()` 换菜单时只 `menu.remove()`，
而它的 Esc / mousedown 监听挂在 `document` 的 capture 上；`close()` 又拿
`if (!menu.isConnected) return` 当「已经关过」，于是 DOM 没了、监听还在 ——
开过两次右键菜单之后，每一次 Esc 都被幽灵菜单 `stopPropagation()` 吞掉，
未保存提示的「Esc 取消」跟着失效。真机探针第一条 Esc 断言红、N / Y 却绿，
正是这个顺序：那一次 Esc 顺手把幽灵监听清掉了。修法是模块级记住当前菜单的
`close()`，换新菜单前先调它，用显式 `closed` 标志代替 `isConnected`，
`setTimeout(..., 0)` 注册监听前也先看一眼 `closed`。测试里同样别直接
`m.remove()`，点一下空白走菜单自己的关闭路径。⛔ 浮层监听挂在 document 上
时，「摘 DOM」不等于「卸载监听」。

**判别法**：撤掉字母键映射，N / Y 两条断言立刻红；撤掉输入框守卫，
「弹层输入框里按 Y 不会误关」变红并连累后面一串；把菜单清理逻辑退回旧版，
「连开两次浮层菜单后 Esc 仍能取消对话框」立刻红 —— 每条都有可观测收益。

**59. 「高亮」在两种编辑器里是三件不同的事，别让一个命令通吃。**

用户连着报了三条：当前行底色太深、选了一段字该把全文相同的字一并标出来、非 md 文件点
「高亮」只多出两个等号却没颜色。三条看着都是「加个底色」，根子是**语义没分层**：
`==文字==` 是文档内容，当前行 / 选区匹配是跟着光标走的临时提示，重复行是行级开关。
原来 `toggleHighlight()` 对所有文件一律往源码里插 `==`，到了 `.py` / `.txt` 里那两个等号
既不是语法也不会被渲染 —— 文件被改脏了，屏幕上什么都没发生。更隐蔽的是
`selectionHighlighted()` 用「源码里有没有 `==`」判「是否已高亮」，于是 Python 的
`a == b` 被判成已高亮，再点一次只删等号，文件当场坏掉。

修法是按 `detectKind(t.name)` 分流：md 保持原样（所见即所得写 `<mark>`、编辑模式写 `==`），
其余一律用 CM6 的 `StateField` + `Decoration.mark` 上黄底，区间存 `t.viewMarks`，
`docChanged` 用 `map` 跟住正文、`plain.load()` 之后按标签重放。当前行则从 `--accent` 7%
换成中性灰 3% / 5%：**强调色只表示状态**，拿它铺满一整行，深色主题下就是一条橙红横杠。

第二层坑在「看起来能直接用的现成件」上：`@codemirror/search` 的 `baseTheme` 自带亮绿
`.cm-selectionMatch`，不在 `editor/theme.js` 里显式覆盖就白捡一条荧光绿；参数叫
`minSelectionLength` 而不是 `minLength`，写错了不报错、只是中文单字不生效 —— 中文一个字
就是一次完整选择，把门槛设成 2 会静默丢掉最常见的情况。所见即所得那侧
`CSS.highlights` 是全局表，`_render()` / `clearView()` 不注销 `sn-same`，切标签后
上一份文档的灰底会一直挂着。⛔ 这三条都不报错、不崩溃，只有 computed 底色与实际选区
能对出来，所以断言必须量样式、不能只数 DOM 节点。

还有一条**只会在真机暴露**的口径差：CM6 的 `getDeco` 明确跳过主选区自身，
所见即所得的 `sn-same` 却把选中那处也算进去。三个「红」选第一个，一边是 2 处、一边是 3 处。
离线用例恰好写的是 `>= 2` 就绿了，真机按「3」卡立刻红 —— ⛔ 别把这种红当实现缺陷去改扩展，
先去读依赖源码判清语义；也别为了让数字一样给选区再叠一层装饰，那是拿视觉换断言。

**判别法**：把 `.cm-activeLine` 改回 accent，computed 底色断言立刻红；把 `MIN_LEN`
调回 2，「选中『红』标出三处」红；删掉 `toggleHighlight()` 的分流，`run-app.mjs` 的
「非 md 不写 `==`」与「`a == b` 不误判」两条同时红 —— 每条都能单独观测。

### 15.3 视觉与文案（75～77 的来龙去脉）

**起因**：2026-11-09 那一轮不是「改几个颜色」，而是把整个界面换到一套**有出处的色板**
（Radix UI Colors）上，并顺手把字号、圆角、边框、动效、文案一起收口。之所以要一次做完，
是因为这五件事互相咬：只换颜色不换边框，0.5px 的线配着 3/6/9 的圆角照样乱；只改文案
不改层级，省下来的字会被更显眼的装饰吃掉。

**色板的价值不在颜色本身，在「第几步 = 什么语义」**。定了这条之后，判断「这个底色
该取哪一档」就不再是审美问题，而是查表：分区块 → 1–2，组件面 → 3–5，边框 → 6–8，
实心填充 → 9–10，低对比字 → 11，正文 → 12。这也是唯一能让九个组件看起来像一套的办法。

**深浅两套的方向是反的**，这是最容易翻车的一处。Radix 暗色第 1 步**最暗**，所以
「纸面比侧栏亮」在亮色下是 1 vs 2、在暗色下必须写成 2 vs 1。照抄步号的结果是两块
糊成一片 —— 而截图里两块差不多的深灰，第一眼很难说出哪里不对，只觉得「脏」。

**「浮层上的控件」必须单开令牌**。这是本轮最实在的一个 bug：暗色浮层取第 3 步，
而所有控件的「浅坑」也取第 3 步，于是设置面板整片控件消失。合成一个 `--bg-soft` 是
省事的写法，但「凹进去」和「凸起来」是两个方向，在暗色里必然分成两个值。
最后分成 `--bg-soft`（纸面上的坑）/ `--bg-well`（浮层上的坑）/ `--bg-chip`（浮层上的
浅色按钮）/ `--bg-raised`（浮起来的选中项）四个，每个都有明确的一句话语义。

**0.5px 是被截图逼出来的**。1px 的线在同色平面上像用尺子划过一条，界面上到处是「框」；
落成半像素覆盖之后，它才回到「一条分界」的分量。代价是所有用 `box-shadow` 画的线
都得改成真边框 —— 顺手把「线归线、影归影」也做了，浮层从此只有一层投影。

**字号从 22 种收到 4 种**。原来的层级是「一点点缩」，`11.5 / 12 / 12.5 / 13 / 13.5`
各差半号，读者根本分不出来，只剩「整体偏小、偏密」。收成 12 / 13 / 15 + 编辑器之后，
层级交给**字重、颜色、间距**，反而更清楚 —— 顺带把 12px 定成下限（再小在 100% DPI 上就是糊的）。
同一个道理中文⛔ 不加 `letter-spacing`：`.04em` 的字距加在四字标签上只会让它散开。

**「卡片彩边」是一种 2010 年的语汇**。引用块、提示块、JSON 校验条、块公式、重复行、
大纲当前项原来都在左沿挂一条 2–3px 彩条。它确实能表达分类，但代价是整个界面充满了
左边一条一条的颜色，看起来像后台模板。改成「底色 + 标题字色」之后，同样的信息还在，
页面安静下来了。

**文案的问题不是长，是「说了不该由界面说的话」**。`自动保存（停手约 1 秒写盘）` 里那半句
是实现的细节；`要保存吗？` 下面就是三个按钮；`3 920 字 · 5 128 字符` 用一个中点把两个
数粘成一句。判断标准只有一条：**这句话删掉，用户会不会做错事？** 会 → 留；不会 → 删。
按它删掉了 14 条词条、3 条设置说明、状态栏的「已保存」、以及每个对话框末尾的追问。

**改文案的连带成本在 i18n**：词条表的键就是简体原文，改名等于新增一条 + 删掉一条，
九种译文要一起写；删掉的键如果还有调用点，`test/run-i18n.mjs` 的覆盖率断言会立刻红。
所以这轮把「先改代码、再跑 i18n、看它报哪条没收录」当成固定流程，报错信息就是待办清单。

### 15.4 窗口化列表：三条独立缺陷叠成同一个症状（78、79 的来龙去脉）

**症状**：文档写长之后，滚到底，大纲里一个高亮都没有。几十行代码看下来「索引算的是
第 30 节」，可 DOM 里搜不到 `.outline-item.active`。

**根因是三层，任何一层单独存在都只是小毛病，摞在一起才变成空白**：

1. `renderOutlineWindow` 用 `list.replaceChildren(...)` 重建那一段。DOM 规范里摘掉
   全部子节点 = 容器高度归零 = 浏览器立刻把 `scrollTop` 夹到 0；内容插回来不会自动
   复原。于是每次重铺都把用户踢回顶部。
2. `paintOutlineActive` 只给「已铺出来的节点」加类，窗口外的那一项 `at(cur)` 是
   `null`，加类加在空气上。**更隐蔽的是它的 `if (cur === outlineActive) return`**：
   第一次算对、类也加上了，随后被第 1 条搞丢，但索引没变，于是之后每次调用都提前
   返回 —— 自己把自己的重试机会掐掉。
3. `revealOffset(atTop)` 只校一次落点。CM6 首屏用的是估算行高，滚一次才把视口外的
   行真正测出来：120 行的文档实测**长高近 500px**。按旧布局算出来的目标位置，在新
   布局里已经偏了一整行，于是点「第 22 节」高亮停在第 21 节。

**修法各归各位**：重铺前后存写 `scrollTop`；高亮项不在窗口内就先把列表滚过去再点亮；
`revealOffset` 在下一帧按新布局再校一次。三处都只多几行，但少任何一处症状就会回来。

**为什么平时看不见**：窗口一大，侧栏一次能铺下全部条目，窗口外这个前提根本不成立；
滚动距离小，估算行高与实际差得也少。把窗口缩到 620×420 的下限，三条一起现形。

**排查方法值得记一笔**：一开始都在猜「窗口太小」「渲染没跟上」，直到把内部状态打成
一行 JSON（`start/end/active/nodes/top/same/connected`）才看清 `top` 是 0 而
`active` 是 29 —— 于是问题从「高亮为什么丢」立刻变成「列表为什么滚不动」。**先量，
再猜**；量的时候把「我以为它是真的」那几个值全打出来，包括引用是否还连通。

**顺带挖出的测试缺陷（79）**：探针 A 段把侧栏切到文件页之后没切回来，后面整段大纲
测试都在 `clientHeight: 0` 的隐藏容器里跑。元素在、DOM 查询能过一半，滚动全失效 ——
失败项看起来毫无规律（数量不对、高亮不对、点击不对），其实只有一个原因：它不在台上。
另外，窗口化列表的总条目数**永远不能数 DOM**（只铺可见段），要给探针一个只读钩子
（`__snp.outlineCount()`）去问真实条目数，再用「滚到底看最后一项」验证渲染也到位。

## 16. 真机验证：比单测贵十倍，也只有它能抓到单测抓不到的

**1. 分层：单测抓逻辑，真机抓「系统集成」。**
本项目 155 项单测全绿，但「菜单开窗口页面白屏」「tao maximize 失效」这类
问题只有真机能暴露。真机工具链自己搭（UIA 按键名找菜单、SendInput 合成鼠标、
CDP 读状态、BitBlt 截图 + 局部放大），比引入 Playwright/Electron 系工具轻得多。

**2. 合成点击的坐标系要「相对量」。**
无边框窗口铺满/还原切换后绝对坐标全废。约定从窗口右下角（或矩形）量坐标，
放大截图人工量按钮位置一次、写进用例生成器，之后窗口尺寸再变也不怕。
特别注意 DWM 隐形边框：窗口 rect 原点不在可见区左上角（实测 `-7, 0`）。

**2.5 输入前必须验证「前台真的是被测窗口」。**
SendInput 的点击/键盘落点是全局的：另一个应用（比如最大化还弹着对话框的
Chrome）盖在屏幕上时，全部输入静默落进它那里，而 `PrintWindow` 截图不依赖
z-order，画面永远「看起来正常」——这个组合能浪费一整个下午。正解是发输入前
`ForceFocus` 并**核实** `GetForegroundWindow()`，失败就大声报错，绝不静默继续。

**2.7 原生文件对话框走 Win32，不走 UIA。**
Vista+ 的 IFileDialog 保留老模板控件 ID（路径框 1148/1152、IDOK=1），UIA 对
路径框暴露不稳定且新建顶层窗口可能几秒都进不了托管 UIA 的桌面查询。
路径用 `WM_SETTEXT`（文件夹选择器**不收正斜杠**），找对话框用
`EnumWindows`（可见 `#32770` + pid），确认用 `PostMessage(BM_CLICK)`——
**SendMessage 等回复期间对话框自我销毁会直接崩掉调用进程**；报 ok 前等对话
窗口真正消失，否则「文件夹名无效」的横幅会把假成功递给你。

**3. 每条真机用例自带断言与夹具重建。**
用例开头先重写夹具文件（不依赖上次运行残留），结尾用字节比对校验收盘内容，
中间的关键状态（窗口矩形、页面标题、统计行文字）靠 `wins` / 截图三重交叉。
**「看起来对」不算过，能机器判读的判读，不能的截图放大人工看。**

**4. 测试环境的噪音要提前识别。**
vitest 在沙箱里报 `EPERM ...\Temp\...` 是环境噪音不是项目缺陷（`TMP` 指到
`node_modules/.tmp` + `--no-file-parallelism` 可绕）；`cargo test` 报
「拒绝访问 os error 5」多半是残留进程占着产物，重跑即可。**先分类「假失败」，
别急着改代码。**

## 17. 过程方法论

**1. 一次只怀疑一个变量。**
「菜单路径白屏」排查走过：先怀疑时序 → 加前端兜底 → 怀疑权限 → 怀疑
`on_page_load` 没触发 → 最后靠全链路日志锁定 `build()` 阻塞。回头看，第一步
就该埋日志；**盲改三处不如日志一处**。

**2. 修完立刻删诊断代码，但把结论写进文档。**
本轮日志、看门狗、标题诊断全部清干净后才提交，根因与修法沉淀到
`RESULTS.md` 的「这轮修掉的 4 个坑」表格。代码要干净，**知识要留下来**。

**3. 根因修法要能一句话讲清。**
「tao 标志位先写后跳过」「同步命令占主线程」——如果一个 bug 的根因不能
一句话说清，说明还没真正定位，修了大概率会复发。

**4. UI 的美观靠纪律不靠灵感。**
三层底色分界靠面不靠线、圆角只有三档、accent 只给当前态、浮层不写 border
走 shadow —— 这些约定写进长期记忆，每次新界面照抄，风格自然统一，评审
成本趋近于零。

### 17.1 和模型结对时才成立的七条

这个项目绝大部分代码是模型写的。上面四条是通用方法，下面七条只在「代码由模型写、
由人验收」时成立 —— 每一条都对应一次真实的假绿或一次返工，不是原则宣言。

**1. 「改好了」要落到产物上验，不能读代码点头。**
模型能写出读起来完全正确的补丁而实际没进二进制：前端是**编译期内嵌**的，改了
`src/` 不 `cargo build`，探针读到的还是旧界面，于是「新功能没生效」。自检不是
「再看一遍代码」，是 `fetch('js/xxx.js')` 里搜新函数名 —— 名字在，才是真的在。

**2. 接管旧进程 = 假红。**
探针发现 CDP 端口已就绪就直接复用现有进程，于是**刚重建的代码不生效**：新分支
看起来像「没写对」，同一用例换个写法又通了，极容易误判成逻辑错误。规矩是先
`taskkill /IM EZNotepad.exe /F /T` 再 `ensureApp()`，再搜一遍新常量确认换的是新壳。

**3. 别用「重启」验证启动期行为。**
WebView2 的 `localStorage` 延迟落盘：写完立刻杀进程，草稿可能还在缓存里没落地，
于是启动时「恢复草稿」不弹，用例假绿（等 6 秒再杀一样丢）。启动顺序这类不变量
改用 `run-units.mjs` 读源码断下标 —— 两条静态断言比十次重启可靠。

**4. 绿条不等于验过。**
判据只有一条：**把被测函数删掉，这条用例会不会红**。绕过被测对象直接改状态、
用 mock 盖住真集成路径，都能让测试全绿而功能全坏。本项目的对应做法是真机探针
只经由 UI 与文件系统操作，不 import 模块调内部函数。

**5. 文档漂移是结对开发的第一大债。**
模型改代码时看不到文档全文，改完就往下走。于是「工具行只留三个」能活过两轮修订，
而实际是五个；「注释写着行底淡红」能撑到整个设计换掉。规矩是**以代码为准、当场
改文档**，并且文档里写**判据**而不是形容词 —— 写「`mark ≤ 16 个字符` 且正则尾部
必须带一个空格」，下一轮照得对；写「应该好看一点」，下一轮只能靠猜。

**6. 「想清楚不做的事」必须写进文档，否则下一轮会被热心补上。**
跨文件替换整体删除后，若不写进《功能设计》的「明确不做」并给出理由，下一轮很
容易被「顺手补齐」——模型倾向于把看起来缺的能力补全。**否决的理由和决定本身一样
重要**，它是唯一能挡住下次重做的东西。

**7. 一次只怀疑一个变量 —— 对模型尤其重要。**
模型倾向于「三处一起修」，修好了也不知道是哪一处起的作用，复发时无法归因。
先埋一条日志、只改一处，比盲改三处快得多；本轮「菜单路径白屏」就是盲改三处
之后才回去埋日志的。

⚠️ 共同的底层事实：**上下文会丢**。下一轮能读到的只有代码、文档和探针 ——
留在对话里的推理等于没写过。所以这条链的顺序是：结论 → 写进文档 → 变成断言，
少任何一环，下一轮就要重新踩一遍。

## 18. 如果重来一次

- **窗口管理第一周就该建真机工具链。** 多窗口、无边框、DWM 这些问题躲不掉，
  晚建工具链 = 晚发现 = 晚修。
- **Tauri 的命令签名表（sync vs async）该在项目开头立规矩**，而不是踩一次坑改一处。
- 单测对「编辑器」这类强 DOM 组件覆盖有限，**jsdom 测不到光标、滚动、合成层**；
  对这类模块，几个精心设计的真机用例价值超过几十个组件测试。
- `--compare 左 右` 这类命令行入口成本极低（几十行 Rust），却是自动化测试的
  最佳抓手 —— **给每个复杂功能留一条绕过 UI 的直开通道**，测试会感谢你。
- **平台 API 要先确认「真的有实现」，而不是相信接口名。** `window.print()` 是标准接口，
  在嵌入式 WebView 里却是空函数：不弹框、不报错、不 reject。整整一版功能「点下去没反应」，
  查权限、查弹窗拦截、查 CSP 全查空了，真凶是一句能编译能运行的空实现。
  教训：**凡是没有返回值也没有异常的外部调用，都要先给它一个「现象可观测」的探针**。
- **体积与内存预算要在动手前量，而不是做完再解释。** mermaid 单文件 5.12MB / 渲染后
  JS 堆 +21MB，两个数字拿到之后「集成 / 不集成」就是一道算术题；反过来先做再解释，
  很容易被「反正已经做了」绑架。
- **「这段 DOM 属于谁」这类隐性归属，必须写成显式变量。** 编辑器 DOM 是共享的一块舞台，
  标签是轮流上台的演员；靠「当前是谁」去反推「这堆 DOM 是谁的」，迟早把 A 的正文写进 B。
  `renderedTabId` 只是一个字符串，却消掉了一类「清空速记把别的文档清了」的幽灵 bug。
- **内存高先量三件事，别猜**：进程拆分（GPU / 页面 / 网络各自多少）、合成层数量与面积、
  隐藏但没销毁的 DOM 节点数。这次 900 行文档 39k 字符的实测结论是
  「**占用基本合理，没有明显浪费**」—— 但顺手发现的 `display:none` 预览 DOM 是真实的 6000+ 节点，
  也就是唯一值得做的那处优化。
