## 改完代码要同步哪些文档

**规则：代码与文档冲突时以代码为准，然后当场把文档改掉。** 不写「回头再补」——
下一轮改动就会照着错的文档改（《实现规格》初稿里四处错误全是这么来的）。

| 你改了什么 | 必须同步 |
|---|---|
| 用户能感知的行为（默认值、交互、文案） | 《功能设计》对应章节 + 《功能详解》对应小节 |
| 界面尺寸 / 颜色 / 图标 | 《功能详解》取值表 + §18.2 颜色表 + 《实现规格》§11（若涉及阈值） |
| 解析器 / 序列化 / 差异算法 | 《实现规格》§4 / §7 + 附录 A、B 的测试向量 |
| 新增 IPC 命令 | 《架构设计》命令表 + 《实现规格》§1 原语表 |
| 新增设置项 | 《功能设计》设置章 + 《功能详解》§10 + `state.js` 的 `__v` 判断 |
| 新增窗口 | 《架构设计》窗口表 + `capabilities/default.json` 的 `windows` + 《功能详解》新一节 |
| 修一个踩过的坑 | 《功能详解》该功能的「坑」段 + `.workbuddy/memory/` 当日日志 |

**新增一个功能时**：先写《功能设计》的承诺 → 再在《功能详解》加一节（固定六段：
一句话 / 为什么这样 / 取值表 / 实现 / 坑 / 验收）→ 有新算法就补《实现规格》→
加验收（`test/run-*.mjs` 或 `test/probe-*.mjs`）→ 一个功能一个提交。
细节见《功能详解》§20。

## 给「要开发 mac / Linux 版」的读者的最短路径

1. 读《跨平台移植》§0～§1 的总览表，先知道**只有 4 项是阻断级**，不必整体重写。
2. 读《架构设计》§3（运行时结构）和 §4（前端分层）——业务逻辑不用改，但要知道边界在哪。
3. 按《跨平台移植》§9 的 M1～M6 里程碑推进，每步都有验收标准。
4. 遇到「改了没反应」先看《构建说明》§二的三条铁律（前端是编译期内嵌的）。
