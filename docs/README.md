## 改完代码要同步哪些文档

**规则：代码与文档冲突时以代码为准，然后当场把文档改掉。** 不写「回头再补」——
下一轮改动就会照着错的文档改（《实现规格》初稿里四处错误全是这么来的）。

| 你改了什么 | 必须同步 |
|---|---|
| 用户能感知的行为（默认值、交互、文案） | 《功能设计》对应章节 |
| 界面尺寸 / 颜色 / 图标 | 《功能设计》该章的「落地」小节 + §16.9 颜色表 + 《实现规格》§9.7 令牌表 + §11（若涉及阈值）；**程序图标另走** `scripts/app-icon.mjs` + `pnpm icons:app`，见 §9.8 |
| 换了图标 / 换了构建期资源 | 《实现规格》§9.8 的生成链与 `build.rs` rerun 说明；《构建说明》「界面图标、应用图标与 KaTeX」；重编后核对 exe 内嵌 ico 帧 |
| 解析器 / 序列化 / 差异算法 | 《实现规格》§4 / §7 + 附录 A、B 的测试向量 |
| 新增 IPC 命令 | 《架构设计》§7 契约 + 《实现规格》§1 原语表（若引入了新的宿主能力） |
| 新增设置项 | 《功能设计》§8 + `state.js` 的 `__v` 判断（新增键不 bump，改默认值必须 bump） |
| 新增窗口 | 《架构设计》§3.1 + `capabilities/default.json` 的 `windows` + 《功能设计》新一节 |
| 修一个踩过的坑 | 《架构设计》§15 加一条（编号接上，§19 索引同步）+ 《功能设计》该功能的「坑」段 |
| 宿主 API 用法变了（窗口 / 文件 / 剪贴板） | 《实现规格》§1 原语表 + §10.4 对应条目 |

## 新增一个功能的五步

1. **先在《功能设计》写「对用户承诺什么、不承诺什么」**——写不出来说明功能还没想清；
2. 同一章末尾的「落地」小节补取值（每个数都要能说出「从哪来」）；
3. 有新算法就补《实现规格》，新常量登记进 §11；
4. 加验收：离线进 `test/run-*.mjs`，真机进 `test/probe-*.mjs`，并在文档里写明探针名与条数；
5. 一个功能一个提交，提交信息写清「为什么」。

## 四条不许

- ⛔ **不许只写「应该好看一点」**这种无法验收的描述。要么给数，要么别写。
- ⛔ **不许把早期设计留在代码注释里**（`compare.js` 开头那段「行底淡红 / 行号栏红竖条」
  就是反例）。改设计时，注释和 CSS 一起改。
- ⛔ **不许在文档里写「见源码」了事**。文档的价值就在于不用翻源码。
- ⛔ **不许四份文档各说一套**。冲突时以代码为准，然后**同时**改掉相关的每一份。

## 给「要开发 mac / Linux 版」的读者

1. 读《实现规格》§10.4 的总览表，先知道**只有 4 项是阻断级**，不必整体重写；
2. 读《架构设计》§3（运行时结构）与 §4（前端分层）——业务逻辑不用改，但要知道边界在哪；
3. 按 §10.7 的 M1～M6 推进，每步都有验收标准；**M1 之后先做 M3 的手工回归**（无边框方案选错，
   后面的结论全部重来）；
4. 遇到「改了没反应」先看《构建说明》§二的三条铁律（前端是编译期内嵌的）。
